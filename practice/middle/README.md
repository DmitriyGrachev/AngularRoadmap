# Продвинутый этап: Angular для Fullstack-разработчика

Этот этап опирается на уверенное владение Java, Spring Boot, JPA, SQL и backend-тестами. Его цель — научиться самостоятельно доводить frontend-изменение до проверенного результата и объяснять границы решения. Прохождение материалов и зелёные проверки сами по себе не подтверждают профессиональный уровень.

## Перед началом

Пройдите недели 1–6 либо самостоятельно повторите итоговый сценарий базового трекера: список с поиском через URL, прямой переход в детали, typed form, POST/PATCH, сохранение ввода после ошибки и тест поведения. Если приходится копировать готовый ответ, вернитесь к соответствующему уроку. Рабочая первая задача может выполняться параллельно курсу, но сложные новые темы опираются на эти механизмы.

Недели 7–12 добавляют 90 часов: три занятия по 3 часа и один практикум по 6 часов на модуль. Делите занятия на удобные сессии, а практикум — на два-три дня. Ещё 0–5 часов в неделю оставляйте на повторение и чтение рабочего кода. Указанные часы — план, а не таймер, после которого тему надо принудительно закрыть.

## Проверяемая практика

В папках `middle-01`…`middle-12` находится независимая задача на один механизм. Начните с её README и описания в лаборатории сайта.

```powershell
cd C:\ProjectsDirectory\Angular
npm.cmd run learn -- check middle-01
```

Редактируйте `solution.mjs` или `solution.ts`, указанный в задании. `starter.*` сохраняет исходный вариант. Начальная неуспешная проверка ожидаема. После своей попытки используйте подсказки, затем при необходимости сравните с отдельным авторским примером в `author/solutions/middle-XX`. Команда проверки не переносит авторский код в ваше решение.

Каждый запуск выдаёт новый JSON в `practice/reports`. Импортируйте именно его на странице «Прогресс». После изменения кода снова выполните проверку. Если часть проверок пройдена, а часть нет, прочитайте сообщение и воспроизведите конкретный случай: не заменяйте возвращаемое значение только ради одного примера.

| Задания | Что проверяется |
|---|---|
| middle-01 / 02 | Ограничение параллелизма, порядок результатов и внешние DTO |
| middle-03 / 04 | Инварианты Signal-store и восстановление состояния из URL |
| middle-05 / 06 | Кэш Observable и последовательная обработка записей |
| middle-07 / 08 | Вложенные формы и ошибки строк по устойчивому ID |
| middle-09 / 10 | Ошибки API и конфликтующие оптимистичные изменения |
| middle-11 / 12 | Качество написанных вами тестов и границы окна большой таблицы |

## Ручная практика и работающий проект

Папки `w7-03-ex1`…`w12-workshop-ex1` содержат постановку и `notes.md` для ваших доказательств. Это не двенадцать новых приложений: вы реализуете изменения в существующем учебном трекере или Service Desk, как указано в конкретном задании. Поле `notes.md` не заменяет работающий код — запишите путь изменения, наблюдаемый результат, проверки и ограничения.

Команды выполняются из корня всего проекта, каждый сервер — в отдельном терминале:

| Для чего | Команда | Адрес |
|---|---|---|
| Курс и результаты | `npm.cmd run site` | http://127.0.0.1:4300 |
| Ваш Angular-трекер | `npm.cmd run practice:angular` | http://127.0.0.1:4302 |
| Его HTTP API на Java | `npm.cmd run practice:api` | http://127.0.0.1:8080/api/issues |
| Разобранные примеры | `npm.cmd run practice:labs` | http://127.0.0.1:4304 |
| Service Desk для UI-задач | `npm.cmd run practice:workplace` | http://127.0.0.1:4305 |

Service Desk использует API в памяти: в нём нельзя доказать корректность реальных HTTP-заголовков, серверной авторизации или транзакций. Для полного пути до backend используйте интеграционный практикум недели 11 и собственный локальный Spring Boot backend по его контракту. Встроенный JDK-сервер первых недель также не превращается автоматически в production-систему с БД и авторизацией. Материалы отличают исходную реализацию от возможностей, которые вы должны добавить сами.

## Как проверить самостоятельность

После решения измените одно требование: новая строка DTO, второй потребитель кэша, поздний ответ, другой порядок строк формы, конфликт двух вкладок. Предскажите результат и проверьте его. Запишите в журнал не только исправление, но и предположение, которое оказалось неверным.

Итоговая защита в уроке w12-workshop требует работающей функции, изменения через весь стек, воспроизводимого инцидента и объяснения решения. Сохраните запрос/ответ, тесты и шаги воспроизведения; скриншот успешного экрана не доказывает обработку отказа. Внешний review коллегой полезен, но курс не требует отправлять рабочие исходники или использовать платный сервис.

Прогресс курса и журнал экспортируются отдельно. У новых материалов те же правила хранения, что у базового этапа; успешная проверка не ставит отметку «могу объяснить» автоматически.
