# Полезные проверки: функция, HTTP-сервис и форма

120 минут. Результат: три небольшие проверки ловят три разных нарушения поведения. Нужны [первые тесты](/lessons/w2-05), [HTTP testing](/lessons/w4-05), [форма](/lessons/w5-05).

## Ситуация и прогноз

Тест вызвал метод фильтра и проверил только `expect(true).toBe(true)`. Он зелёный, но что произойдёт после удаления фильтрации? Ничего. Проверка полезна, когда связана с требованием и меняет результат при нарушении. До написания сформулируйте конкретное поведение, вход и наблюдаемый выход.

## Три границы, три типа проверки

Чистую функцию удобно проверять прямым вызовом: вход не требует браузера, результат не требует ожидания сети. Для фильтра важны обычное совпадение, отсутствие совпадений и вариант «все». Один пример не доказывает, что параметр вообще используется: набор должен включать записи, которые обязаны быть исключены.

HTTP-сервис проверяют с тестовым backend. Он ловит неверный URL, метод, параметры и чтение envelope без настоящей Java-сети. Внешний API при этом не проверяется. Не заменяйте сам сервис объектом, который сразу отдаёт желаемый результат, если цель — проверить построение запроса внутри этого сервиса. Подменяйте границу транспорта, а не проверяемую логику.

Компонент формы проверяют через TestBed и, когда требуется, DOM-события. TestBed создаёт Angular-окружение с зависимостями. Для standalone-компонента используют imports, а не declarations. Сервис можно подменить коротким fake с Observable ответом, потому что здесь цель — реакция компонента на успех/ошибку, а построение HTTP проверено отдельно.

Прямой вызов submit полезен для guard invalid-формы, но не докажет, что кнопка действительно связана с ngSubmit. Для такого требования нужна проверка пользовательского действия через DOM. Не тестируйте private-поля только потому, что их легко прочитать. Наблюдаемый текст, вызов команды с DTO и отсутствие вызова при invalid — устойчивее внутреннего названия signal.

## Разобранная демонстрация

Полный файл: `practice/angular-labs/src/demos/filter.spec.ts`. Из корня выполните `npm.cmd run practice:labs:test`. Ожидаются четыре зелёные проверки лаборатории, две из них — availableBooks из этого файла. Java API не нужен. Здесь данные подобраны так, что ошибка «вернуть весь массив» действительно будет обнаружена. Для опыта меняйте этот demo-файл, а не ученический фильтр; после красного запуска восстановите код.

```ts
import { describe, expect, it } from 'vitest';

type Book = { id: string; available: boolean };
function availableBooks(items: Book[], onlyAvailable: boolean): Book[] {
  return onlyAvailable ? items.filter(item => item.available) : items;
}

describe('availableBooks', () => {
  const books = [
    { id: 'a', available: true },
    { id: 'b', available: false },
  ];
  it('исключает недоступную книгу', () => {
    expect(availableBooks(books, true).map(book => book.id)).toEqual(['a']);
  });
  it('оставляет обе при выключенном фильтре', () => {
    expect(availableBooks(books, false)).toEqual(books);
  });
});
```

Сначала запустите тест в корректном варианте. Затем во временной копии замените тело функции на `return items`. Первая проверка должна упасть, вторая остаться зелёной. Верните реализацию и повторите запуск. Это контролируемая проверка чувствительности теста, а не требование хранить сломанный код.

Вариация: добавьте пустой вход. Спросите себя, какую новую ошибку он способен выявить. Если новый test только повторяет код реализации тем же выражением `filter`, он может скопировать ту же ошибку. Ожидаемые IDs в примере записаны независимо от алгоритма.

## Асинхронные случаи

Тест должен дождаться результата проверяемой операции. Подписка, которая завершится уже после выхода тестовой функции, может дать ложный успех. Используйте поддерживаемый runner способ ожидания: возвращаемый Promise, async/await с firstValueFrom либо управляемый HttpTestingController.flush. Не добавляйте произвольное ожидание «две секунды должно хватить»: это замедляет suite и зависит от компьютера.

При проверке ошибки форма должна сохранить ввод, снять saving и показать объяснение. Нужен тест, который действительно выдаёт error из fake-сервиса, например `throwError(() => new Error(...))`, а не возвращает успешное `{ error: true }`, если компонент ожидает канал error. Для повторения fake должен позволять второй исход; иначе тест не проверит восстановление.

После каждого HTTP-теста `verify` обнаруживает неожиданные незавершённые запросы. Failing expectOne может означать, что запрос не создан из-за отсутствия подписки. Не меняйте ожидаемый URL на фактически ошибочный только ради зелёного результата: сначала вернитесь к контракту.

## Мост от Java

Fake сервиса похож на Mockito stub, но Observable может синхронно выдать значение или ошибку. Это способно отличаться от сетевого времени. Поэтому тест компонента не заменяет ручной медленный сценарий. TestBed также не поднимает Java ApplicationContext: зависимости backend здесь отсутствуют, а response DTO остаётся обычным объектом JavaScript.

## Практика в IDE — w6-03-ex1

В `practice/issue-tracker/src/app` дополните `issue.service.spec.ts`, `issue-form.spec.ts` и при необходимости вынесите существующую чистую фильтрацию в маленькую функцию с соседним spec. Не извлекайте абстракцию только ради теста, если функцию уже можно проверять напрямую. Проверьте фильтр, GET с параметрами и invalid/ошибочный submit.

Запустите `npm.cmd run practice:test -- --watch=false`. Для одной проверки временно внесите относящееся к ней нарушение в отдельной копии или рабочем файле, подтвердите красный результат, затем обязательно восстановите код и зелёный запуск. Это ручная оценка качества ваших тестов; общий test runner платформы не засчитывает её автоматически.

## Проверка понимания

1. Почему зелёный тест может ничего не проверять?
2. Что именно подменяет HTTP testing backend?
3. Как доказать, что async-тест дождался результата?
4. Почему тест через submit не всегда проверяет кнопку?

Новая вариация: в fake-сервисе первая отправка падает, вторая успешна. Проверьте восстановление без пересоздания формы.

## Критерии ручной проверки

Три проверки соответствуют разным границам; данные выявляют ошибку; async ожидается; ошибка формы не теряет ввод; контролируемое нарушение делает нужный тест красным; после восстановления все добавленные проверки проходят.
