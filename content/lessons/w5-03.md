# POST: ожидание записи и повторное нажатие

120 минут. Результат: создаётся одна заявка, ввод сохраняется при сбое, успех подтверждается ответом API. Нужны [валидация](/lessons/w5-02), [HTTP-состояния](/lessons/w4-03), [switchMap и отмена](/lessons/w4-04).

## Ситуация и прогноз

Пользователь дважды нажал «Создать», потому что сеть медленная. Можно ли решить это switchMap, отменив первый запрос? Нет гарантии: сервер уже мог создать первую запись. Предскажите число записей, если оба POST дошли до сервера. Отмена ожидания на клиенте не откатывает запись. Политика отправки должна отличаться от поиска.

## DTO и граница команды

Форма содержит controls и их состояния, HTTP принимает простой DTO. Создание заявки отправляет title, description, priority. ID, createdAt и начальный status назначает сервер. Выделение типа CreateIssueRequest помогает не отправить случайно поля из модели чтения. Не делайте `POST(form)`: FormGroup содержит инфраструктуру и ссылки, которые не являются JSON-контрактом.

Нормализуйте значение осознанно: trim названия полезен, если таково правило API; описание может содержать значимые пробелы и переносы, поэтому не обрезайте каждое поле автоматически. Валидатор и отправка должны согласовываться, иначе UI разрешит строку, которую собственный submit затем превратит в пустую.

На время отправки нужен `saving`. Он отражает запрос записи, а не `form.pending`, которое в Angular относится к асинхронным валидаторам. В начале submit проверьте invalid и saving. Затем включите saving синхронно до подписки. Кнопка disabled улучшает обратную связь, guard обработчика обеспечивает понятную защиту от повторного вызова в самом компоненте.

Успех наступает после успешного ответа. Если навигация к детали находится в finalize или сразу после вызова post до subscribe, UI может сообщить о создании после ошибки. Перейти к `/issues/:id` нужно с ID, который вернул сервер, а не с вычисленным на клиенте «следующим номером». Параллельные пользователи делают такие вычисления неверными.

## Разобранная демонстрация

Полный файл: `practice/angular-labs/src/demos/w5-03.ts`. Запуск: `npm.cmd run practice:labs`; страница `http://127.0.0.1:4304/w5-03`. Он уже подключён и запускается без backend. Введите «Анна»: через 600 мс появится `Создан reader-17`. Введите «ошибка»: появится отказ, текст останется в поле. Нейтральная регистрация читателя демонстрирует одну активную отправку.

```ts
import { Component, DestroyRef, inject, signal } from '@angular/core';
import { FormControl, ReactiveFormsModule, Validators } from '@angular/forms';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { finalize, map, timer } from 'rxjs';

@Component({
  selector: 'reader-save-demo', standalone: true, imports: [ReactiveFormsModule],
  template: `
    <label for="reader">Читатель</label>
    <input id="reader" [formControl]="name">
    <button type="button" [disabled]="saving()" (click)="save()">
      {{ saving() ? 'Сохраняем…' : 'Зарегистрировать' }}
    </button>
    <p role="status">{{ message() }}</p>
  `,
})
export class ReaderSaveDemo {
  name = new FormControl('', { nonNullable: true, validators: [Validators.required] });
  saving = signal(false);
  message = signal('');
  private destroyRef = inject(DestroyRef);
  save() {
    if (this.name.invalid || this.saving()) return;
    const submitted = this.name.value;
    this.saving.set(true);
    this.message.set('');
    timer(600).pipe(
      map(() => {
        if (submitted === 'ошибка') throw new Error('Имитация сбоя');
        return { id: 'reader-17', name: submitted };
      }),
      finalize(() => this.saving.set(false)),
      takeUntilDestroyed(this.destroyRef),
    ).subscribe({
      next: reader => this.message.set(`Создан ${reader.id}`),
      error: () => this.message.set('Не сохранено. Ввод оставлен для повторения.'),
    });
  }
}
```

Введите имя и нажмите дважды: индикатор ожидания и guard допускают одну операцию. Введите `ошибка`: через 600 мс появится объяснение, введённое значение сохранится. Исправьте имя и повторите — ошибка должна смениться успехом. Вариация: разрешите редактирование во время запроса, как уже сделано в примере, и измените текст после отправки. Ответ относится к снимку submitted, а не новому тексту. В реальном продукте нужно явно решить, блокировать ли поля или показывать, какие данные сохранились.

## Что делать при неопределённом исходе

Если POST завершился сетевой ошибкой, клиент не всегда знает, успел ли сервер сохранить запись. Автоматический retry может создать дубликат. В промышленном API это решают идемпотентным ключом или проверкой результата по согласованному контракту. Учебный API не обещает такую возможность, поэтому не добавляйте бесконечный retry и не утверждайте, что при любом сбое ничего не создано.

Для учебного задания достаточно предотвратить параллельный повтор внутри страницы, сохранить ввод и явно сообщить о неуспешном подтверждении. После возвращения связи пользователь может проверить список. Это честнее ложной гарантии. Ограничение не требует строительства распределённой транзакции в браузере.

## Мост от Java

POST похож на вызов сервисной команды, но callback не является границей серверной транзакции. Завершение подписки и commit базы — разные события в разных процессах. Блокировка кнопки также не заменяет уникальное ограничение в базе, когда оно нужно предметной области. UI снижает случайные повторы, сервер защищает инварианты.

## Проверка понимания

1. Чем saving отличается от form.pending?
2. Почему switchMap не гарантирует отсутствие дубликата POST?
3. Где должен находиться переход после успеха?
4. Что неизвестно после сетевого сбоя записи?

<a id="criteria"></a>
## Критерии ручной проверки

Payload содержит только поля создания; одна активная отправка; ожидание видно; переход происходит после ответа; ввод не теряется; повтор после исправления возможен; неопределённый сетевой исход не выдается за гарантированный откат.
