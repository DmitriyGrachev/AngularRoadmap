# Очередь записи: порядок, ошибки и граница отмены

180 минут: 35 на политику, 30 на пример, 85 на реализацию и 30 на проверку. Предыдущий шаг — [кэш чтения](/lessons/w9-01). Результат: вы выбираете подходящий оператор по требованию, сериализуете команды и не уничтожаете очередь первым отказом.

## Чтение и запись требуют разных решений

При поиске новый запрос часто делает старый ненужным. Для этого подходит switchMap: он отписывается от предыдущего внутреннего Observable. При сохранении последовательных изменений такое поведение может потерять ожидание результата первой команды, хотя сервер уже принял её. Новый title тогда не обязательно окажется последним сохранённым title. Выбор оператора начинается с вопроса, какие события разрешено отбросить и какой порядок гарантирует продукт.

ConcatMap подписывается на внутренние потоки последовательно: следующая команда ждёт complete предыдущего. MergeMap допускает одновременное выполнение с выбранным concurrency. ExhaustMap игнорирует новые события, пока активен внутренний поток. SwitchMap заменяет предыдущую подписку новой. Ни один из них не является универсальной «защитой от двойного клика». Если повторный клик должен быть проигнорирован — это одна политика; если все команды должны сохраниться в порядке — другая.

В этом уроке каждая команда важна и должна начать выполнение после завершения предыдущей. При успехе выдаётся результат с исходным ID команды. При отказе выдаётся результат ошибки, после чего очередь продолжает работу. Следующий пользовательский ввод не зависит от того, была ли предыдущая команда успешной. Это протокол последовательных независимых команд, а не транзакция «всё или ничего».

Очередь имеет цену. Если пользователь создаёт команды быстрее, чем сервер сохраняет, число ожидающих элементов растёт. ConcatMap не предоставляет автоматически ограниченный backpressure. Для реальной формы может быть лучше явная кнопка, debounce черновика, ограничение очереди либо слияние ещё не отправленных изменений по согласованной политике. Учебное упражнение получает конечный поток и проверяет порядок; оно не обещает безопасную бесконечную очередь автосохранения.

## Ошибка должна остановиться на нужной границе

CatchError снаружи concatMap обрабатывает ошибку всей результирующей цепочки. Если он возвращает один of(errorResult), после него эта замещающая цепочка завершится; последующие команды исходного потока уже не будут обработаны прежней подпиской. Для продолжения очереди ошибку отдельного save превращают в значение внутри обработки команды. Тогда внутренний поток завершается нормальным результатом отказа, и concatMap переходит к следующему.

Учтите синхронный throw. `save(command)` может выбросить исключение до возврата Observable: например, адаптер обнаружил недопустимые аргументы. Если нужно обработать его тем же внутренним catchError, вызов должен происходить в соответствующей Observable-границе. Defer помогает связать создание операции с подпиской и перенести throw в канал error. Это также защищает от раннего старта записи при построении массива операций.

Для Java полезна аналогия с однопоточным исполнителем задач, но не с транзакцией Spring. Ошибка второй команды не откатывает первую, а уничтожение UI не гарантирует отмену серверной операции. Даже в последовательной очереди два разных клиента могут писать одновременно. Optimistic locking и серверная версия решают другую задачу и появятся позже. Сейчас мы гарантируем локальный порядок начала и обработки команд в одной подписке.

## Разобранный пример

Сохраните `serial-demo.mjs` в корне рабочей копии, выполните `node serial-demo.mjs`. Завершением операций управляем вручную, поэтому пример не зависит от скорости компьютера:

```js
import { Subject, Observable, concatMap } from 'rxjs';
const commands = new Subject();
const finish = new Map();
const queue = commands.pipe(concatMap(id => new Observable(observer => {
  console.log('start', id);
  finish.set(id, () => { observer.next(id); observer.complete(); });
}))).subscribe(id => console.log('done', id));
commands.next('A');
commands.next('B');
console.log('queued');
finish.get('A')();
finish.get('B')();
commands.complete();
queue.unsubscribe();
```

Ожидаются `start A`, `queued`, `done A`, `start B`, `done B`. Обратите внимание: next A ещё не запускает B — запуск происходит после complete A. Если внутренний поток выдаст значение и никогда не завершится, очередь остановится на нём. Для HttpClient с обычным ответом завершение естественно; для произвольного Subject это обязанность контракта.

Пример намеренно не обрабатывает ошибки и не реализует упражнение. Добавьте в своём черновике отказ A и объясните, почему B без внутреннего восстановления не начнётся. Затем сравните с оператором, допускающим одновременные подписки: порядок запуска меняется, даже если оба ответа приходят очень быстро. Проверяйте последовательность событий, а не только конечный массив одинаковых значений.

## Практика в IDE — middle-06

В `practice/middle/middle-06/solution.mjs` реализуйте `serializeWrites(commands$, save)`. Он возвращает Observable результатов `{id,ok:true,value}` либо `{id,ok:false,error:'save-failed'}`. Команды выполняются по очереди, ошибка одной не останавливает следующие, синхронный throw save тоже превращается в результат отказа. Отписка от результата прекращает активную подписку и не запускает ожидающие команды. Точные требования к входам находятся в README.

Проверка: `npm.cmd run learn -- check middle-06`. Составьте свой сценарий A успех, B ошибка, C успех, затем сценарий отмены во время A с B в очереди. Отдельно проверьте момент вызова save: для B он не должен происходить до завершения A. Простое создание всех Promise сразу с последующим concat их результатов не сериализует реальные записи.

<details><summary>Подсказка 1 — оператор</summary>Нужно сохранить все команды и порядок. Выберите оператор, который ждёт завершения текущего внутреннего Observable, а не только его первого значения.</details>
<details><summary>Подсказка 2 — локальная ошибка</summary>Преобразование отказа в значение относится к одной команде. После такого значения внутренний поток должен нормально завершиться.</details>
<details><summary>Подсказка 3 — момент вызова</summary>Поместите вызов save в ленивую границу, чтобы синхронное исключение попало в тот же обработчик ошибки, что и error возвращённого потока.</details>

**Новые данные.** Передайте четыре команды с одинаковым entity ID, но разными command ID, чтобы не перепутать корреляцию. Вторая бросает синхронно, третья ошибается асинхронно, четвёртая успешна. Должны появиться четыре результата в порядке команд. Затем отпишитесь до завершения первой: наблюдайте teardown активного fake API и отсутствие вызова save для остальных. Это доказательство отмены клиентской подписки, не rollback базы данных.

## Критерии самопроверки

Обязательны один активный save, правильные ID результатов, продолжение после обоих видов ошибки и cleanup при отписке. Самостоятельный уровень требует объяснить, когда concatMap неправильный выбор для продукта: например, накопление бессмысленных черновиков. Повторить нужно, если решение работает лишь при успехе или называет закрытие страницы гарантированной отменой записи. Для переноса сформулируйте отдельную политику двойного клика и отдельную политику последовательных изменений формы.
