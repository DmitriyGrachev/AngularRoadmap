# Профилирование и виртуальное окно фиксированных строк

180 минут: 35 на измерения, 35 на геометрию, 80 на реализацию и 30 на новый набор данных. Нужны [чувствительные тесты](/lessons/w12-01). Результат — вы различаете дорогую фильтрацию, лишний DOM и сетевую задержку, а диапазон видимых строк вычисляется без пограничных пропусков.

## Начните с наблюдения

«Таблица тормозит» может означать медленный GET, вычисление на каждом вводе, слишком много DOM-узлов, layout или потерю кадров при скролле. Сначала выберите воспроизводимое действие и одинаковый набор данных: например, 10 000 фиксированных строк, ввод трёх букв, затем прокрутка в середину. Запишите build mode, браузер, размеры окна и выбранное CPU/network throttling. Сравнение dev-режима на одном компьютере с production на другом не даёт честного эффекта правки.

Chrome Performance показывает работу главного потока и кадры; Network — запросы и время ответа. Одна длинная операция JavaScript не означает медленный Angular render, а медленный HTTP не исправляется track. Снимите короткую запись вокруг действия, найдите доминирующую работу, сформулируйте одну гипотезу и только затем изменяйте код. После повторите тот же сценарий несколько раз и сравните типичный результат, не единственный лучший. [Chrome Performance](https://developer.chrome.com/docs/devtools/performance).

На frontend сначала проверьте простые причины: повторный expensive sort внутри template, вычисление производного массива при каждом проходе, несколько запросов на одно намерение, отсутствие устойчивой идентичности строк. Computed signals подходят для производного состояния и кешируют вычисление до изменения зависимости; они не делают сортировку 100 000 элементов бесплатной. `track row.id` помогает сохранить соответствие DOM и сущности, но не уменьшает число всех отрисованных строк. [Signals](https://angular.dev/guide/signals), [Angular control flow](https://angular.dev/guide/templates/control-flow).

## Геометрия фиксированной высоты

Виртуализация рисует только часть массива, сохраняя общую высоту прокрутки. Для одинаковой высоты rowHeight положение каждой строки вычисляется арифметически. Диапазон задаётся как `[start,end)`: start включён, end исключён, поэтому `items.slice(start,end)` имеет ту же семантику. Offset сдвигает первый отображаемый элемент на его место в полном списке; totalHeight сохраняет размер scroll area.

Частично видимая строка должна попасть в диапазон. Поэтому левая граница видимости использует floor, правая — ceil. Overscan добавляет строки перед/после окна, чтобы уменьшить заметность пересоздания при прокрутке. Он не является бесконечным запасом: большое значение снова создаёт много DOM. После фильтрации старый scrollTop может оказаться за новым концом списка, поэтому его сначала ограничивают реальным максимумом.

## Разобранный пример

Для count=100, rowHeight=20, scrollTop=45 и viewportHeight=50 видимая область идёт от 45 до 95 пикселей. Строки с индексами 2,3,4 хотя бы частично видны. Overscan=1 расширяет диапазон до 1…5 включительно. Следующий код показывает применение уже рассчитанного результата, а не полный алгоритм упражнения:

```ts
const window = { start: 1, end: 6, offset: 20, totalHeight: 2000 };
const rows = Array.from({ length: 100 }, (_, index) => ({
  id: `row-${index}`, label: `Строка ${index}`,
}));
const visible = rows.slice(window.start, window.end);
console.log(visible.map(row => row.id));
// row-1, row-2, row-3, row-4, row-5
console.log(visible.length); // 5, потому что end не включается
```

Если округлить правую границу вниз, строка 4 исчезнет, хотя её часть видна. Если использовать end включительно и затем slice, появится off-by-one. Если offset вычислить из первого видимого индекса без overscan, отрисованный набор сместится. Нарисуйте координаты 0,20,40,60,80,100 и объясните каждую строку до запуска.

В Java это похоже на вычисление диапазона страницы, но browser window зависит от пикселей и включает частичные строки. Server pagination сокращает объём переданных данных; virtual scrolling сокращает DOM. Это разные задачи и могут использоваться вместе. Если все данные уже скачаны, виртуализация не уменьшает память исходного массива или цену полной фильтрации.

## Ограничения интерфейса

Алгоритм фиксированной высоты неверен, если строки растут из-за переноса текста, раскрытых деталей или ошибок. Нельзя просто указать rowHeight=40, когда фактическая строка занимает 68px: offset начнёт расходиться. Либо обеспечьте фиксированный layout с доступом к полному содержимому, либо используйте измерения и другую стратегию. CDK имеет инструменты виртуального scrolling, но не установлен в учебном проекте; обязательная практика не требует пакетов. [CDK scrolling](https://material.angular.dev/cdk/scrolling/overview).

Виртуализация также влияет на focus, поиск браузером и доступность: удалённый DOM не виден обычному поиску страницы. Не переносите фокус на элемент, который будет немедленно уничтожен. Проверьте клавиатурный переход и выбранную строку при скролле; для важной таблицы разумной альтернативой может быть простая пагинация. Не добавляйте role=grid без реализации обещанного клавиатурного поведения. Математическая проверка окна не доказывает эти свойства UI.

## Практика в IDE — middle-12

В `practice/middle/middle-12/solution.mjs` реализуйте `virtualWindow({count,rowHeight,scrollTop,viewportHeight,overscan})` → `{start,end,offset,totalHeight}`. Count и overscan — неотрицательные safe integers; rowHeight — положительное конечное число; scrollTop и viewportHeight — конечные неотрицательные числа. Неверный параметр вызывает RangeError. Вход не меняется; дробные размеры допустимы.

Сначала вычислите totalHeight=count*rowHeight. В допустимых сценариях произведение конечно. При count=0 либо viewportHeight=0 верните start=end=offset=0 с сохранённым totalHeight. Иначе ограничьте scrollTop максимумом max(0,totalHeight-viewportHeight), вычислите floor/ceil, расширьте overscan и ограничьте границами списка. Запуск: `npm.cmd run learn -- check middle-12`.

После зелёного результата сделайте короткую ручную запись Performance своего текущего списка. Даже если данных мало и ускорение не требуется, запишите, какая работа занимает время и почему вы не добавляете виртуализацию без необходимости. Практика оценки важнее искусственного усложнения маленького экрана.

<details><summary>Подсказка 1 — размер</summary>Валидация выполняется до раннего выхода для пустого списка: плохой rowHeight не становится допустимым из-за count=0.</details>
<details><summary>Подсказка 2 — фильтрация</summary>Clamp scrollTop делается до вычисления индексов, иначе окно после уменьшения count может оказаться пустым.</details>
<details><summary>Подсказка 3 — границы</summary>Проверьте, что end-start равно длине slice, а offset вычислен от окончательного start.</details>

## Новые данные и критерии

Проверьте count=100, rowHeight=20, scrollTop=999999, viewport=50, overscan=1: ожидаются start=96, end=100, offset=1920, totalHeight=2000. Для count=3 и viewport=200 показываются только три строки. Для viewport=0 окно пустое, но общая высота сохраняется. Добавьте дробную высоту 17.5 и отрицательный overscan; последняя ситуация обязана бросить RangeError.

## Критерии самопроверки

middle-12 проходит; частичные строки включены; диапазон не выходит за count; нулевые случаи определены; данные не мутируют. В профиле названо наблюдение, а не предполагаемое ускорение. Самостоятельно объясните, когда выбрать pagination, fixed virtual window или другую стратегию для строк переменной высоты.
