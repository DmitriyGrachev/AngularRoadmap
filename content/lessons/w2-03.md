# TypeScript: договор о форме данных

**Результат:** вы описываете заявку и состояния загрузки так, чтобы редактор находил неверный статус и пропущенную обработку отсутствия. Нужны [объекты](/lessons/w1-04) и [асинхронные состояния](/lessons/w2-02). TypeScript добавляет проверку до запуска, но исполняемые данные всё ещё подчиняются JavaScript.

## Рабочая ситуация и прогноз

После опечатки `OPNE` фильтр молча перестал показывать заявку. Хотелось бы находить такой дефект до браузера. Ещё одна ошибка появляется только при отсутствии id: код обращается к title результата find.

```ts
type Status = 'OPEN' | 'IN_PROGRESS' | 'DONE';
const status: Status = 'OPNE';
```

Что должен сказать проверяющий инструмент? Если удалить type и аннотацию, перестанет ли строка существовать во время выполнения? Предположите, что произойдёт с чтением `issues.find(...).title` при отсутствии совпадения. Нам нужны разные ответы для проверки типов и реального выполнения.

## Вывод типов и аннотации

TypeScript анализирует программу, чтобы проверить совместимость значений и операций. В `const title = 'Письмо'` тип выводится без явной записи. В параметре функции аннотация помогает сообщить ожидаемую форму: `function label(title: string): string`. Двоеточие относится к TypeScript и не является преобразованием значения. Если передать число, проверка пожалуется; она не превратит его автоматически в строку.

Типы `string`, `number`, `boolean` описывают соответствующие примитивы JavaScript. Не используйте обёртки String или Number для обычных полей. Массив `Issue[]` означает последовательность значений формы Issue. Инструмент сможет проверить доступ к полям и результат преобразования. Однако процесс проверки работает с кодом и его предположениями; произвольный вход из сети ещё предстоит проверить во время выполнения.

`interface Issue { id: string; title: string; status: Status; }` задаёт именованную форму объекта. `type` может назвать такую форму, объединение или другой тип. В простых моделях оба варианта описания объекта подходят. Не нужно тратить занятие на выбор «единственно правильного»: выберите понятный стиль и используйте последовательно. Ни интерфейс, ни type не создают экземпляр класса и не добавляют конструктор.

## Union и допустимые значения

Объединение, или union, `A | B` означает одно из допустимых значений. Строковые литералы `'OPEN' | 'DONE'` ограничивают статус конкретными строками. Поэтому OPNE не соответствует контракту. Обычный string был бы слишком широк: он разрешает любые строки. При добавлении нового статуса нужно обновить модель и логику, а не отключать проверку.

Optional-поле `assignee?: string` может отсутствовать. Его чтение даёт string или undefined. Nullable-поле `assignee: string | null` присутствует по контракту, но может содержать явное отсутствие. Это два разных соглашения. Если API обещает null, опишите null; если свойство может быть пропущено, используйте optional. Не заменяйте все варианты произвольной пустой строкой, пока не выбрали смысл.

При строгой проверке null и undefined учитываются отдельно. `find` возвращает Issue или undefined, и доступ к title без проверки небезопасен. Проверка `if (found === undefined)` выделяет ветку отсутствия; в другой ветке инструмент знает, что осталась Issue. Такое уточнение типа по управляющему потоку называется narrowing. Оно опирается на реальные проверки в коде, поэтому помогает и во время выполнения.

Для короткого чтения `found?.title` означает: если found равен null или undefined, результат undefined; иначе прочитать title. Оператор `??` подставляет запасное значение только для null/undefined. В отличие от `||`, он не считает 0 или пустую строку отсутствием. Запись `found?.title ?? 'Не найдено'` полезна для подписи, но не должна скрывать обязательную ошибку, если отсутствие нарушает бизнес-контракт.

## Состояния вместо противоречивых флагов

Три независимых поля loading, error и items могут случайно одновременно сказать «загружается» и «ошибка». Для учебной модели удобно объединение с отличительным полем:

```ts
type LoadState =
  | { kind: 'loading' }
  | { kind: 'ready'; items: Issue[] }
  | { kind: 'error'; message: string };
```

Поле kind выступает признаком варианта. После `if (state.kind === 'ready')` доступны items; message относится к другой ветке. Это не обязательно единственный способ состояния в Angular, но хороший способ увидеть контракт. Пустой список `{kind:'ready', items:[]}` остаётся успехом и не превращается автоматически в ошибку.

## Мост от Java

Модель похожа на договор DTO по составу полей, union — на ограниченный набор допустимых вариантов. Однако TypeScript проверяет форму, а не принадлежность к объявленному Java-классу. Типы стираются перед выполнением. `Issue` не валидирует JSON и не вызывает десериализатор с проверками. Классы TypeScript существуют, но интерфейс модели не является скрытым конструктором. Следующий урок специально показывает эту границу.

## Разобранный пример

В корне выполните `node practice/foundations/async-types/examples/types.ts`. Подготовленная Node 22.23 поддерживает удаление используемых здесь аннотаций; команда не проверяет типы. Ожидаются `Заявок: 1` и `Не найдено`.

Для проверки типов выполните `npx.cmd tsc --noEmit -p practice/foundations/async-types/tsconfig.json`. Конфигурация уже включает strict. На PowerShell можно `npx.cmd`. Измените в своей копии примера OPEN на OPNE: tsc должен сообщить о несовместимости. Простое выполнение через node само по себе такой гарантии не даёт. Верните изменение, чтобы общий пример снова был корректен.

## Практика в IDE

Упражнение `w2-03-ex1`: редактируйте `practice/foundations/async-types/w2-03-ex1/main.ts`. Опишите Status с тремя статусами, Issue с id/title/status и необязательным assignee, а также LoadState. Поменяйте временный unknown параметра describeIssue на Issue и верните понятную подпись. Добавьте список, поиск отсутствующего id и осмысленный вывод без небезопасного доступа.

Запускайте файл командой `node practice/foundations/async-types/w2-03-ex1/main.ts`, типы проверяйте указанной командой tsc. На время проверьте запрещённый статус и восстановите правильный код. Не используйте any, `as Issue` или оператор `!` для подавления проблемы; условия должны объяснять отсутствие. Это ручная проверка, не отчёт runner.

## Критерии

- Итоговый tsc завершается без ошибок в строгом режиме; OPNE при временной проверке обнаруживается.
- find отсутствующего id не падает; причина безопасного доступа объяснена.
- Ветка ready читает items, ветка error — message; пустой ready корректен.
- Вы различаете запуск Node и отдельную проверку типов.

## Проверка понимания

1. Чем string отличается от union конкретных строк?
2. Чем optional отличается от явно nullable-поля?
3. Что останется от interface при выполнении?
4. Почему запуск .ts через Node не заменяет tsc?

Новая вариация: добавьте в LoadState вариант empty, который не содержит items. Найдите места, где теперь нужно обновить логику, и объясните отличие от ready с пустым массивом.
