# bug-01: Поиск умер после первого 503

Связанный урок: [w4-04](../../../content/lessons/w4-04.md). Около 30 минут; упражнение может заменить часть ручной практики урока.

Симптом: запрос «сбой» показывает «Нет сети», а следующий ввод «сеть» ничего не меняет. Запустите node practice/bug-lab/bug-01/repro.mjs: сценарий посылает ошибку и новый текст в тот же Subject. До правки request вызывается только для «сбой». Сначала определите, завершился один HTTP или весь поток ввода; затем исправьте search, сохранив форму состояний.

## Запуск из корня проекта

```powershell
node practice/bug-lab/bug-01/repro.mjs
npm.cmd run learn -- check bug-01
```

Сценарий работает без сайта, dev server и Java API с установленными зависимостями проекта. Исходный дефект намеренно завершает repro с AssertionError и ненулевым кодом. После исправления сценарий завершается успешно. Полная проверка создаёт отчёт версии 1 для учебного сайта.

Редактируйте только `solution.mjs`. `starter.mjs` сохраняет исходную поломку для проверки качества задания и не зависит от вашего решения. Существующее приложение ученика не используется и не переписывается.

## Контракт

search(queries$, request) возвращает Observable состояний. request(query) возвращает Observable массива. Передавайте строку, включая пустую, без изменения.

## Критерии результата

- Следующий текст и пустая строка после ошибки вызывают request.
- Отказ выдаёт { status: "error", message }, успех — { status: "ready", items }.
- Два отказа подряд не завершают внешний поток; пустой успешный результат остаётся ready с [].

## Диагностика

Перед изменением запишите ожидаемое и фактическое поведение, гипотезу причины и эксперимент, различающий две возможные причины. После исправления запустите полную проверку, а не только один repro. Три последовательные подсказки и объяснение находятся в тренажёре; сначала сохраните собственную попытку.

## Новый регрессионный пример

Регрессионная задача: успех → ошибка → ошибка → пустой успех в одной подписке. Проверьте четыре состояния и запишите, почему retry у одного HTTP не заменяет правильную границу catchError.
