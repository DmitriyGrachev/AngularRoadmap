# RxJS-кэш: совместное чтение, инвалидация и время жизни

180 минут: 40 на модель, 25 на разбор, 85 на упражнение и 30 на новые данные. Предыдущий шаг — [архитектура feature](/lessons/w8-workshop). Результат: вы реализуете кэш чтения с явной политикой подписок, ошибок и повторных запросов.

## Одно имя метода не означает один запрос

HttpClient возвращает cold Observable: каждая подписка обычно создаёт собственный HTTP-запрос. Если два компонента независимо вызывают getDetails и подписываются, сервер может получить два чтения. Даже два async pipe над двумя вызовами метода способны создать дублирование. Прежде чем добавлять кэш, подтвердите реальный повтор и определите, какие потребители должны делить один результат. Кэш не исправляет случайное создание нового потока при каждом вычислении шаблона.

Нужно различать совместное выполнение и сохранение результата. Пока запрос выполняется, два потребителя могут ждать один источник. После успеха поздний потребитель может получить сохранённое значение. После изменения данных старое значение должно стать недействительным. После ошибки новый потребитель должен иметь возможность повторить запрос. Это четыре разных правила; слово «кэширование» само по себе не выбирает ни одно.

В RxJS 7.8.2 shareReplay может разделять источник и повторять последнее значение. Конфигурация `bufferSize: 1, refCount: true` прекращает незавершённый источник, когда не остаётся подписчиков. Успешно завершённый источник при этом остаётся сохранённым в соответствующем Observable. Отсутствие подписчиков не равно сбросу уже завершённого результата. Эту деталь легко пропустить, ожидая, что уход со страницы автоматически сделает следующий GET свежим.

Параметр windowTime ограничивает возраст воспроизводимых значений, но сам по себе не проектирует полноценный TTL-кэш с обязательным повторным запросом после истечения срока. Не добавляйте его как магическую «свежесть пять минут» без проверки поздней подписки. Для упражнения используем явную invalidation: вызов сообщает, что будущие чтения данного ключа должны обращаться к новому поколению данных.

## Ключ и поколение защищают корректность

Ключ должен описывать запрос: для списка обычно недостаточно слова issues, если различаются q, page и sort. В упражнении ключ уже передаётся как строка; его нормализация является ответственностью вызывающего. В приложении сначала нормализуйте параметры из URL, затем постройте стабильный ключ. Иначе два эквивалентных фильтра создадут разные записи, а два разных фильтра случайно разделят одну.

Инвалидация в этом контракте забывает запись для будущих read, но не обрывает текущих подписчиков. Представьте: A начал загрузку, ключ инвалидировали, B начал новую загрузку, затем A завершился ошибкой. Cleanup A не должен удалить новую запись B. Перед удалением сверяйте, что карта по-прежнему содержит именно старую запись. Такая проверка принадлежности важнее красивого названия метода; это защита от гонки поколений.

В Java аналогия — cache с загрузчиком и вычислением значения для ключа. Отличие RxJS — подписка владеет временем жизни вычисления, а один Observable может иметь несколько подписчиков. Cache entry не просто готовый объект, а ещё и разделяемая работа. Кэш в root-сервисе также переживает переходы между страницами. Если данные зависят от пользователя или tenant, смена контекста требует очистки либо отдельного ключа; технически успешный replay может быть логически недопустимым.

## Разобранный пример

Сохраните `replay-demo.mjs` в корне рабочей копии, выполните `node replay-demo.mjs`. Зависимости RxJS уже установлены:

```js
import { defer, of, shareReplay, lastValueFrom } from 'rxjs';
let starts = 0;
const raw$ = defer(() => {
  starts += 1;
  return of({ version: starts });
});
const shared$ = raw$.pipe(shareReplay({ bufferSize: 1, refCount: true }));
console.log((await lastValueFrom(shared$)).version);
console.log((await lastValueFrom(shared$)).version);
console.log('starts', starts);
```

Ожидаются 1, 1 и `starts 1`. Поздний подписчик получил завершённый результат. Если заменить shared$ на raw$ в обоих чтениях, ожидаются 1, 2 и `starts 2`. Использован lastValueFrom, который ждёт complete; firstValueFrom отписывается после первого значения и в некоторых потоках меняет наблюдаемый refCount-сценарий. Всегда проверяйте именно тот жизненный цикл, о котором делаете вывод.

Этот пример не содержит ключей и инвалидации. Он показывает только базовый механизм разделения. Добавление `shareReplay` внутри каждого вызова `read(key)` без сохранения созданного Observable в карте не объединит разные вызовы: каждый получит собственную разделяемую, но независимую работу. Аналогично, eager-вызов load до первой подписки нарушит ленивость, даже если сам результат затем обёрнут в Observable.

## Практика в IDE — middle-05

Реализуйте `createReadCache(load)` в `practice/middle/middle-05/solution.mjs`. Возвращаемый объект имеет `read(key): Observable` и `invalidate(key): void`. Полный контракт рядом в README: чтение ленивое, одинаковый ключ делит активную загрузку, завершённый успех воспроизводится, ошибки и отменённые незавершённые загрузки удаляются. Инвалидация влияет на будущие read; существующие подписки продолжают независимо. После отказа возможна новая попытка.

Команда: `npm.cmd run learn -- check middle-05`. Перед кодом нарисуйте timeline двух подписчиков и одной записи карты. Отметьте subscribe, unsubscribe, next, error, complete и invalidate разными событиями. Затем добавьте второй ключ. Если для объяснения приходится предполагать, что все HTTP-ответы приходят в порядке запуска, модель недостаточна. Используйте управляемые источники при собственной проверке.

<details><summary>Подсказка 1 — разделяемый объект</summary>Карта должна хранить запись, которую найдут разные read одного ключа. Сам load должен запускаться подпиской, а не чтением имени метода.</details>
<details><summary>Подсказка 2 — окончание</summary>Различайте успешное complete и teardown незавершённого источника. finalize выполняется в обоих случаях и не означает только ошибку.</details>
<details><summary>Подсказка 3 — поколение</summary>Старый cleanup удаляет запись лишь если она всё ещё принадлежит этому поколению. После invalidate новая запись может уже занимать тот же ключ.</details>

**Новые данные.** Подпишитесь A и B на один ключ, отпишите A, убедитесь, что источник жив для B; затем отпишите B до ответа. Новое чтение должно запустить источник заново. Во втором сценарии дождитесь успешного complete и повторите чтение: нового запуска нет. В третьем инвалидируйте активный ключ, создайте новый запрос, завершите старый ошибкой и проверьте, что новый остаётся в кэше.

<a id="criteria"></a>
## Критерии самопроверки

Нужны доказательства ленивости, одного активного источника, повторного чтения после отказа и отсутствия удаления нового поколения старым cleanup. Самостоятельная защита объясняет разницу refCount, завершённого replay и invalidation, а также границы хранения. Зелёный runner не доказывает свежесть всех продуктовых данных: отдельно назовите, какие ключи надо инвалидировать после изменения одной заявки и почему деталь и отфильтрованный список могут требовать разных действий.
