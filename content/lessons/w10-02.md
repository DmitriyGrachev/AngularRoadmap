# Ошибка сервера принадлежит строке и редакции

180 минут: 40 на временную модель, 35 на пример, 75 на практику и 30 на новые случаи. Нужны [вложенные формы](/lessons/w10-01). Результат — ошибка задержанного ответа не оказывается у другой строки и не отменяет исправления пользователя.

## Почему индекс недостаточен

На отправке rows[0] содержит «Анализ», rows[1] — «Проверка». Пока сервер отвечает, пользователь удаляет первую строку. Сообщение `rows[1].label` теперь либо некуда приложить, либо оно относится к совсем другому элементу после добавления. Индекс описывает снимок порядка, но не идентичность строки. Стабильный client ID нужен уже до первого сохранения, когда серверного ID ещё нет.

Вторая проблема не решается одним ID. Пользователь мог исправить label у той же строки. Ответ валидирует отправленный текст, а не новое значение. Поэтому сохраняют снимок отправки и revision. Локальная revision увеличивается по принятой политике изменений draft; response содержит редакцию, к которой относится. В этом упражнении действует консервативная политика: response.revision, snapshot.revision и currentRevision обязаны совпадать. Затем дополнительно сравнивается текущий label со снимком. Структурная перестановка допустима, если приложение не меняет смысл/редакцию данных; если ваша политика увеличила revision, ответ целиком устарел.

Это не server version и не optimistic locking: локальная revision защищает отображение ошибок внутри клиента. Серверная version защищает сохранённую запись от конкурирующих клиентов. Один счётчик для обеих задач создаёт ложное ощущение безопасности: совпадение локального номера ничего не сообщает о чужой записи в базе.

## Разобранная последовательность

Нейтральный пример показывает только поиск кандидата, не готовое решение применения errors:

```ts
const snapshot = {
  revision: 6,
  rows: [{ id: 'r-a', label: 'Анализ' }, { id: 'r-b', label: 'Ошибка' }],
};
const current = [
  { id: 'r-b', label: 'Исправлено' },
  { id: 'r-a', label: 'Анализ' },
];
const incoming = { id: 'r-b', field: 'label', message: 'Недопустимо' };
const sent = snapshot.rows.find(row => row.id === incoming.id);
const now = current.find(row => row.id === incoming.id);
console.log(sent?.label === now?.label); // false: этот текст уже не проверялся
console.log(current[1].id);             // r-a: старый индекс опасен
```

Ожидается отсутствие field error у обеих строк: r-a не является адресатом, r-b уже изменена. При одинаковом label и актуальной редакции сообщение можно приложить к r-b независимо от её индекса. Если строка удалена, не создавайте её заново из ответа. Общая подсказка о старом отказе может остаться на уровне отправки, но не должна делать новое поле invalid без основания.

Снимок обязан содержать значения, а не ссылки на живые объекты. Иначе изменение label одновременно поменяет «отправленный» label и проверка равенства всегда пройдёт. В Java это похоже на неизменяемую команду и сопоставление результата с её correlation ID. Отличие — пользователь меняет интерфейс ещё до завершения команды; контрол с тем же DOM-положением может уже представлять другую сущность.

## Как не стереть клиентскую валидацию

`control.setErrors({server: message})` заменяет весь error map. Если у поля уже есть required или minlength, такая запись их потеряет до следующей валидации. При добавлении server сохраняйте существующие ключи; при очистке удаляйте только server. Но не храните в error map всё состояние запроса: saving, requestId и общая ошибка принадлежат модели отправки.

В Angular вручную выставленные errors могут быть заменены следующим запуском валидаторов. Поэтому приложение должно явно определить, когда server error устаревает: обычно после изменения данного поля либо новой отправки, а не после любого blur. Не обещайте, что setErrors навсегда «добавил серверный валидатор». Для долговременной модели можно хранить внешние ошибки отдельно и объединять представление; в текущем упражнении проверяется одно применение ответа. [AbstractControl.setErrors](https://angular.dev/api/forms/AbstractControl).

При обработке ответа разрешайте только известные имена полей. Путь, присланный сервером, не является командой выполнить произвольное property access. Неизвестный field, неизвестный ID и пустое сообщение игнорируются согласно контракту, а malformed payload должен быть распознан на границе transport. Текст отображается как текст, не через innerHTML. Не переносите необработанный stack trace на страницу.

## Практика в IDE — middle-08

В `practice/middle/middle-08/solution.mjs` реализуйте `applyRowErrors(rowsFormArray, response, snapshot, currentRevision)`, возвращающую число приложенных сообщений. Здесь rowsFormArray — настоящий Angular FormArray групп с id и label. Response имеет `{revision, errors:[{id, field:'label', message}]}`, snapshot — `{revision, rows:[{id,label}]}`.

Применяйте только ответ с тремя совпадающими редакциями, существующей строкой из снимка и текущей формы, неизменённым label, известным field и непустым message. Найдите контрол по стабильному id; добавьте `server` к существующим errors без изменения value. Точные граничные случаи описаны README. Запустите `npm.cmd run learn -- check middle-08`. Готовый алгоритм не обновляет revision за приложение и не выполняет HTTP.

Затем набросайте на бумаге место вызова в компоненте: кто создаёт snapshot, кто увеличивает revision, кто хранит active request, кто решает состояние общей ошибки. Если невозможно назвать владельца, правильная чистая функция не спасёт интеграцию от ошибочного параметра currentRevision.

## Проверка на новых данных

Отправьте revision 12 со строкой k-91/«Ошибка». До ответа переставьте её; ожидайте прежний адресат при актуальной revision. Затем измените label и ожидайте игнорирование. Удалите строку, добавьте новую с другим ID и тем же текстом — сообщение не переносится. Повторите с response revision 11, неизвестным field и message из пробелов. Для строки с локальной required подтвердите, что добавление server не удалило required и не изменило value.

## Критерии самопроверки

Проверка middle-08 проходит; число приложенных ошибок соответствует изменениям; stale ответ не имеет побочных эффектов; перестановка не путает строки; локальные ошибки и значения сохранены. Самостоятельно объясните более точную политику field revision, её пользу и цену относительно консервативного global revision.
