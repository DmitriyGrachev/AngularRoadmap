# Практикум: редактор динамических строк без потери ввода

360 минут: 35 на контракт, 150 на реализацию, 90 на сценарии, 45 на исправления и 40 на объяснение. Нужен [собственный контрол](/lessons/w10-03). За неделю получается 15 обязательных часов; оставшиеся 0–5 часов используйте для повторения, а не для расширения объёма задачи.

## Конкретное требование

Добавьте редактор «План решения» у одной заявки. План содержит `title` и от одной до восьми строк `{ clientId, description, estimateHours }`. Описание после trim занимает 3–160 символов; оценка — целое число 1–40; сумма оценок не больше 80. `clientId` создаётся один раз при добавлении строки, сохраняется при перестановке и не определяется индексом. Удаление последней строки запрещено с понятным объяснением. После удаления фокус получает следующая строка или кнопка добавления.

Пользователь может менять строки во время ожидания проверки. Успех подтверждает отправленную редакцию; более новый ввод остаётся на экране и помечается как несохранённый. Ошибка старой редакции не приклеивается к новому тексту. Перестановка не переносит сообщение на чужую строку. После отказа ввод, порядок и доступные действия сохраняются. На экране есть статус ожидания, общая ошибка и ошибки полей; одного красного цвета недостаточно.

## Подготовленная база и граница задания

Возьмите текущий трекер `practice/issue-tracker` или работающий `practice/workplace`; перед изменением сохраните свою точку восстановления. В обоих baseline поля плана отсутствуют. Создать модель, форму и отдельный локальный adapter проверки плана — ваша работа. Adapter должен возвращать управляемый Observable, позволяющий тесту вручную завершить запрос. Нельзя считать обычный таймер доказательством устойчивого хранения. Здесь не нужны новые пакеты, новый backend или изменения PL-исходников.

Используйте два фиксированных ответа: для description `blocked` — ошибка строки, для суммы больше 80 — ошибка всего плана. Имитация отказа доступна через отдельную учебную кнопку «Следующая проверка: отказ». Не привязывайте дефект к случайной вероятности: сценарий должен повторяться. Эти контракты вы реализуете в adapter; исходный Java API их не поддерживает. Реальное сохранение и серверная версия появятся в [следующем интеграционном практикуме](/lessons/w11-workshop).

## Механизм: редакция и идентичность

У формы есть текущая редакция; у отправки — снимок значений и их редакций. Глобальный номер помогает понять, изменился ли весь документ, но для ошибок строки полезно отдельно знать, изменилось ли конкретное поле. Стабильный ID отвечает на вопрос «какая строка», редакция — «какое её значение». Номер серверной версии из следующей недели решает другую задачу: конфликт между клиентами.

Разберите последовательность на нейтральном примере, прежде чем создавать UI:

```ts
const sent = {
  requestId: 'check-1',
  rows: [{ clientId: 'r-8', description: 'blocked', revision: 2 }],
};
const current = [
  { clientId: 'r-9', description: 'Документация', revision: 1 },
  { clientId: 'r-8', description: 'Исправлено', revision: 3 },
];
const error = { clientId: 'r-8', field: 'description', message: 'Недоступный шаг' };
const before = sent.rows.find(row => row.clientId === error.clientId);
const now = current.find(row => row.clientId === error.clientId);
console.log(before?.revision === now?.revision); // false: ошибка устарела
```

Ожидается, что ошибку нельзя показать у `r-9`, хотя она теперь занимает старый индекс, и нельзя показать у исправленной `r-8`. Это не означает скрыть отказ целиком: статус «Предыдущая редакция не прошла проверку; проверьте текущую» объясняет результат без обвинения нового поля. Сравнение только текста не замечает сценарий «A → B → A», поэтому выберите и обоснуйте revision-политику.

В Java это похоже на сопоставление команды с агрегатом по ID и версии. Но форма не является серверной транзакцией: пока запрос идёт, пользователь продолжает редактировать. Полный reset успешным DTO может разрушить новые изменения. Избежать этого можно осознанным запретом редактирования во время записи либо аккуратным подтверждением снимка; здесь требование явно выбирает второй вариант.

## Самостоятельная реализация

Сначала опишите инварианты и четыре состояния экрана в `practice/middle/w10-workshop-ex1/notes.md`. Затем реализуйте typed FormArray, отдельную функцию построения DTO, cross-field validator суммы и отображение ошибок по ID. Для строк используйте `track` по стабильному ID. Добавление/удаление через API FormArray сохраняет согласованность контролов; не подменяйте его внутренний массив напрямую.

Подключите один собственный control из предыдущего урока или небольшой новый control оценки. После неудачной отправки покажите сводку ошибок, с которой можно перейти к полю. Фокус перемещайте после появления элемента в DOM; не ищите его по давно сохранённому индексу. Поле, скрытое или удалённое к моменту ответа, не получает фокус.

Запустите выбранное приложение штатной командой. Добавьте тесты лишь для существенных переходов: устаревшая ошибка, перестановка, изменённый во время ответа ввод, сумма и управление disabled. Ручная клавиатурная проверка остаётся отдельным свидетельством: чистая функция не видит фокус браузера.

## Проверка на новых данных

Введите строки `a-17: Анализ / 40`, `b-24: Проверка / 40`, `c-31: Запись / 1`: ожидается ошибка суммы. Удалите `c-31` — сумма 80 допустима. Отправьте `b-24=blocked`, затем переставьте строки и измените его на «Проверка ролей» до ответа. Старое сообщение не должно появиться ни у одной строки. Повторите с удалением `b-24`, затем с новым `d-45`, содержащим тот же текст. Это другая строка.

## Критерии ручной проверки

Проверены все границы чисел и длины; строка сохраняет ID при перестановке; старый ответ не теряет новый ввод; ошибки различают поля и документ; клавиатура достигает добавления, удаления и сводки. Notes содержат прогноз, фактический результат, одну найденную ошибку и её исправление. Без подсказок объясните замену global revision на field revision и влияние этого решения. Зелёный middle-08 подтверждает алгоритм, но не завершение этого UI-практикума.
