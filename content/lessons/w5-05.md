# Редактирование: начальные данные и PATCH

120 минут. Результат: существующая заявка загружается в форму, название и статус сохраняются частичным запросом. Нужны [модель формы](/lessons/w5-01), [POST](/lessons/w5-03), [ошибки сервера](/lessons/w5-04).

## Ситуация и прогноз

Форма открылась, пользователь начал печатать, затем пришли начальные данные и затёрли его текст. Кто владеет значением на этой стадии? Предскажите, как избежать конфликта: не разрешать редактирование до завершения первоначальной загрузки либо защищать уже начатый ввод. Удобнее сначала загрузить запись, затем показать готовую форму, а отдельное loading не путать с saving.

## Чтение и изменение — разные шаги

Редактирование начинается с ID маршрута и GET детали. Только успешный ответ заполняет controls. Пока запись загружается, пользователь видит ожидание, при 404 — отсутствие, при другом сбое — повтор. Не показывайте пустую форму как будто это новая заявка, если на самом деле существующая не загрузилась.

`setValue` подходит, когда передаёте все controls группы. `patchValue` удобен для части данных, но может скрыть несовпадение структуры: неизвестное имя не заполнит ожидаемое поле. Не применяйте весь Issue слепо к форме. Создайте небольшой объект с нужными полями, чтобы граница чтения была видимой и типизированной.

Начальное заполнение не должно притворяться пользовательской правкой. После успешной загрузки форма обычно pristine и untouched. Если вы заполняете повторно после явного действия «Отменить изменения», reset с данными возвращает и значения, и состояние взаимодействия. Простое patchValue меняет значения, но не является универсальной командой сброса истории.

PATCH по учебному контракту принимает изменяемые title, status и priority. В этом уроке обязательны title и status; priority подключите самостоятельно в практикуме. Отсутствующее поле означает «не менять». Пустая строка означает переданное пустое значение и может нарушить правило title. JSON не включает undefined в обычном объекте, но полагаться на случайную сериализацию вместо явного DTO не стоит.

Отправлять все допустимые поля или только изменённые — зависит от контракта и требования. Для маленькой учебной формы допустим DTO с title/status. Если строите частичный DTO по dirty, помните: dirty не означает отличие от исходного значения. Для точного набора изменений сравнивайте с исходным снимком. Не усложняйте сравнение вложенных структур, которых здесь нет.

## Разобранная демонстрация

Полный файл: `practice/angular-labs/scripts/w5-05.ts`. Команда из корня `node practice/angular-labs/scripts/w5-05.ts` выводит `true` с заполненной формой, затем `{ title: 'Компьютерные сети' }`. Файл включает необходимый import `@angular/compiler` для инициализации forms в Node; Java API и браузер не нужны. Нейтральный пример книги показывает отличие начального reset и PATCH-объекта.

```ts
import { FormControl, FormGroup, Validators } from '@angular/forms';

type Book = { id: string; title: string; available: boolean };
type BookPatch = Partial<Pick<Book, 'title' | 'available'>>;
const book: Book = { id: 'b8', title: 'Сети', available: true };
const form = new FormGroup({
  title: new FormControl('', { nonNullable: true, validators: [Validators.required] }),
  available: new FormControl(false, { nonNullable: true }),
});
form.reset({ title: book.title, available: book.available });
console.log(form.pristine, form.getRawValue());
form.controls.title.setValue('Компьютерные сети');
const value = form.getRawValue();
const patch: BookPatch = {};
if (value.title !== book.title) patch.title = value.title;
if (value.available !== book.available) patch.available = value.available;
console.log(patch); // { title: 'Компьютерные сети' }
```

Сначала pristine равно true, хотя значения уже заполнены. Затем PATCH содержит только изменившееся название. Программный setValue сам по себе не доказывает пользовательский dirty. Вариация: верните прежнее название. Объект patch станет пустым; решите, должна ли кнопка сохранить сообщать «Изменений нет» или вообще не отправлять запрос. Это решение относится к UX, а не к магии Reactive Forms.

## После успешного PATCH

Ответ сервера считайте авторитетным сохранённым представлением: он может нормализовать title. Обновите видимую деталь/список из ответа либо выполните согласованную повторную загрузку. Если перейти назад к закэшированному локальному объекту, легко показать устаревший статус при успешной записи.

Обычный PATCH не решает одновременное редактирование двумя людьми. Для промышленного конфликта часто используют version или ETag/If-Match, но учебный контракт их не содержит. Не обещайте защиту от потерянного обновления. На этой стадии достаточно корректной одиночной формы и честного понимания границы.

## Мост от Java

`Partial<...>` существует во время TypeScript-проверки и не создаёт Java patch DTO. На backend отсутствующее поле и null могут требовать специальной обработки. Соблюдайте данный контракт, не переносите модель JPA entity напрямую в браузер. Дата создания и ID относятся к серверному представлению и не должны случайно отправляться как редактируемые поля.

## Проверка понимания

1. Чем отсутствие поля PATCH отличается от пустой строки?
2. Почему dirty не является точным сравнением с исходником?
3. Когда initial GET может затереть ввод?
4. Что не решает обычный PATCH без версии?

Новая вариация: откройте неизвестный ID редактирования и покажите отсутствие записи без пустой «новой» формы.

## Критерии ручной проверки

Начальные данные загружаются по ID; controls заполнены явно; PATCH соответствует контракту; ошибки сохраняют ввод; повторное чтение подтверждает запись; проверки формы ловят invalid submit; отсутствие записи обработано.
