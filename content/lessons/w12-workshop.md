# Итоговая работа: новая функция, инцидент и защита решения

360 минут: 35 на требования, 150 на самостоятельную реализацию, 75 на инцидент, 60 на проверки и 40 на защиту. Нужна [доставка изменения](/lessons/w12-03). Подготовленные артефакты недель 10–11 входят в оценку; строить весь backend заново за шесть часов не требуется.

## Новая функция без пошагового решения

В редакторе плана добавьте «Архивировать план» и возможность открыть архивный план только для чтения. Расширьте модель полем `archivedAt: string | null`. Архивировать может owner с EDITOR либо ADMIN; обычное редактирование архивного плана запрещено всем. Повторная команда архивирования уже архивного плана с актуальной version возвращает текущий DTO без дополнительного увеличения version. Stale expectedVersion даёт 409. Дата создаётся сервером. Frontend показывает статус, блокирует ввод, сохраняет навигацию и объясняет отказ.

Задание выполняется на настоящем Java API из недели 11. Если вы ранее работали только с workplace mock, сначала завершите интеграционный практикум; mock можно использовать для быстрых UI-тестов, но он не заменяет итоговое доказательство. API-маршрут команды выберите сами и зафиксируйте его метод, body, статусы и поведение повторов до реализации. Выбор между отдельной командой и расширением PUT нужно защитить с учётом версии и старого клиента.

В UI подтверждение содержит название плана и понятные действия. После отмены ничего не отправляется. При 403/409 форма не сообщает об успехе и не теряет существующий draft. Если план архивирован в другой вкладке, первая вкладка после конфликта получает серверное состояние и предлагает сохранить локальный текст вне действия записи по явно выбранной политике. Не удаляйте его молча.

## Механизм и нейтральный пример

Функция проходит четыре границы: пользовательское намерение → клиентская команда → серверное правило → подтверждённое состояние экрана. Disabled UI уменьшает ошибки пользователя, но окончательное правило принадлежит серверу. Version помогает различить повтор уже выполненного намерения и попытку применить решение к устаревшим данным.

Нейтральный пример показывает, как проверять контракт независимо от внутренней реализации. Это не готовый endpoint:

```text
Given: draft id=P-72, owner=anna, version=9, archivedAt=null
When:  anna архивирует с expectedVersion=9
Then:  200, version=10, archivedAt заполнен сервером

When:  anna повторяет с expectedVersion=10
Then:  200, version=10, та же archivedAt

When:  старая вкладка редактирует с expectedVersion=9
Then:  409, запись version=10 не изменена

When:  admin пытается редактировать архив с expectedVersion=10
Then:  отказ по доменному правилу, содержимое не изменено
```

Для последнего отказа выберите 409 либо отдельный согласованный domain error и объясните отличие от 403. Ожидаемое поведение должно быть одинаково понятным во frontend и Java-тестах. Java-аналогия — команда над агрегатом с предусловиями; frontend добавляет ещё одну незавершённую реальность: draft, который не обязан совпадать с сохранённым DTO.

## Обязательный инцидент

В безопасной локальной копии воспроизведите: пользователь открывает подтверждение для P-72, переключает маршрут на P-73, затем завершает старый запрос. Дефектная реализация показывает «P-73 архивирован», хотя сервер изменил P-72. Можно внедрить дефект намеренно, если ваша версия уже корректна. До исправления зафиксируйте IDs команды, ответа и текущего маршрута. Затем добавьте регрессионный тест и устраните неверное применение результата.

Не исправляйте это глобальным reload или запретом всех переходов. Обоснуйте область состояния, привязку результата к entity ID и политику ухода во время операции. Отмена подписки не гарантирует, что сервер отменит запись. Для локального mock эта гарантия ещё слабее: таймер и commit не воспроизводят реальный сетевой разрыв.

## Проверка переноса на новое требование

После первой реализации добавьте правило: архивировать план с суммой оценок больше 40 может только ADMIN. Данные для независимой проверки: P-72 с суммой 40, P-73 с суммой 41, P-74 уже архивирован и имеет version 12. Проверяйте anna и admin, прямую HTTP-команду и UI, повтор с актуальной и устаревшей версией. Это расширение отличается от правила сохранения недели 11: оно относится именно к архивированию и не должно случайно запретить разрешённое чтение.

В `practice/middle/w12-workshop-ex1/notes.md` соберите четыре свидетельства: работающая frontend-функция, настоящий Java-контракт, исправленный инцидент и ответы защиты. Приложите команды проверок и краткие фактические результаты, не cookie/token и не снимок целого private-проекта. Запишите, где использовали подсказки, документацию и помощь. Это помогает оценить самостоятельность, а не уменьшает ценность честной попытки.

## Итоговая рубрика компетентности

Каждый пункт получает 0–3: 0 — нет работающего свидетельства; 1 — выполнено с пошаговой помощью, объяснение неполное; 2 — выполнено самостоятельно по требованиям, проверены границы; 3 — самостоятельно перенесено на новое условие, объяснены альтернативы и ограничения. Документация разрешена на любом уровне; копирование без понимания не равно самостоятельности.

| Область | Что нужно предъявить |
| --- | --- |
| Frontend-функция | Согласованные form/store/router, понятные loading/error/readonly, клавиатурный маршрут |
| Интеграция Java | Настоящие HTTP-запросы, DTO и ошибки, version, сохранение и последующее чтение |
| Корректность записи | Stale-команда не затирает запись; повтор соответствует контракту; ответ не применяется к чужому ID |
| Безопасность | Авторизация объекта на сервере; отклонение unsafe-запроса без CSRF; отсутствие опасного HTML/утечек |
| Тесты и инцидент | Воспроизведение, различающая гипотеза, чувствительный тест, исправление и повтор |
| Самостоятельность и перенос | Собственный план, новое правило 40/41, объяснение компромиссов и политики совместимости |

Ориентир готовности этого учебного этапа — не меньше 2 по каждой области, минимум 15 из 18 и выполненные жёсткие условия ниже. Это критерий курса, не гарантия должности Middle или трудоустройства. Если одна область равна 1, повторите соответствующий практикум на другом требовании; сумма баллов не скрывает пробел.

**Жёсткие условия:** чужой пользователь не меняет ресурс прямым запросом; CSRF проверяется реальным сервером; stale version не уничтожает чужую запись; failure не стирает draft; результат не применяется к другому entity ID. Любой провал означает «ещё не готово», даже при высоком балле интерфейса.

На устной защите за 10–15 минут объясните путь одного запроса, границы Signals/RxJS, отличие local revision от server version, выбор оператора записи, повтор после потерянного ответа и один тест, который раньше был красным. Затем без запуска предскажите сценарий 40 → 41 и старой вкладки. Хорошая защита различает факт, предположение и ещё не проверенное ограничение.
