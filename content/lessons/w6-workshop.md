# Итоговый практикум: сброс фильтров и объяснение решения

300 минут: 120 на самостоятельное действие, 60 на диагностику старой страницы, 60 на критические сценарии и 60 на показ проекта. Нужны [самостоятельный фильтр](/lessons/w6-04), [завершение изменения](/lessons/w6-05) и весь основной маршрут курса.

## Требование

Добавьте действие «Сбросить фильтры». Оно очищает q, status и priority, возвращает page=0, обновляет URL и загружает соответствующий список. После обновления вкладки и навигации назад интерфейс должен следовать URL. Размер страницы сохраняйте, если он не является частью фильтров по вашей явно записанной политике.

Это самостоятельная задача: последовательность правок не даётся. До кода сформулируйте критерии и предскажите полный результат для URL со всеми тремя фильтрами и page=3. Какие параметры исчезнут, какие останутся, сколько актуальных GET требуется? Объясните, почему три отдельных последовательных navigate могут создать лишние промежуточные запросы.

## Механизм задачи

Сброс — один переход состояния списка. Если URL является источником, одно согласованное изменение URL должно привести к одному актуальному чтению. Ручное очищение трёх DOM-полей недостаточно: Router и сервис могут продолжить использовать прежние значения. Аналогично, очистка локальных signals без изменения URL не переживёт перезагрузку.

После любого изменения фильтра дальняя page больше не обязана существовать. Дефект «остаётся старая страница» часто выглядит как пустой результат, хотя API работает верно. Найдите, где переход состояния обязан сбросить страницу, и проверьте значение до HTTP. Ложное исправление «если items пустой, показать старый список» скроет противоречие и покажет пользователю данные другого запроса.

Сходство с Java-командой — атомарное выражение намерения на уровне модели. Но здесь нет серверной транзакции UI: несколько присваиваний и навигаций могут породить отдельные наблюдаемые состояния. Поэтому проверяйте итоговый запрос и историю браузера, а не только визуально очищенные select.

## Нейтральная демонстрация

Полный файл: `practice/angular-labs/scripts/w6-workshop.ts`. Выполните из корня `node practice/angular-labs/scripts/w6-workshop.ts`. Ожидаются пустой q, category null, page 0 и size 10. Браузер и Java API не нужны. Независимый каталог помогает выразить сохранённые настройки отдельно от очищаемых условий, не подставляя готовый код маршрутизации трекера.

```ts
type Catalog = { q: string; category: string | null; page: number; size: number };
const current: Catalog = { q: 'сети', category: 'technical', page: 3, size: 10 };
const reset: Catalog = { q: '', category: null, page: 0, size: current.size };
console.log(reset); // q пустой, category null, page 0, size 10
```

Вариация: size меняется пользователем до сброса. Подтвердите, что команда сохраняет выбранную политику. Пример не решает сериализацию null в URL: ваша реализация должна удалить фильтр, а не передать строку `null` серверу.

## Практика в IDE — w6-workshop-ex1

Рабочие файлы — `practice/issue-tracker/src/app/{app.ts,models.ts,issue.service.ts,issues-list.ts,issue-detail.ts,issue-form.ts}` и связанные spec; редактируйте только нужные. Запустите `npm.cmd run practice:api` и `npm.cmd run practice:angular`, тесты — `npm.cmd run practice:test -- --watch=false`.

Реализуйте сброс по собственному плану. Затем диагностируйте дефект старого page в текущей реализации или отдельной временной копии: дойдите до дальней страницы, смените фильтр, сравните URL и HTTP. Запишите гипотезу до правки. Верните корректное поведение и подтвердите исходный сценарий плюс другой фильтр.

Пройдите критический маршрут проекта: прямой список с фильтрами; детали по известному и неизвестному ID; пустой поиск; сбой чтения и повтор; создание; редактирование; серверная ошибка поля; сброс всех условий; Back/Forward; управление клавиатурой. Не требуется огромный тестовый отчёт: у каждого пункта достаточно действия и наблюдаемого результата. Если сценарий нельзя выполнить, честно отметьте причину и вернитесь к соответствующему уроку.

**Проверка на новых данных.** Откройте `practice/issue-tracker/scenarios/final-cases.json`: это входные данные, не готовое решение. В чистой учебной сессии API исходный `total=32`; через свою форму создайте ровно один раз две указанные заявки «Контроль-А» и «Контроль-Б», не меняя их начальный OPEN. В Network проверьте URL запроса `/api/issues` и поле total: `q=Контроль-` даёт 2, дополнительно `priority=HIGH` — 1, вместо приоритета `status=DONE` — 0. После «Сбросить фильтры» должны исчезнуть q/status/priority, установиться page=0 и вернуться `total=34`: все 32+2 заявки сохранены, хотя items содержит только страницу. Если API уже использовалось, сначала запишите свой исходный total B, убедитесь, что поиск `Контроль-` ещё пуст, и ожидайте B+2 вместо 34; чужие тестовые записи не считаются дефектом фильтра. Отдельный пример неизвестного priority в файле проверяет нормализацию URL на клиенте; это не допустимый вход API. Самостоятельно объясните каждый результат, затем проверьте Back и обновление вкладки.

Для защиты результата покажите проект и ответьте без указания строки преподавателем: где URL превращается в параметры API, где форма строит DTO, что отменяет switchMap, почему нельзя считать отменённый POST откатанным, как тест ловит ваш исправленный дефект. Официальная документация разрешена; самостоятельность означает принятие и объяснение решения.

## Итоговая проверка понимания

1. Как доказать, что сброс изменил запрос, а не только поля?
2. Где возник дефект page и почему API не виноват?
3. Что проверено автоматически, а что вручную?
4. Какую слабую тему нужно повторить на другой задаче?

Новая вариация: после сброса нажмите Back. Объясните, какое состояние должно восстановиться, и подтвердите его без перезапуска приложения.

## Критерии итоговой ручной проверки

Оцените выполнение требования, ошибки/пустые данные, восстановление URL, полезную проверку и объяснение решения. Каждый пункт — «самостоятельно», «с подсказкой» или «нужна повторная попытка». Для завершения нужно самостоятельно выполнить небольшое изменение и объяснить его. Чтение всех страниц и зелёный runner платформы не заменяют это условие. Слабый пункт получает конкретную повторную вариацию, а не формальный общий процент.
