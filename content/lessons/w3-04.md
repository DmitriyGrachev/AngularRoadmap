# Сервис, DI и время жизни компонента

120 минут. Результат: общие данные имеют явного владельца, а ресурсы освобождаются вместе с представлением. Нужны [signals](/lessons/w3-03).

## Ситуация и прогноз

Список и детали создают `new IssueService()` каждый для себя. В деталях статус изменился, но список продолжает показывать старое значение. Предскажите причину до чтения: созданы разные объекты, каждый со своим состоянием. Одинаковое имя класса не означает один экземпляр.

## Зависимость получает окружение

Dependency injection, или DI, — механизм предоставления зависимостей. Компонент сообщает, какой сервис нужен, через `inject(IssueService)` либо параметр конструктора. Injector ищет provider по токену и возвращает соответствующий экземпляр. В простом случае токеном является сам класс. Создание сервиса вручную обходит эту систему, включая зависимости его конструктора.

`@Injectable({ providedIn: 'root' })` регистрирует сервис в корневом окружении приложения. В пределах одного запущенного приложения компоненты, разрешающие этот токен из root, получают общий экземпляр. Это не вечный singleton на компьютере и не общий объект между вкладками. Перезагрузка страницы запускает приложение заново. Если добавить тот же сервис в `providers` компонента, его дочерняя ветвь получит локальную версию, которая может скрыть корневую.

Сервис нужен для общей операции или состояния: загрузить записи, найти запись, применить изменение. Он не обязан хранить любой временный флаг интерфейса. Открыта ли подсказка одной карточки — обычно дело карточки. Какой статус сохранён у заявки — общая предметная информация. Разделение уменьшает число мест, где приходится искать изменение.

Поле с `inject` и constructor выполняются при создании экземпляра. Это подходящее место для получения зависимостей, но входы компонента ещё не гарантированно инициализированы. `ngOnInit` вызывается один раз после первоначальной установки inputs. `ngOnChanges` сообщает об изменениях inputs; для signal inputs нередко достаточно computed. `ngOnDestroy` вызывается перед уничтожением. Скрытие через CSS не уничтожает компонент, а удаление ветки `@if` обычно уничтожает её экземпляры.

## Разобранная демонстрация

Полный компонент и сервис: `practice/angular-labs/src/demos/w3-04.ts`; переключающий wrapper `ClockHost` — в `practice/angular-labs/src/app.ts`. Запуск: `npm.cmd run practice:labs`, страница `http://127.0.0.1:4304/w3-04`. Число увеличивается раз в секунду; «Скрыть часы» уничтожает компонент и таймер. После повторного показа root-сервис сохраняет прежнее число. Здесь таймер делает существование ресурса видимым; в основном проекте не нужно добавлять таймер ради таймера.

```ts
import {
  ChangeDetectionStrategy, Component, DestroyRef, Injectable, inject, signal,
} from '@angular/core';

@Injectable({ providedIn: 'root' })
export class ReadingState {
  private readonly value = signal(0);
  readonly minutes = this.value.asReadonly();
  addMinute() { this.value.update(n => n + 1); }
}

@Component({
  selector: 'clock-demo', standalone: true,
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `<p>Учебных минут: {{ state.minutes() }}</p>`,
})
export class ClockDemo {
  readonly state = inject(ReadingState);
  constructor() {
    const timer = setInterval(() => this.state.addMinute(), 1000);
    inject(DestroyRef).onDestroy(() => clearInterval(timer));
  }
}
```

Для ускорения демонстрации «минута» проходит за секунду. После трёх срабатываний увидите три. Добавьте второй `<clock-demo />`: оба читают общий сервис, но каждый запускает собственный таймер, поэтому число растёт быстрее. Это важная граница ответственности: общий сервис не отменяет повторные побочные действия в компонентах. Уберите второй экземпляр после наблюдения.

Оберните единственный компонент в переключаемый `@if`. После удаления счётчик перестаёт увеличиваться благодаря cleanup; при повторном создании таймер появляется снова, а значение root-сервиса сохраняется. Если удалить `clearInterval`, старый таймер продолжит работать невидимо, а после каждого открытия добавится ещё один. Так возникают утечки и неожиданные повторные действия.

`DestroyRef` связывает очистку с областью, где его получили. Здесь это экземпляр компонента. Позднее для Observable используем `takeUntilDestroyed`, который завершает подписку при уничтожении. Не пытайтесь вызывать `inject()` произвольно в обработчике клика: ему нужен injection context. Получите зависимость при создании и используйте сохранённое поле.

## Общий StoreService и старые подписки в PL

По переданному разбору, в PL2.2/PL2.1 состояние находится в сервисах на Signals, а события и запросы используют RxJS. Standalone описывает организацию компонентов, но не отменяет иерархию DI. Если добавить общий `StoreService` в `providers` отдельной панели, она может получить собственный экземпляр и перестать видеть выбор соседней панели. Сначала найдите фактическое место предоставления сервиса: имя `StoreService` само по себе не доказывает root scope. Локальный provider полезен для действительно независимого состояния редактора, если это предусмотрено устройством страницы.

В PL также найден базовый класс с ручной отпиской. Это не означает, что приложение построено на NgModules, и не требует немедленной миграции. При чтении выясните, где создаются подписки, в какую коллекцию добавляются и кто вызывает `unsubscribe`. Если наследник переопределяет `ngOnDestroy`, проверьте, сохраняет ли он очистку базового класса, обычно вызовом `super.ngOnDestroy()`. У базового метода могут быть и другие обязанности: закрытие ресурсов, удаление обработчиков, сброс состояния.

Для новой подписки Angular 21 поддерживает `takeUntilDestroyed` из `@angular/core/rxjs-interop`. В constructor можно вызвать его без аргумента; внутри `ngOnInit` или обработчика передавайте заранее полученный `DestroyRef`. Он должен принадлежать нужному владельцу: очистка, привязанная к root-сервису, не произойдёт при закрытии отдельной панели. Операторы и варианты `async`/`toSignal` подробно применим в [уроке поиска](/lessons/w4-04).

При небольшой доработке сохраните действующий механизм cleanup. Перед заменой ручной отписки проверьте открытие → закрытие → повторное открытие: одно событие должно вызывать одну реакцию, а закрытая панель — ни одной. Механическое удаление базового класса по слову «устаревший» может убрать нужное поведение вместе с отпиской.

## Change detection и OnPush

Change detection — согласование данных и представления. `OnPush` позволяет Angular пропускать ветви, для которых нет причины проверки. Среди причин — новые входы, события в ветви и уведомления signals, прочитанных шаблоном. Это не обещание «проверить только один раз». Прямая мутация прежнего входного объекта особенно плохо сочетается с ожиданием, что дочерний OnPush-компонент заметит изменение сам.

В примере шаблон читает signal сервиса, поэтому его уведомление связано с отображением. Возвращайтесь к механизму, а не к рецепту «после каждого присваивания вызвать detectChanges». Ручные вызовы могут скрыть неправильного владельца данных и привести к дополнительным проверкам. Для курса явные signals и неизменяемые обновления дают более понятный путь.

## Мост от Java

Сходство со Spring DI полезно для идеи «зависимость предоставляется окружением». Граница: browser injector не является контейнером backend, root scope не означает HTTP session и не даёт доверенной авторизации. Сервис в браузере доступен пользователю через загруженный код и инструменты разработчика. Проверка прав остаётся на Java API.

## Критерии ручной проверки

Владение массивом одно; экземпляры не создаются вручную; изменение видно всем потребителям; вы объясняете область root и пример cleanup; OnPush не обходится бессистемными принудительными обновлениями. Можете показать, почему локальный provider разделяет состояние и почему при замене отписки нужно проверить обязанности базового класса.
