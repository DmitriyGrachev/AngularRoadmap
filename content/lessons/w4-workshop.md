# Практикум: список и детали с Java API

300 минут: 180 на интеграцию, 60 на диагностику, 60 на объяснение ошибок. Нужны [HTTP-контракт](/lessons/w4-01), [состояния](/lessons/w4-03), [поиск](/lessons/w4-04), [пагинация](/lessons/w4-05).

## Рабочая ситуация

Приложение должно переживать медленный ответ, отсутствие записей и временно недоступный backend. Открытый URL обязан воспроизводить поиск. Успех — не один удачный GET, а понятное поведение на каждом исходе и возможность найти причину сбоя по наблюдениям.

Сначала предскажите два случая: сервер вернул 200 с пустым items; сервер вернул 500. В первом пользователь может очистить фильтр, во втором — повторить загрузку. Если оба случая выглядят одинаково, интерфейс лишает пользователя полезного действия. Затем предскажите гонку двух поисков с обратным порядком ответов и объясните выбранную политику конкуренции.

## Сборка механизма

URL задаёт проверенную комбинацию q/status/page/size. Сервис переводит её в HttpParams и возвращает Observable. Компонент выбирает актуальное чтение через switchMap, преобразует результат в состояние представления и показывает items вместе с total. Отдельная карточка продолжает отвечать только за отображение и событие. HTTP не должен просачиваться в каждую строку списка без предметной необходимости.

Отмена чтения не равна ошибке для пользователя. Когда он набрал новый текст, старый запрос больше не нужен. Ошибка актуального чтения, наоборот, требует видимого объяснения и повторения. Размещение catchError внутри актуального запроса позволяет после сбоя продолжать ввод. Подписка связана с жизнью страницы, чтобы уход с маршрута не оставлял невидимый потребитель.

Сходство с Java-интеграцией состоит в контракте и границе ответственности. Отличие — браузер добавляет origin и CORS, а UI хранит видимое состояние между запросами. Серверный status и ошибка отображения относятся к разным слоям. Если JSON пришёл, но код читает поле `content` вместо `items`, настройка CORS не поможет.

## Нейтральная диагностическая демонстрация

Полный файл: `practice/angular-labs/scripts/w4-workshop.ts`. Команда из корня `node practice/angular-labs/scripts/w4-workshop.ts` выводит пять кодов с объяснениями, показанными ниже. Это чистая классификация: сервер, браузерная Console и настоящая система авторизации для неё не нужны.

```js
function explain(status) {
  if (status === 401) return 'Нет подходящей аутентификации';
  if (status === 403) return 'Доступ запрещён';
  if (status === 404) return 'Ресурс не найден';
  if (status === 0) return 'Нет доступного HTTP-ответа: нужна диагностика';
  return 'Смотрите контракт и тело ответа';
}
[401, 403, 404, 0, 500].forEach(s => console.log(s, explain(s)));
```

Status 0 здесь — условное значение Angular HttpErrorResponse для сетевого/браузерного сбоя, а не ответ Java со статусом «ноль». Оно само по себе не доказывает CORS: возможны отсутствие сети, блокировка, timeout или другая причина. Учебный API не обязан реально выдавать 401/403, поэтому эти случаи объясняются на моделях, без строительства auth-системы.

## Практика в IDE — w4-workshop-ex1

Работайте в `practice/issue-tracker/src/app/{app.ts,models.ts,issue.service.ts,issues-list.ts,issue-detail.ts}` и соседнем тесте сервиса. В разных терминалах запустите `npm.cmd run practice:api` и `npm.cmd run practice:angular`. Проверьте адрес `http://127.0.0.1:4302`.

Соберите цепочку: открыть URL списка → поиск → следующая страница → деталь → назад. Затем повторите при медленной сети и после остановки API. Быстро смените поисковую строку; после ошибки введите новую. Очистка должна вернуть полный набор с первой страницы. В деталях различайте loading, отсутствие и другой сбой.

Для диагностики по одному временно внесите два дефекта: неверный URL в сервисе и неверное чтение поля envelope. Перед каждым запишите гипотезу и ожидаемое наблюдение Network/Console. Подтвердите причину, верните исправление и повторите тот же сценарий. Не оставляйте временный дефект в итоговом коде и не удаляйте ошибочную проверку ради зелёного результата.

Один короткий тест должен проверять параметры клиента, второй — обработку ответа с ошибкой. Он дополняет браузерную проверку, но не заменяет её. Зафиксируйте отдельно «прошла проверка контракта» и «самостоятельно объяснил гонку и восстановление».

<details><summary>Подсказка 1 — локализация</summary>Сначала определите: запроса нет, запрос неуспешен или ответ есть, но неверно прочитан.</details>
<details><summary>Подсказка 2 — актуальность</summary>Один внешний поток параметров должен выбирать один актуальный внутренний HTTP-запрос.</details>
<details><summary>Подсказка 3 — envelope</summary>Сверьте items/total/page/size в Network с используемыми полями; не применяйте as any.</details>

## Контрольная точка

1. Почему новый ввод работает после ошибки?
2. Как доказать, что старый ответ не затрёт новый?
3. Чем 401, 403 и 404 отличаются по смыслу?
4. Что проверять при status 0, прежде чем называть причину?

Новая вариация: откройте URL с заведомо неверным page и объясните нормализацию, не меняя исходный API.

## Критерии ручной проверки

Оцените восстановление из URL, поиск без гонок, пагинацию по total, все состояния чтения, диагностику двух разных дефектов. Для каждого сохраните конкретный сценарий и уровень самостоятельности. Слабый пункт повторите на другом вводе. Сам факт успешного запуска сервера не является освоением интеграции.
