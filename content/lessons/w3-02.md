# Границы компонентов: inputs, outputs и pipe

120 минут. Результат: карточка получает данные и сообщает о намерении пользователя, а родитель принимает решение. Нужен [предыдущий урок](/lessons/w3-01).

## Ситуация и прогноз

В списке пять карточек. Каждая показывает заявку и кнопку смены статуса. Если карточка сама изменит полученный объект, сможет ли родитель гарантированно контролировать изменение? Где искать ошибку, если статус меняется в трёх местах? Предположите, как разделить чтение данных и команду на изменение до изучения примера.

## Контракт между родителем и ребёнком

Компонент стоит выделять вокруг понятной обязанности: карточка отображает запись и сообщает о нажатии; список выбирает данные, управляет фильтром и решает, что делать с событием. Выделение каждого `span` создаёт навигационные расходы без полезной границы. Хороший признак границы — вы можете описать входы и события компонента одним предложением.

Input — вход компонента. `input.required<T>()` создаёт обязательный типизированный вход; шаблон родителя должен передать значение. Его чтение похоже на чтение signal: `item()`. Сам компонент не вызывает `set` у input. Это намеренное ограничение: владение данными остаётся у передавшего их родителя. Вход `input('значение')` имеет значение по умолчанию и может быть необязательным.

Output — пользовательское событие компонента. `output<T>()` создаёт канал с методом `emit`. Родитель подписывается на него в своём шаблоне: `(rename)="handle($event)"`. Здесь `$event` — переданный полезный объект, а не обязательно DOM Event. События outputs не всплывают по DOM автоматически, поэтому промежуточный компонент должен явно передать нужное событие выше.

Называйте событие по намерению, например `statusRequested`, а не по внутренней детали вроде `buttonClicked`. При замене кнопки на меню намерение сохранится. Передавайте минимальные данные, достаточные для операции: ID и новый статус. Не заставляйте родителя угадывать запись по тексту кнопки и не отдавайте компоненту право незаметно изменять весь список.

Вход readonly не означает глубокую заморозку объекта. Можно технически мутировать вложенное поле обычного JavaScript-объекта, но это нарушит контракт владения и затруднит обновление интерфейса. Родитель должен построить новый объект или вызвать сервис с явной командой. Изменение может быть отклонено: позднее API проверит права и допустимость перехода. Output сообщает о намерении, а не доказывает, что сервер уже сохранил результат.

## Разобранная демонстрация

Полный файл: `practice/angular-labs/src/demos/w3-02.ts`. Запуск из корня: `npm.cmd run practice:labs`; страница `http://127.0.0.1:4304/w3-02`. Компоненты уже подключены; два класса находятся в одном файле, ребёнок объявлен раньше родителя. Ожидаются «HTTP», дата `20.10.2026` и после нажатия ID `b7`.

```ts
import { Component, input, output, signal } from '@angular/core';
import { DatePipe } from '@angular/common';

type Book = { id: string; title: string; publishedAt: string };

@Component({
  selector: 'book-tile', standalone: true, imports: [DatePipe],
  template: `
    <h3>{{ book().title }}</h3>
    <time>{{ book().publishedAt | date:'dd.MM.yyyy':'UTC' }}</time>
    <button type="button" (click)="chosen.emit(book().id)">Выбрать</button>
  `,
})
export class BookTile {
  book = input.required<Book>();
  chosen = output<string>();
}

@Component({
  selector: 'library-demo', standalone: true, imports: [BookTile],
  template: `
    <book-tile [book]="item" (chosen)="selected.set($event)" />
    <p>Выбран ID: {{ selected() }}</p>
  `,
})
export class LibraryDemo {
  item: Book = { id: 'b7', title: 'HTTP', publishedAt: '2026-10-20T00:00:00Z' };
  selected = signal('');
}
```

Ожидается заголовок `HTTP`, дата `20.10.2026` и пустая подпись ID до нажатия. После нажатия появляется `b7`. Ребёнок не знает, будет ли родитель открывать страницу, сохранять выбор или показывать диалог. Это делает его проще для проверки.

Pipe — преобразование для представления. Вертикальная черта передаёт значение в преобразователь, двоеточия — его аргументы. `DatePipe` не меняет ISO-строку внутри книги. Он строит строку для пользователя. В примере явно указан `UTC`, чтобы результат не сместился из-за часового пояса компьютера. Для реального `createdAt` заранее решают, показывать ли местное время или время сервера. Форматирование не заменяет проверку корректности входных данных.

Поменяйте заголовок родительского `item` через создание нового объекта. Карточка должна показать новое название. Затем измените имя события только у ребёнка: ошибка связывания или исчезновение ожидаемого обработчика демонстрирует, что имя является частью контракта. Верните согласованное имя, не обходите проблему отключением проверки шаблонов.

## Мост от Java

Input похож на параметр метода или DTO, output — на callback интерфейса. Но компонент живёт длительно: родитель может передавать новые значения после создания. Поэтому чтение входа только в constructor и сохранение навсегда в другом поле часто приводит к устаревшей копии. Angular output также не является сообщением Kafka: здесь нет очереди, хранения и доставки после перезапуска браузера.

## Критерии ручной проверки

У карточки явные типы входа и события; данные меняет владелец; ID определяет запись; дата форматируется без потери ISO; вы объясняете весь путь нажатия. Проверьте результат минимум на двух разных записях.
