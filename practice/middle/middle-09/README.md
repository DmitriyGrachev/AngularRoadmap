# middle-09 — Отделить Problem Details от безопасного сообщения UI

## Механизм

Problem Details помогает диагностике, но detail/title могут содержать техническую или чувствительную информацию. UI получает ограниченный собственный словарь. Возможность показать кнопку повтора зависит от метода и статуса, а не только от диапазона 5xx.

### Контракт API

`presentProblem(problem,method)` → ровно `{message:string,canRetry:boolean}`. problem неизвестен; распознаётся только числовой целый status у объекта, не массива. Словарь: 0 → "Нет соединения"; 400 → "Проверьте данные"; 401 → "Войдите в систему"; 403 → "Недостаточно прав"; 404 → "Объект не найден"; 409 → "Данные изменились; обновите экран"; 429 → "Слишком много запросов"; целые 500..599 → "Сервис временно недоступен"; прочие/отсутствующие/неверного типа → "Не удалось выполнить запрос". Никогда не возвращайте detail, title, type или сырой HTML. canRetry=true только для method GET/HEAD/OPTIONS (регистр значим) и status 0/429/502/503/504. Для POST/PATCH/PUT/DELETE false: в этой учебной политике нет серверного idempotency-контракта. Не выполняйте запрос и не реализуйте автоматический retry.

### Пример и новая проверка

{status:503,detail:"<img...>"} + GET → безопасная фиксированная строка и true. POST с тем же ответом → false. Новый пример: status:"503" — неизвестная форма, а не временный отказ.

## Критерии

- Словарь покрывает известные статусы, неизвестный ввод не вызывает исключение.
- Серверные detail/title/HTML никогда не выводятся как сообщение.
- Повтор зависит одновременно от метода и ограниченного набора статусов.

## Подсказки по порядку

1. Отделите проверку формы от выбора сообщения.
2. Проверьте точные статусы, затем диапазон 500..599.
3. Пересечение двух allowlists проще неявного правила status>=500.
