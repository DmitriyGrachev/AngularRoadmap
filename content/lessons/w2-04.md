# Внешние данные: unknown, проверка и Page<T>

**Результат:** вы принимаете внешний объект как unknown, проверяете обязательные поля и только затем используете типизированную заявку. Нужны [объекты](/lessons/w1-04), [обработка ошибок](/lessons/w2-02), [строгие типы и narrowing](/lessons/w2-03).

## Рабочая ситуация и прогноз

Java API изменился или вернул неожиданное тело. Редактор молчит, потому что разработчик написал утверждение типа. Во время отображения приложение падает на поле title.

```ts
interface Issue { id: string; title: string; }
const value: unknown = { id: 7 };
const issue = value as Issue;
console.log(issue.title);
```

Создаст ли `as Issue` недостающее поле? Проверит ли оно строковый id? Предскажите вывод. Затем назовите место, где проверка должна происходить, если данные приходят по сети, а интерфейс ожидает другой контракт.

## Структурная совместимость

TypeScript в основном проверяет совместимость объектов по нужным свойствам. Если функция ожидает `{id: string; title: string}`, ей подходит значение с такими полями, даже если оно пришло из другого объявления и содержит дополнительный status. Это структурная типизация. В Java обычно важно, что класс явно объявил реализацию интерфейса; здесь похожая форма может быть достаточной без такой декларации.

При непосредственной записи литерала объекта инструмент дополнительно помогает находить лишние поля. Это полезная диагностика опечаток, а не доказательство, что во время выполнения объект всегда содержит ровно перечисленные ключи. Не стройте безопасность на предположении «тип удалил неизвестные поля»: тип ничего не удаляет. В нашем parser ниже новый объект строится явно, чтобы в слой приложения попали только нужные значения.

Аннотации, interface, type и generic существуют при проверке и стираются для JavaScript-выполнения. `as Issue` — сообщение проверяющему инструменту «считай это Issue». Оно не преобразует число в строку, не создаёт свойства, не проверяет ответ и не вызывает конструктор. Поэтому прогноз даёт undefined. Более поздний вызов строкового метода у отсутствующего title приведёт к ошибке. Подавление подсказки редактора только отложило обнаружение.

## any и unknown отвечают на разные вопросы

`any` разрешает почти любые операции и распространяет потерю проверки дальше. Если ответ объявлен any, `value.customer.profile.title.trim()` может выглядеть допустимо без доказательства существования цепочки. Внешние данные безопаснее обозначить unknown: значение есть, но его форма ещё неизвестна. Перед операцией инструмент потребует уточнения. Unknown не проверяет данные сам, он заставляет написать реальную проверку перед использованием.

Проверка нужна на границе доверия: когда значение впервые приходит из внешнего источника — JSON, пользовательского файла, хранилища или сети. После успешного разбора внутренний код может принимать проверенный Issue, не повторяя все условия в каждом компоненте. Это уменьшает дублирование и делает причину ошибки понятной. Здесь делаем небольшой ручной parser; для большой сложной схемы в рабочем проекте может использоваться отдельная библиотека, но изучение её API не является условием урока.

## Как проверяется объект

Сначала проверяем `typeof value === 'object'`, затем отдельно исключаем `null`: исторически typeof null тоже даёт object. Только после этого можно проверять наличие ключей оператором `in`. Условие `'id' in value` говорит, что свойство доступно; оно ещё не говорит, что свойство строковое. Поэтому далее проверяется `typeof value.id === 'string'`. Оператор `||` вычисляет части слева направо и прекращает работу на истинной части: цепочка отказа не обращается к полям до доказательства объекта.

Статус требует двух ступеней: сначала значение должно быть строкой, затем входить в допустимый набор OPEN/IN_PROGRESS/DONE. Проверка только `typeof status === 'string'` пропустит ARCHIVED. Название по нашему минимальному контракту строковое; бизнес-правило длины — отдельная проверка. Не утверждайте, что проверены все правила сервера, если parser проверяет лишь минимальные поля для отображения.

Если условие нарушено, parser бросает Error с понятным сообщением. Вызывающий код обрабатывает её через try/catch и показывает ошибку данных. После всех проверок возвращаем новый объект с проверенными полями. Возвращаемый тип Issue документирует успешный результат, а throw означает, что неверный вход не даст притворно корректную заявку.

## Generic без загадки

`type Page<T> = {items: T[]; total: number}` описывает форму страницы, где T — параметр типа элемента. `Page<Issue>` содержит заявки, `Page<string>` — строки. Это способ переиспользовать одну структуру, сохранив точный тип items. Здесь нет сложного вычисления типов. Параметр T не создаёт parser и исчезает при выполнении; проверять вход по-прежнему нужно отдельно. Total — общее количество подходящих элементов, которое может превышать длину одной страницы.

## Мост от Java и разобранный пример

Page<T> напоминает Java generic DTO, однако TypeScript не передаёт конструктор T для автоматической проверки JSON. Нельзя написать проверку «value instanceof Issue», если Issue — только interface. `instanceof Error` работает, потому что Error является реальным конструктором в JavaScript. Эта граница между типом и существующим значением важнее внешнего сходства синтаксиса.

Запустите `node practice/foundations/async-types/examples/validation.ts`. Ожидаются `Письмо 1` и `Ожидались строковые id и title`. Первый внешний JSON проходит минимальный parser, второй объект с числовым id отвергается. В catch используется `error instanceof Error`: он позволяет безопасно получить message, иначе выбирается запасной текст. Пример намеренно проверяет только id/title; в самостоятельной работе добавляется статус. Затем выполните `npx.cmd tsc --noEmit -p practice/foundations/async-types/tsconfig.json`.

Упражнение `w2-04-ex1`: редактируйте `practice/foundations/async-types/w2-04-ex1/main.ts`. Опишите Issue с id/title/status, Page<T> и реализуйте parseIssue(value: unknown): Issue. Не используйте any или утверждение `as Issue`. Проверьте корректный объект, числовой id, null, отсутствие title и неизвестный статус. Для каждого неверного входа покажите понятное сообщение без необработанного падения всей демонстрации.

Запуск: `node practice/foundations/async-types/w2-04-ex1/main.ts`; проверка типов — указанная команда tsc. Создайте Page<Issue> с одной проверенной заявкой и total 1. Это ручное упражнение: сохраните наблюдения, но не импортируйте обычный вывод консоли как автоматический отчёт.

## Критерии

- Unknown не превращается в Issue без реальных проверок объекта и всех требуемых полей.
- Четыре неверных входа отклоняются, корректный проходит; ошибки обработаны и понятны.
- Page<Issue> сохраняет тип элемента, строгая проверка проходит без any и подавления ошибки.
- Вы объясняете, что именно parser проверяет и какие бизнес-ограничения ещё не проверены.

## Проверка понимания

1. Что делает as и чего не делает?
2. Почему typeof null требует отдельного условия?
3. Чем наличие поля отличается от корректного типа поля?
4. Почему Page<Issue> не проверяет тело HTTP-ответа?

Новая вариация: parser должен принимать optional assignee только строкового типа, если поле присутствует. Сформулируйте поведение для отсутствия, null и числа до написания условий.
