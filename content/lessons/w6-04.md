# Самостоятельная задача: фильтр приоритета через API

120 минут. Результат: вы превращаете небольшое требование в проверяемое изменение без пошагового рецепта. Нужны [URL и пагинация](/lessons/w4-05), [диагностика](/lessons/w6-02), [проверки](/lessons/w6-03).

## Требование

Добавьте фильтр приоритета списка: «Все», `LOW`, `MEDIUM`, `HIGH`. Фильтрация выполняется API, выбор сохраняется в URL и восстанавливается после обновления страницы. При изменении приоритета список начинается с page=0. Поиск и фильтр статуса продолжают работать вместе с новым условием. Это первый сеанс задачи; завершение и самопроверка — [следующий урок](/lessons/w6-05).

До открытия файлов предскажите три наблюдения: какой query появится в URL; какой параметр уйдёт в HTTP; что случится с дальней страницей при смене приоритета. Если вы не можете назвать ожидаемое поведение, начинать с select рано: сначала уточните собственную модель задачи по данному требованию.

## Критерий готовности отличается от списка правок

«Добавить поле в компонент» — действие разработчика. «Прямая ссылка с priority=HIGH показывает только высокий приоритет» — наблюдаемое поведение. Второе позволяет проверить результат независимо от устройства кода. Сначала сформулируйте несколько критериев готовности: выбор, сохранение URL, серверный параметр, сочетания, очистка и плохое значение.

Затем найдите фактических владельцев по цепочке, которую строили в начале недели. Не предполагайте, что задача затронет ровно три файла: в вашем решении функция нормализации может быть в другом месте. Но и не переписывайте весь сервис ради одного параметра. Размер изменения определяется существующей ответственностью, а не стремлением показать все изученные технологии.

Для URL сохраните один источник состояния. Если q/status/page уже читаются из queryParamMap, новый priority должен пройти тот же путь. Отдельный signal, который обновляет только select, создаст рассинхронизацию после Back или прямой ссылки. Если параметр отсутствует, это «все»; если значение неизвестно, безопасная нормализация не должна передавать его как действительный priority.

Серверное условие существенно: локальный `.filter` на текущей странице может показывать подходящие строки, но потерять совпадения с других страниц и неверно сообщить total. В Network должны быть видны priority и остальные условия одновременно. Комбинация фильтров — пересечение, а не замена q на priority.

## Независимый пример планирования

Полный файл: `practice/angular-labs/scripts/w6-04.ts`. Команда из корня `node practice/angular-labs/scripts/w6-04.ts` выводит `сети 0`; браузер и Java API не нужны. У библиотеки просят новый фильтр доступности. Сначала удобно записать переходы в чистом виде, не копируя решение трекера:

```ts
type Availability = 'ALL' | 'AVAILABLE' | 'BORROWED';
type CatalogState = { query: string; availability: Availability; page: number };
const state: CatalogState = { query: 'сети', availability: 'ALL', page: 4 };
const afterChoosingAvailable: CatalogState = {
  ...state, availability: 'AVAILABLE', page: 0,
};
console.log(afterChoosingAvailable.query, afterChoosingAvailable.page); // сети 0
```

Пример показывает сохранение независимого условия и сброс страницы. Он не решает преобразование URL, построение HTTP и отображение select: это разные границы. Вариация: пользователь меняет только page. Какие поля должны остаться прежними? Сформулируйте это до кода.

Теперь составьте маленькую проверку контракта библиотеки: запрос должен содержать `availability=AVAILABLE` и прежний query. Если assertion проверяет только новый параметр, он пропустит потерю старого. Перенесите этот принцип на задачу приоритета, не копируя имена демонстрации в реальный DTO.

## Границы ответственности и риска

Backend уже поддерживает priority, поэтому изменение Java API не нужно, пока наблюдение не докажет нарушение готового контракта. Не добавляйте миграции, новые статусы и глобальное хранилище. Фильтр не является проверкой прав: скрыть строки на клиенте не означает ограничить доступ к ним. Но в данной задаче требуется чтение, а не новая auth-система.

Контроль размера полезен: если маленький фильтр заставляет менять форму создания, объясните, почему. Возможно, вы смешали модель запроса списка и DTO записи. Общий union приоритета уместен, один гигантский объект «параметры всего» — нет. Разделение следует смыслу данных, а не количеству файлов.

## Мост от Java

Это похоже на добавление необязательного параметра controller, но изменение начинается с пользовательского состояния и истории браузера. Java-контракт уже принимает priority; ваша работа — провести его от URL до HttpParams и показать соответствующий результат. Nullable/optional в TypeScript и отсутствие query-параметра нужно трактовать явно, а не сериализовать слово `undefined`.
