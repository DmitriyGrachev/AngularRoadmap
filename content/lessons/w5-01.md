# Typed Reactive Forms: модель формы

120 минут. Результат: форма создания имеет типизированную модель, а состояние полей можно объяснить без чтения DOM вручную. Нужны [компоненты](/lessons/w3-02), [типы](/lessons/w2-03), [HTTP-контракт](/lessons/w4-01).

## Ситуация и прогноз

Пользователь изменил название, затем вернул исходный текст. Стало ли поле снова pristine? Нет: dirty описывает факт пользовательского изменения, а не равенство исходному значению. Предскажите также, станет ли поле touched после программного setValue. Эти вопросы различают значение и историю взаимодействия.

## Модель отдельно от разметки

Reactive Forms — подход, при котором модель формы создаётся в TypeScript. `FormControl` представляет одно поле, `FormGroup` объединяет именованные controls. HTML связывается с моделью через `[formGroup]` и `formControlName`. Для этих директив standalone-компонент импортирует `ReactiveFormsModule`. Обычный import FormControl в TypeScript не предоставляет директивы шаблону.

Control хранит не только value. Он знает статус проверки и взаимодействия: valid/invalid, pending, touched/untouched, dirty/pristine, disabled/enabled. Valid означает прохождение зарегистрированных проверок; это не гарантия серверной допустимости. Pending означает выполняющуюся асинхронную проверку, а не автоматически любой ваш POST. Для отправки обычно требуется отдельное состояние saving.

Touched становится true после ухода пользователя из поля; dirty — после пользовательского изменения значения. Эти факты помогают выбрать момент сообщения об ошибке. Программное заполнение существующей записи обычно не должно выглядеть как пользовательская правка. Поэтому не пытайтесь вычислять touched из значения и не маркируйте все поля dirty при начальной загрузке.

Typed forms связывают типы controls и их значений. По умолчанию FormControl строки может быть nullable, поскольку reset способен вернуть null. Параметр `nonNullable: true` меняет тип и поведение reset: он возвращает начальное значение. Это подходит полям, где null не имеет предметного смысла, например названию. Но nullable-выбор «ничего не выбрано» вполне может быть правильной моделью другого поля.

Значение FormGroup через `.value` учитывает disabled controls и потому может иметь optional-поля. `.getRawValue()` включает отключённые поля. Выбирать нужно по требованию запроса, а не ради подавления ошибки типов. Disabled input не является защитой от подмены: клиентский код доступен пользователю, сервер обязан проверять разрешённые поля.

## Разобранная демонстрация

Полный файл: `practice/angular-labs/src/demos/w5-01.ts`. Запустите `npm.cmd run practice:labs`, откройте `http://127.0.0.1:4304/w5-01`. Читательский профиль уже подключён. С пустым именем результат не появляется; после имени и submit показываются имя/город; reset возвращает исходные controls. Пример не создаёт заявку и не обращается к API.

```ts
import { Component, signal } from '@angular/core';
import { FormControl, FormGroup, ReactiveFormsModule, Validators } from '@angular/forms';

@Component({
  selector: 'reader-form-demo', standalone: true, imports: [ReactiveFormsModule],
  template: `
    <form [formGroup]="form" (ngSubmit)="submit()">
      <label for="reader-name">Имя читателя</label>
      <input id="reader-name" formControlName="name">
      <label for="reader-city">Город</label>
      <input id="reader-city" formControlName="city">
      <button type="submit">Показать</button>
      <button type="button" (click)="form.reset()">Начальные значения</button>
    </form>
    <p>Отправлено: {{ result() }}</p>
    <p>dirty: {{ form.dirty }}, touched: {{ form.touched }}</p>
  `,
})
export class ReaderFormDemo {
  form = new FormGroup({
    name: new FormControl('', { nonNullable: true, validators: [Validators.required] }),
    city: new FormControl('Кишинёв', { nonNullable: true }),
  });
  result = signal('');
  submit() {
    if (this.form.invalid) { this.form.markAllAsTouched(); return; }
    const value = this.form.getRawValue();
    this.result.set(`${value.name}, ${value.city}`);
  }
}
```

С пустым именем результат не появляется; после ввода и отправки показывается строка. Reset возвращает пустое имя и исходный город. Он сбрасывает модель формы, но не ваш отдельный signal result: проверьте это наблюдением. Решение, очищать ли старый результат, относится к поведению компонента и должно быть выражено отдельно.

Вариация: отключите city программно через `form.controls.city.disable()`, затем сравните `form.value` и `form.getRawValue()` в Console/отладчике. Первое значение не включает city, второе включает. После эксперимента верните поле. Не применяйте non-null assertion к каждому чтению только потому, что форма «по идее заполнена»; настройте модель под реальный контракт.

## Как меняют модель

`setValue` требует полную структуру группы, поэтому полезен, когда ожидаете все поля. `patchValue` меняет переданные поля и оставляет остальные прежними. `reset` возвращает форму в начальное или явно переданное состояние. Эти операции отличаются от отправки HTTP: ни одна из них сама не сохраняет данные на сервере.

Не связывайте один control одновременно через formControlName и отдельную ручную запись value при каждом input. Получится два владельца одного поля. Аналогично, не копируйте все значения формы в signals без потребителя: это второй слой синхронизации. Signals хорошо подходят для состояния запроса и результата, controls — для модели ввода.

## Мост от Java

FormGroup похож на объект с полями, но содержит изменяемые controls, validators и историю взаимодействия, а не просто DTO запроса. Перед HTTP вы явно строите payload. Передавать сам FormGroup в JSON нельзя: это объект инфраструктуры, а не данные предметной области. Сервер также не знает, какое поле touched, пока контракт специально не передаёт такую информацию.

## Критерии ручной проверки

Все поля связаны с типизированными controls; отсутствует двойное владение DOM; submit получает данные, а не FormGroup; reset предсказуем; приоритет ограничен типом; подписи доступны с клавиатуры.
