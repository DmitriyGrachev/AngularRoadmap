# Валидация: когда и как объяснять ошибку

120 минут. Результат: некорректная форма не отправляется, а сообщения помогают исправить конкретное поле. Нужна [модель формы](/lessons/w5-01).

## Ситуация и прогноз

При первом открытии формы все поля уже красные. Другой вариант — кнопка disabled, но нигде не объяснено почему. Какой из экранов помогает новичку? Сам validator не выбирает удобный момент сообщения. Предскажите состояние required-поля с пустой строкой: invalid с самого начала, но untouched и pristine. Значит, ошибка существует в модели раньше, чем обязана появиться на экране.

## Проверка и представление различаются

Validator — функция, которая читает control и возвращает объект ошибок либо null. Встроенные required, minLength, maxLength покрывают обычные ограничения. Ключ ошибки нужен шаблону для конкретного текста: `required` означает отсутствие обязательного значения, `minlength` — недостаточную длину. Не показывайте пользователю JSON внутреннего объекта errors вместо понятного предложения.

В Angular `Validators.required` не считает строку из пробелов отсутствующей. Если предметное требование — непустое после trim название, это отдельное условие. Можно нормализовать перед отправкой и валидировать нормализованное значение либо добавить маленький validator. При этом не изменяйте control внутри validator: проверка должна возвращать результат, а не запускать новую цепочку изменений.

Практичная политика показа: invalid и (touched или была попытка отправки). Пользователь может спокойно заполнять поле; после ухода из него видит ошибку. При submit вызывайте markAllAsTouched и явно прекращайте отправку, если форма invalid. Отключение кнопки само по себе не заменяет проверку в обработчике: событие может прийти другим способом, а будущее изменение шаблона не должно обходить правило.

Сообщение должно отвечать, что исправить: «Введите название» или «Не более 120 символов», если именно такое число задано контрактом. Не устанавливайте произвольный лимит только ради упражнения. В основном трекере берите ограничения из локального API README. Клиентская проверка помогает пользователю быстро, серверная защищает данные независимо от браузера.

## Разобранная демонстрация

Полный выполняемый файл: `practice/angular-labs/scripts/w5-02.ts`. Команда из корня `node practice/angular-labs/scripts/w5-02.ts` выводит `true false`, затем `true` и `true`. Файл предварительно импортирует `@angular/compiler` для инициализации библиотеки forms; decorators и браузер здесь не используются. Самостоятельный control относится к псевдониму читателя. Лимит 12 принадлежит только нейтральному примеру и не является ограничением названия заявки.

```ts
import { FormControl, Validators } from '@angular/forms';
import type { AbstractControl, ValidationErrors, ValidatorFn } from '@angular/forms';

const nonBlank: ValidatorFn = (control: AbstractControl): ValidationErrors | null => {
  const value: unknown = control.value;
  return typeof value === 'string' && value.trim().length > 0
    ? null : { blank: true };
};

const nickname = new FormControl('', {
  nonNullable: true,
  validators: [nonBlank, Validators.maxLength(12)],
});
console.log(nickname.invalid, nickname.touched); // true, false
nickname.setValue('   ');
console.log(nickname.hasError('blank')); // true
nickname.setValue('Анна');
console.log(nickname.valid); // true
```

Здесь unknown не позволяет молча вызвать trim на любом значении. В типизированном control строка ожидается, но validator имеет общий контракт AbstractControl; явная проверка делает небольшую функцию корректной на своей границе. Вариация: передайте строку длиннее 12 символов. Ошибка blank исчезнет, появится maxlength. Решите, какое сообщение показывать первым при нескольких ошибках.

Следующий HTML — фрагмент для чтения связи label/input/errors, а не отдельный исполняемый файл. Его можно встроить в компонент по образцу формы из `practice/angular-labs/src/demos/w5-01.ts`; самостоятельно через Node HTML не запускается:

```html
<label for="nickname">Псевдоним</label>
<input id="nickname" [formControl]="nickname"
  [attr.aria-invalid]="nickname.invalid && nickname.touched ? 'true' : null"
  aria-describedby="nickname-help">
<p id="nickname-help">
  @if (nickname.touched && nickname.hasError('blank')) {
    Введите хотя бы один непробельный символ.
  }
</p>
```

Для запуска шаблона control должен быть полем standalone-компонента, а ReactiveFormsModule — его импортом, как [в прошлом уроке](/lessons/w5-01). ID связывает label и input; aria-describedby связывает поле с текстом помощи. Цвет может усиливать сообщение, но не заменять его: пользователь может не различать оттенки или использовать экранный диктор.

## Фокус и отправка

После неудачной попытки полезно перевести фокус на первое неверное поле либо дать сводку со ссылками на поля. Не перемещайте фокус при каждом введённом символе: это мешает набору. Сохраняйте видимый focus outline. HTML required и maxlength могут дополнять модель и помогать браузеру, но согласуйте их с Angular validators, чтобы пользователь не видел противоречивые ограничения.

Не очищайте форму при клиентской ошибке. Значение, которое не прошло проверку, как раз нужно пользователю для исправления. А сообщения серверных ошибок должны оставаться отдельной темой: сервер может отклонить даже валидное по клиентским правилам значение, например из-за дубликата.

## Мост от Java

Validators похожи на Bean Validation по идее ограничений, но работают в другой доверенной зоне. Пользователь может изменить браузерный код и отправить POST напрямую. Поэтому перенос `@NotBlank` в UI не позволяет удалить серверную проверку. Совпадение правил полезно для удобства, сервер остаётся окончательным источником допустимости записи.

## Проверка понимания

1. Почему invalid не означает «сразу показать красный текст»?
2. Что возвращает validator при успехе?
3. Почему disabled не заменяет guard обработчика?
4. Какие проверки обязательно остаются на сервере?

Новая вариация: опишите поведение поля, которое исправили после первого submit, не сбрасывая всю форму.

## Критерии ручной проверки

Правила совпадают с контрактом; сообщения конкретны и связаны с полями; untouched-поле не пугает преждевременно; invalid не отправляется; клавиатура и фокус работают; значение сохраняется после ошибки.
