# Границы компонентов и DI: кто владеет данными и временем жизни

180 минут: 35 на чтение, 25 на демонстрацию, 90 на рефакторинг и 30 на проверку. Нужны [Signals store](/lessons/w8-01) и [URL-состояние](/lessons/w8-02). Результат: вы выделяете компонент по ответственности и выбираете область сервиса по требуемому времени жизни.

## Разделение без архитектуры ради архитектуры

Страница списка одновременно читает Router, выполняет запрос, форматирует статус, рисует строку и обрабатывает выбор. Не вся эта работа обязательно требует пяти слоёв. Хорошая граница появляется там, где есть независимый контракт: строка получает проверенные данные и сообщает намерение открыть карточку; страница знает маршруты и загрузку. Выделять компонент только потому, что шаблон стал длиннее двадцати строк, недостаточно. После выделения должно стать проще понять, проверить или повторно использовать конкретное поведение.

Input передаёт данные вниз, output сообщает событие вверх. Событие `selected` с ID не говорит, какая страница должна открыться; решение остаётся у владельца сценария. Если дочерний компонент сам читает ActivatedRoute и вызывает API, его внешний вид может выглядеть переиспользуемым, но фактический контракт привязан к окружению. Это допустимо для feature-компонента, но не следует называть его универсальной карточкой.

Не передавайте в output весь изменяемый store. Маленькое событие `{id}` или конкретная команда сохраняет границу. Angular custom output не всплывает по DOM как обычный click: промежуточный компонент должен явно обработать или передать событие, если так устроен контракт. В то же время click вложенной кнопки внутри кликабельной строки может всплывать и запускать два действия. Лучше отделить ссылки и кнопки семантически, чем расставлять stopPropagation без понимания структуры.

## Provider определяет экземпляр

`providedIn: 'root'` обычно даёт общий экземпляр сервиса в root injector приложения. `providers: [FeatureStore]` на компоненте создаёт доступный его поддереву экземпляр, связанный с этим компонентом. Если child повторно объявит тот же provider, он получит свой экземпляр и перестанет видеть родительский выбор. Это частая причина «кнопка обновила сервис, но панель не изменилась». Проверьте область регистрации до попытки вручную рассылать события между двумя случайными stores.

Component imports и providers отвечают на разные вопросы. Imports определяет зависимости шаблона standalone-компонента; providers определяет, что injector может выдать. Добавление сервиса в imports не является его регистрацией. ES import лишь позволяет обратиться к символу в файле. Эти три операции похожи синтаксически, но решают разные задачи. В рабочем PL standalone-компоненты — исходная точка чтения, даже когда они импортируют библиотечный NgModule.

Область сервиса должна следовать пользовательскому сценарию. Справочник, общий для приложения, может жить на root. Черновой выбор отдельной панели часто должен исчезнуть при её закрытии и не влиять на вторую панель. Route-level provider полезен в некоторых feature-границах, но его фактическое время жизни зависит от маршрутизации и стратегии переиспользования. Не обещайте очистку «при каждом уходе» без проверки. Для учебного сравнения двух одновременно открытых панелей component provider даёт явную границу.

Java-аналогия — singleton и scoped bean в Spring. Но Angular ищет зависимость по иерархии injector, и несколько одинаковых компонентов могут иметь независимые экземпляры. Также `inject()` нельзя вызывать в произвольном обработчике кнопки: нужен injection context. Получите зависимость в поле класса или конструкторе, затем используйте её в обработчике. Перенос вызова в callback без контекста не становится корректным от того, что сам компонент создан Angular.

## Разобранная демонстрация

Запустите `npm.cmd run practice:labs`, откройте `http://127.0.0.1:4304/w3-04`. Исходники: `practice/angular-labs/src/demos/w3-04.ts` и `practice/angular-labs/src/app.ts`. ClockDemo создаёт таймер, а ReadingState зарегистрирован в root. Дождитесь нескольких учебных минут, нажмите «Скрыть часы», подождите, затем «Показать часы».

Ожидается: пока компонент скрыт, его таймер очищен и счётчик не увеличивается; после повторного создания он продолжает от сохранённого значения общего ReadingState. Число не обязано точно совпасть с секундомером из-за планирования таймеров. Важен факт остановки во время отсутствия компонента и сохранения state. Это два независимых срока жизни: ресурса компонента и root-сервиса.

Теперь на собственной временной копии демонстрации добавьте `providers: [ReadingState]` в metadata ClockDemo. Повторите скрытие и показ: новый экземпляр компонента получает новый state, счётчик начинается с нуля. После наблюдения верните временную правку. Не меняйте лабораторный файл ради прохождения задания; самостоятельная реализация находится в workplace. Этот опыт показывает, почему cleanup таймера не означает автоматический сброс всех связанных данных.

## Практика в IDE — w8-03-ex1

Условия: `practice/middle/w8-03-ex1/README.md`, отчёт — `notes.md`. В своей копии `practice/workplace` выделите отображение одной заявки из `list-page.html` в standalone-компонент. Он получает необходимые данные и сообщает событие выбора. Список остаётся владельцем URL и обращения к DeskApi. Сохраните подписи, дату, статус, приоритет и клавиатурное открытие. Событие выбора должно сработать один раз.

Затем добавьте небольшую панель локального выбора: максимум три ID, счётчик и очистка. Создайте две панели на одной странице для проверки изоляции и provision одного store на экземпляр панели. Вложенный счётчик должен видеть тот же store, что его родительская панель; соседняя панель — другой. После проверки можно оставить только продуктово нужную панель, сохранив тест изоляции двух экземпляров. Это упражнение про области, а не требование навсегда усложнить экран двумя похожими виджетами.

Команды: `npm.cmd run practice:workplace`, `npm.cmd run test:workplace`, `npm.cmd run build:workplace`. Для нового поведения добавьте ограниченный компонентный тест: выбор в первой панели, ноль во второй, очистка и повторное создание. Baseline-тесты подтверждают отсутствие некоторых регрессий, но не доказывают вашу новую границу. API workplace — сервис в памяти; независимость панелей не доказывает независимость серверных сессий.

<details><summary>Подсказка 1 — ответственность</summary>Перед переносом выпишите, что нужно строке для отображения. Router, запрос и общий фильтр не становятся input автоматически только потому, что доступны родителю.</details>
<details><summary>Подсказка 2 — экземпляр</summary>Найдите все providers выбранного store. Внутри одной панели provider должен находиться у владельца, а не повторяться у каждого ребёнка.</details>
<details><summary>Подсказка 3 — тест границы</summary>Создайте два настоящих host-компонента с панелями. Проверка двух объектов через new не проверяет Angular DI.</details>

**Новые данные.** Выберите одинаковый ID в обеих панелях, очистите первую, закройте и создайте её заново. Вторая сохраняет выбор; первая начинает пустой. Затем переименуйте заголовок строки через новый input и проверьте отображение без повторного создания всего списка. Добавьте длинное имя из прошлого урока: выделение компонента не должно вернуть переполнение.

## Критерии ручной проверки

Нужны понятный input/output-контракт, отсутствие скрытого API в строке, единственное событие действия и подтверждённая изоляция экземпляров. Самостоятельная защита объясняет difference между imports и providers, источник общего состояния и его очистку. Если рефакторинг потребовал глобального event bus для двух соседних компонентов, пересмотрите владение: возможно, состояние оказалось на неверной границе. Размер diff сам по себе не доказывает качество архитектуры.
