# middle-11 — Написать контрактные тесты, которые ловят дефекты

## Механизм

Здесь решением является тестовая функция. Проверка одного happy path мало говорит о политике. Несколько независимых условий дают полезную таблицу примеров: роль, активность, владение, состояние записи и отсутствие пользователя.

### Контракт API

Экспортируйте `verifyCanEdit(canEdit)` — синхронную или async функцию, которая вызывает переданную реализацию и бросает assertion/Error при нарушении контракта. canEdit(actor,issue) должен вернуть boolean. actor — null или `{id:string,roles:string[],active:boolean}`, issue=`{ownerId:string,status:"OPEN"|"IN_PROGRESS"|"DONE"}`. Разрешено редактирование только активному actor, когда статус не DONE и (есть ADMIN либо есть EDITOR и actor.id===issue.ownerId). ADMIN не требует владения, но не обходит inactive/DONE. Неизвестная роль или совпадение owner без EDITOR/ADMIN не дают права. null → false. Корректная реализация должна пройти без исключений; реализации, пропускающие эти условия, должны отклоняться. Можно импортировать node:assert/strict. Не возвращайте только boolean: при найденной ошибке нужно бросить исключение. Это политика видимости клиентской команды; реальная авторизация всегда на backend.

### Пример и новая проверка

Активный EDITOR владеет OPEN → true. Активный ADMIN не владеет IN_PROGRESS → true. Неактивный ADMIN → false. Новый пример: владелец с VIEWER и открытой заявкой → false.

### Работа

Из корня проекта выполните `npm.cmd run learn -- check middle-11`. Редактируйте только `practice/middle/middle-11/solution.mjs`; starter остаётся исходной точкой. Сначала запишите прогноз или собственную попытку. JSON-отчёт появится в practice/reports; импорт отчёта не означает самостоятельное освоение урока.

## Критерии

- Правильная реализация проходит, и тесты действительно вызывают параметр canEdit.
- Проверены отрицательные случаи inactive, DONE, отсутствие пользователя.
- Проверены EDITOR+владение, недостаточная роль и ADMIN без владения.

## Подсказки по порядку

1. Запишите таблицу expected boolean до вызова реализации.
2. Добавьте позитивный случай ADMIN чужой заявки и негативный случай EDITOR чужой заявки.
3. Варьируйте по одному условию, чтобы выявить проверку, которую забыли.
