# Практикум: изменение Angular + Java с конфликтом и правами

360 минут: 35 на контракт, 100 на Java-изменение, 100 на frontend, 85 на интеграционные проверки и 40 на защиту. Нужна [граница безопасности](/lessons/w11-03). Используйте знакомые Spring Boot/JPA/SQL; основы backend повторять не требуется.

## Что уже существует и что предстоит сделать

`practice/issue-tracker` запускает Angular на 4302; `npm.cmd run practice:api` поднимает настоящий Java HTTP API на 8080. Подготовленный API — небольшой JDK-сервис в памяти, не Spring Boot: у него нет JPA, auth, version, плана решения или Problem Details. `practice/workplace` ещё проще — только mock в браузере. Ни один baseline не доказывает конкурентную запись или авторизацию.

Ваша задача — подключить редактор плана недели 10 к настоящему локальному Java API по контракту ниже. Если готовы расширять JDK-сервис, используйте атомарное compare-and-set внутри критической секции и настоящие серверные сессии. Предпочтительный для вашего опыта путь — отдельное локальное Spring Boot-приложение с уже знакомыми зависимостями, JPA `@Version`, двумя тестовыми пользователями и Spring Security. Его создание и конфигурация являются учебной работой, а не уже реализованной возможностью курса. В notes укажите путь и команду запуска; не копируйте рабочий PL-код. Облачные сервисы и платные аккаунты не нужны.

## Фиксированный контракт

Для нового ресурса используйте `/api/plans/PLAN-17`, не ломая старые `/api/issues`. Начальная запись: owner `anna`, title `Проверка доступа`, version `4`, строки `row-a` («Анализ», 2) и `row-b` («Тест», 3). Роли: anna — EDITOR, boris — EDITOR без доступа к этому плану, admin — ADMIN. Права проверяются сервером; owner берётся из сохранённой записи, не из присланного JSON.

`GET` возвращает `{ id, ownerId, title, version, rows }`. `PUT` принимает `{ expectedVersion, title, rows }`; полная замена плана облегчает контракт редактора. Сервер валидирует ограничения недели 10, разрешённые поля и уникальные clientId. Успех — 200 с каноническим DTO и увеличенной version; stale expectedVersion — 409 с Problem Details; нарушение полей — 422 с массивом `{id, field, message}`; отсутствие сессии — 401; чужая запись — 403. Запись и проверка версии должны быть атомарны. Отправка ownerId не должна передать владение.

Пример ответа, который нужно обеспечить сервером, а не просто положить во frontend fixture:

```json
{
  "type": "urn:problem:plan-version-conflict",
  "title": "План изменён другим пользователем",
  "status": 409,
  "instance": "/api/plans/PLAN-17",
  "requestId": "req-demo-18"
}
```

Для Spring создание тела может выглядеть так; mapping вашей доменной ошибки, транзакция и проверка прав остаются отдельными обязанностями:

```java
var problem = ProblemDetail.forStatusAndDetail(
    HttpStatus.CONFLICT, "Загрузите актуальную версию плана");
problem.setType(URI.create("urn:problem:plan-version-conflict"));
problem.setProperty("requestId", requestId);
return ResponseEntity.status(HttpStatus.CONFLICT).body(problem);
```

Ожидается JSON Problem Details и HTTP 409, а не 200 с полем error. Клиент выбирает безопасное сообщение по статусу/коду, сохраняет свой draft и предлагает перечитать серверную версию. Не заменяйте draft ответом GET без согласованного действия пользователя. При JPA не ограничивайтесь сравнением version перед save: параллельные транзакции должны конфликтовать на самой записи. [Spring Problem Details](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html), [Jakarta Persistence Version](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/Version.html).

## Последовательность реализации и доказательств

1. Запишите запросы и ожидаемые статусы до кода. Создайте fixture PLAN-17 и API-тесты успешной записи, stale version и чужого пользователя. Выполняйте тесты в отдельной локальной базе/состоянии; не сбрасывайте пользовательские данные.
2. Настройте same-origin `/api` proxy к новому Java-приложению либо явную локальную конфигурацию. Проверьте cookie-сессию и CSRF: valid unsafe-запрос проходит; тот же запрос без token отклоняется. Следуйте SPA-настройкам вашей версии Spring Security, включая обновление token после входа/выхода.
3. Добавьте Angular service с DTO-проверкой ответа, сопоставление 409/422 и состояние saving. Не повторяйте PUT автоматически после timeout: результат записи мог сохраниться. Для этого практикума используйте блокировку повторной отправки; optimistic-preview оставьте опциональным, если он не нарушает draft.
4. Откройте две вкладки под anna, обе читают version 4. Первая сохраняет и получает 5. Вторая отправляет 4 и получает 409; на сервере остаётся первая запись, а во второй вкладке сохраняется несохранённый ввод. После явного перечитывания и согласованного переноса изменений новая запись использует 5.
5. Войдите как boris и попробуйте тот же PUT напрямую через разрешённый локальный API-клиент с корректным CSRF. Ожидается 403 и неизменившаяся запись. Без корректного CSRF запрос тоже должен быть отклонён, но это отдельная причина.

В Java это знакомая защита агрегата; новая работа — провести результат через HTTP, RxJS и форму, не исказив намерение пользователя. Интеграционный тест обязан наблюдать реальный ответ и последующий GET. Fake, возвращающий 409, подтверждает только реакцию интерфейса.

<details><summary>Подсказка 1 — конфликт</summary>Серверная version относится к сохранённой записи, локальная revision — к draft. Не складывайте их в одно поле.</details>
<details><summary>Подсказка 2 — права</summary>В тесте 403 CSRF должен быть корректным, иначе вы не проверили объектную авторизацию.</details>
<details><summary>Подсказка 3 — повтор</summary>После потери ответа сначала выясните серверное состояние. Кнопка «повторить» не отменяет уже совершённую запись.</details>

## Новое требование и отчёт

После основной попытки добавьте правило: план с общей оценкой больше 40 может сохранять только ADMIN. Новый план с оценкой 41 обязан дать 403 для anna, 200 для admin; 40 остаётся доступно anna. Докажите правило запросом в обход UI. Это проверяет перенос, а не запоминание исходных полей.

В `practice/middle/w11-workshop-ex1/notes.md` сохраните контракт, путь Java-проекта, команды, таблицу статусов, пару запрос/ответ без cookie/token, ID исправления и известные ограничения. Если реальный backend пока не подключён, отметьте практикум незавершённым; UI на fake можно сохранить как промежуточное свидетельство.

## Критерии ручной проверки

Полный маршрут выполняется через настоящий Java HTTP; version предотвращает потерянное обновление; 409/422 сохраняют draft; сервер запрещает чужую запись и запрос без CSRF; новое правило проверено отдельно. Жёсткие условия — авторизация и корректность записи. Недоказанные условия не компенсируются красивым UI или числом unit-тестов. Защита включает объяснение одной альтернативы и одного ограничения хранения/сессий.
