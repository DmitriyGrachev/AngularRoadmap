# Браузерная безопасность: сессия, CSRF и граница полномочий

180 минут: 40 на модель угроз, 35 на разбор, 75 на локальную практику и 30 на проверку. Нужна [конкурентная запись](/lessons/w11-02). Результат — объяснение, какие гарантии даёт браузер, какие Angular, а какие обязан обеспечить Java API.

## Три разные задачи

Аутентификация отвечает, кто действует; авторизация — разрешено ли ему действие над конкретной записью. Скрытая кнопка и route guard улучшают интерфейс, но не мешают отправить HTTP напрямую. Сервер проверяет пользователя и доступ к объекту на каждом защищённом запросе. Поле ownerId, пришедшее из браузера, не подтверждает принадлежность записи. Клиентское правило полезно для UX, однако его нельзя использовать как единственный контроль записи. [Angular guards](https://angular.dev/guide/routing/route-guards).

При cookie-сессии браузер отправляет cookie по правилам origin/domain/path/SameSite, а Java восстанавливает пользователя. HttpOnly ограничивает чтение cookie скриптом; Secure ограничивает отправку защищённым транспортом. Эти флаги не превращают приложение в защищённое от XSS: вредный скрипт внутри origin способен выполнять действия от имени пользователя, даже не читая cookie. В локальной HTTP-лаборатории настройка Secure отличается от production HTTPS; это нужно записать, а не выдать лабораторию за конфигурацию развёртывания.

CSRF использует автоматическое прикладывание браузером учётных данных к запросу. Защита unsafe-методов должна проверяться сервером. Angular может брать XSRF token из доступной JavaScript cookie и передавать его заголовком при подходящих запросах; это отдельная cookie от HttpOnly-сессии. Клиентская часть без серверного сравнения не защищает. Не отключайте CSRF только потому, что первый POST дал 403. Для Spring Security SPA важны создание/обновление токена после входа и выхода, а также согласование cookie/header имён. [Angular security](https://angular.dev/best-practices/security), [Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html).

## Origin, proxy и утечка заголовков

В учебном трекере `/api` проксируется на Java: браузер обращается к origin Angular dev server. Это удобная локальная схема, но proxy не является авторизацией. При другом origin понадобятся отдельно продуманная CORS-политика и credentials; успешный preflight не означает право изменить чужую запись. CORS регулирует доступ браузерного JavaScript к cross-origin ответам, а не заменяет серверный контроль доступа или CSRF.

Разберите функцию ограничения области interceptor. Это нейтральный пример выбора адреса; сам токен здесь не создаётся и не хранится:

```ts
function isOwnApi(raw: string, base: string): boolean {
  const origin = new URL(base).origin;
  const target = new URL(raw, base);
  return target.origin === origin &&
    (target.pathname === '/api' || target.pathname.startsWith('/api/'));
}

const base = 'https://desk.example/requests';
console.log(isOwnApi('/api/issues/42', base));             // true
console.log(isOwnApi('https://files.example/api', base)); // false
console.log(isOwnApi('/api-archive', base));              // false
console.log(isOwnApi('//elsewhere.example/api', base));  // false
```

Проверка `url.includes('/api')` допустила бы посторонний host; проверка `startsWith('/api')` приняла бы другой путь. Пример показывает нормализацию URL, а не универсальную security-policy: redirect, доверенные поддомены и deployment base path требуют собственного контракта. Не добавляйте Authorization к каждому запросу приложения автоматически. Cookie-сессия в этом уроке вообще не требует переносить bearer token в localStorage.

## XSS и данные пользователя

Название заявки выводите интерполяцией `{{ issue.title }}`. Для обычного текста не нужны innerHTML и `bypassSecurityTrustHtml`. Удалять только `<script>` недостаточно: HTML имеет другие исполняемые контексты. Для действительно необходимого rich text нужна отдельная договорённость о допустимом формате и обработке на границе. CSP и Trusted Types могут усилить защиту, но не исправляют произвольное доверие опасному содержимому. Ошибки сервера также считаются недоверенными данными; безопаснее показывать своё сообщение по известному коду. [Angular security model](https://angular.dev/best-practices/security).

Для Java-разработчика полезна аналогия с проверкой прав в service/controller: Angular guard напоминает раннюю UX-проверку, а не Spring Security filter chain. Есть и существенное отличие: код frontend полностью доступен клиенту. Секрет, положенный в environment или bundle, перестаёт быть серверным секретом независимо от имени переменной.

Затем проследите путь title до DOM и продемонстрируйте безопасный вывод строки `<img src=x onerror=alert(1)>` именно как текста; не вставляйте её в консоль как исполняемый код.

Для имеющегося или учебного interceptor добавьте тест области адресов на приведённых случаях. Если interceptor не нужен, оставьте функцию политики и обоснование, не создавайте token plumbing ради упражнения. Проверьте реакцию формы на 401 и 403 без потери draft. В Java baseline их можно вызвать `scenario=unauthorized` и `scenario=forbidden`; это лишь симуляции статусов. В workplace этих HTTP-сценариев нет — используйте явный fake в тесте компонента.

## Критерии ручной проверки

Названы реальные границы защиты; текст выводится безопасно; политика URL не принимает похожий host/path; 401/403 не стирают draft; симуляция отделена от доказанного серверного поведения. Самостоятельное выполнение включает новый обходной сценарий и прогноз его результата. Ошибочное утверждение «guard защищает API» требует повторения урока независимо от остальных баллов.
