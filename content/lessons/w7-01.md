# Асинхронность: ограничить работу, сохранить порядок, пережить отказ

180 минут: 40 на модель исполнения, 25 на пример, 85 на упражнение и 30 на новые данные. Нужен [практикум первого этапа](/lessons/w6-workshop). Результат: вы реализуете ограниченный запуск асинхронных операций и доказываете его поведение при ошибке.

## Почему быстрый код перегружает систему

Пользователь выделяет двести строк и просит загрузить детали. Выражение `Promise.all(ids.map(load))` выглядит компактно, но вызовы `load` происходят сразу при выполнении map. `Promise.all` получает уже начатые операции и собирает результаты. Он не является пулом и не знает лимита вашего API. Даже если браузер ограничит соединения, клиент уже создал работу, удерживает объекты и может нагрузить сервер. Требуется управлять моментом запуска, поэтому на вход ограничителя передают данные и функцию worker, а не массив готовых Promise.

В обычном JavaScript-контексте синхронный код выполняется последовательно. После завершения текущего стека продолжения Promise выполняются как microtasks. Таймер лишь планирует callback не раньше указанного времени; точное время зависит от занятости среды. `await` приостанавливает конкретную async-функцию, а не весь браузер. Тяжёлый синхронный цикл внутри worker всё равно блокирует интерфейс. Параллельное ожидание сети не превращает вычисления JavaScript в многопоточные.

Полезно различать три порядка: исходные элементы, запуск работы и завершение. При лимите два первые два элемента запускаются сразу, третий ждёт свободного места. Второй может закончить раньше первого, освободить слот третьему, но результат должен остаться на исходном индексе. Записывание через `results.push(value)` сохраняет порядок завершения и поэтому нарушает контракт ordered results. Индекс — часть задания, а не техническая деталь реализации.

В Java аналогом управления нагрузкой может быть ограниченный ExecutorService. Но `CompletableFuture.allOf` сам по себе тоже не выбирает размер пула, а JS worker в этом уроке вообще не означает Web Worker. Здесь один поток управляет несколькими ожидаемыми операциями. Полезная аналогия — очередь заданий и число занятых слотов; опасная — предположение, что каждое async-ключевое слово создаёт новый поток.

## Ошибка — это политика остановки

В упражнении первая наблюдаемая ошибка отклоняет общий Promise и запрещает запуск новых элементов. Уже начатые операции могут продолжиться: Promise не имеет встроенной универсальной отмены. Если они читают сеть, прерывание требует отдельного механизма, например поддержанного вызываемым API AbortSignal. Если они уже записали данные на сервере, даже отмена ожидания не является rollback. Поэтому выражение «весь пакет отменён» без уточнения слишком сильное.

Порядок «наблюдаемая ошибка» важен. Два Promise могут завершиться почти одновременно, но callback ошибки ещё не исполнился, когда другой worker освободил слот. Контракт ограничивает запуски после того, как ошибка обработана ограничителем; он не требует предвидеть будущее. Тест должен управлять разрешением и отклонением операций, а не предполагать, что задержка в 10 миллисекунд точно означает определённый порядок на любом компьютере.

У каждой начатой операции должна быть обработка rejection. Если общий результат уже отклонён, вторая ошибка активного worker не должна стать unhandled rejection. Отдельно проверьте синхронный throw из worker: функция может бросить исключение ещё до возврата Promise. Для вызывающего это та же неудача задания. На уровне реализации нельзя считать, что любой worker обязательно возвращает только идеально оформленный Promise.

## Разобранный пример

Сохраните код как `queue-observation.mjs` в собственной временной папке и запустите `node queue-observation.mjs`. Это наблюдение за порядком событий, не готовое решение пула:

```js
const gates = new Map();
const load = id => new Promise(resolve => {
  console.log('start', id);
  gates.set(id, () => resolve(id.toLowerCase()));
});
const result = Promise.all(['A', 'B'].map(load));
gates.get('B')();
gates.get('A')();
console.log('sync end');
console.log(await result);
```

Ожидаются строки `start A`, `start B`, `sync end`, затем массив `['a', 'b']`. Оба запуска произошли до ручного завершения. B завершили первым, но Promise.all вернул значения в порядке входа. Добавьте C в исходный массив: немедленно появится `start C`, что доказывает отсутствие ограничения. В своём пуле при лимите два такой вывод до освобождения слота должен быть невозможен.

Не измеряйте правильность только общим временем. Полностью последовательное решение может проходить проверку максимального количества активных задач, потому что один меньше двух. Оно нарушает полезную часть контракта: свободные слоты должны использоваться. Для двух заблокированных первых задач тест должен увидеть два запуска. Для освобождённого слота — запуск следующего элемента, не ожидающий завершения всего пакета.

## Практика в IDE — middle-01

Откройте `practice/middle/middle-01/README.md`, затем редактируйте `solution.mjs`. Реализуйте экспорт `mapConcurrent(items, limit, worker)`. Он возвращает Promise массива результатов в исходном порядке, вызывает `worker(item, index)`, принимает только положительный целый limit и соблюдает описанную политику отказа. Точные пограничные случаи записаны в README; файл starter служит исходной точкой, авторский ответ открывается после собственной попытки.

Команда из корня: `npm.cmd run learn -- check middle-01`. До запуска составьте таблицу для пяти элементов с лимитом два: какие индексы стартовали, сколько активно, куда записан каждый ответ. Затем реализуйте собственный вариант. Не копируйте полностью Java-пул с потоками и блокировками: здесь достаточно небольшого координирующего состояния. Но каждый изменяемый счётчик должен иметь понятный инвариант, иначе короткая реализация останется хрупкой.

**Новые данные.** Проверьте семь строк при limit=3, завершив их в порядке 2, 0, 4, 1, 6, 3, 5 с учётом фактического запуска. Затем первый активный worker отклоните, а второй позже тоже отклоните. Новые элементы после наблюдаемого отказа не стартуют, необработанной ошибки нет. Отдельно проверьте пустой массив и лимит больше длины: отсутствие работы и избыток разрешённых слотов не должны зависнуть.

## Критерии самопроверки

Зелёный runner подтверждает заданный контракт, но защита требует своими словами объяснить момент запуска, порядок выдачи и предел отмены. Самостоятельный уровень: вы построили управляемый сценарий и нашли дефект неправильного порядка без подсказки. С подсказкой: реализация верна, но инварианты пришлось восстановить вместе. Повторить: решение запускает всё сразу, теряет rejection или не различает завершение ожидания и отмену операции. Производительность оценивайте по активным слотам и поведению, а не обещанию «в N раз быстрее».
