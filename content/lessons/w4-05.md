# Пагинация, URL и проверка HTTP-зависимости

120 минут. Результат: страница результата восстанавливается из URL, а проверка сервиса фиксирует контракт запроса. Нужны [Router](/lessons/w3-05), [поиск](/lessons/w4-04), [первые тесты](/lessons/w2-05).

## Ситуация и прогноз

На экране десять заявок и написано «всего 10». API вернул `total: 47`. Откуда ошибка? UI посчитал текущий массив вместо серверного общего числа. Предскажите количество страниц при size 10: `Math.ceil(47 / 10)` даёт пять, с индексами от нуля до четырёх.

## Источник состояния списка

При серверной пагинации браузер не владеет всем набором. Локальная фильтрация одной загруженной страницы не заменяет серверный q/status: она скроет совпадения на других страницах и даст неверный total. Каждый запрос должен передавать согласованную комбинацию q, status, page и size. Ответ сообщает items именно для этой комбинации.

URL удобно сделать источником состояния списка. Пользовательское действие изменяет query parameters, затем поток queryParamMap читает их, проверяет и запускает запрос. Если одновременно вручную менять signal фильтра и отдельно читать URL, появятся две конкурирующие версии. Определите один путь: действие → URL → проверенные параметры → запрос → отображение.

Параметры URL всегда строки или отсутствие. `Number('x')` даст NaN, `Number('')` — ноль, `parseInt('2oops')` — два. Поэтому для page проверяйте целое неотрицательное значение, а не просто вызывайте функцию преобразования. Size лучше ограничить небольшим согласованным набором или известным диапазоном. Невалидный status возвращайте к безопасному «все», а не передавайте произвольную строку под видом union.

Смена фильтра сбрасывает page в ноль, поскольку размер и состав набора изменились. Переход на соседнюю страницу сохраняет фильтры. Кнопка назад не должна создавать отрицательный номер, а «вперёд» — выходить за последнюю страницу. Если после удаления или изменения данных текущая страница стала пустой, интерфейс должен предложить разумный возврат, а не заявлять, что весь набор исчез.

## Разобранная демонстрация

Полный первый пример: `practice/angular-labs/scripts/w4-05.ts`. Команда из корня `node practice/angular-labs/scripts/w4-05.ts` выводит `2 0 0 0`. Он не является готовым парсером всех параметров трекера; он показывает точную проверку одного параметра.

```ts
export function readPage(value: string | null): number {
  if (value === null || !/^\d+$/.test(value)) return 0;
  const page = Number(value);
  return Number.isSafeInteger(page) ? page : 0;
}
console.log(readPage('2'), readPage('-1'), readPage('2oops'), readPage(null));
// 2 0 0 0
```

Вариация: добавьте очень длинную последовательность цифр. Проверка safe integer предотвращает тихую потерю точности. `readPage('0002')` вернёт два; решите отдельно, нужно ли канонизировать URL, это уже требование представления, а не загрузки.

Для сервиса важна проверка HTTP-контракта без настоящей сети. В Angular TestBed заменяет backend тестовым. Сначала регистрируют `provideHttpClient()`, затем `provideHttpClientTesting()`: второй provider подменяет транспорт первого. `HttpTestingController` находит ожидаемый запрос и позволяет ответить ему через flush. Тест не проверяет доступность Java API, зато точно проверяет URL, метод и использование ответа.

```ts
import { TestBed } from '@angular/core/testing';
import { provideHttpClient, HttpClient } from '@angular/common/http';
import { provideHttpClientTesting, HttpTestingController } from '@angular/common/http/testing';
import { describe, it, expect } from 'vitest';

describe('запрос каталога', () => {
  it('передаёт страницу и читает items', () => {
    TestBed.configureTestingModule({ providers: [
      provideHttpClient(), provideHttpClientTesting(),
    ] });
    const http = TestBed.inject(HttpClient);
    const control = TestBed.inject(HttpTestingController);
    let titles: string[] = [];
    http.get<{ items: string[] }>('/api/books', { params: { page: 2 } })
      .subscribe(page => titles = page.items);
    const request = control.expectOne(r => r.url === '/api/books' && r.params.get('page') === '2');
    expect(request.request.method).toBe('GET');
    request.flush({ items: ['Сети'] });
    expect(titles).toEqual(['Сети']);
    control.verify();
  });
});
```

Полный тест уже находится в `practice/angular-labs/src/demos/http.spec.ts`. Выполните `npm.cmd run practice:labs:test`: ожидаются четыре прошедшие проверки лаборатории, включая этот HTTP-тест. Java API не нужен, ответ даёт test backend. Это пример, а не замена упражнения. Для HTTP 500 вызывают `flush` с status/statusText и проверяют ветку ошибки. Не пишите тест, который сам присваивает ожидаемый результат в обход сервиса: он подтвердит только собственную подготовку.

## Мост от Java

Это похоже на тест controller/service с подменой клиента, но здесь проверяется браузерный исходящий HTTP, а не Spring endpoint. `flush` не выполняет Java-код и не доказывает валидацию backend. Полная проверка требует отдельно пройти сценарий с работающим API. Разделение позволяет быстро локализовать нарушение: параметры клиента, контракт сервера или отображение.

## Критерии ручной проверки

URL воспроизводит список; фильтры сбрасывают страницу; границы не выходят за набор; плохой page безопасно обработан; HTTP-проверка ловит неверный параметр и ошибку; прямое открытие детали работает.
