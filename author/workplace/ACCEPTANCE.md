# Приёмка рабочих тикетов

Материал для проверки **после собственной попытки**. Baseline расположен в `practice/workplace`; он не содержит готовых решений шести тикетов. Здесь допустимы разные реализации, если наблюдаемое поведение совпадает с контрактом. Не оценивайте качество по совпадению имён методов с подсказками.

Общий минимум: `npm run test:workplace`, `npm run build:workplace`, проверка в браузере и краткий отчёт об изменившемся поведении. На PowerShell при необходимости запускайте `npm.cmd`. Прохождение этих существующих тестов доказывает лишь сохранность baseline: новые критерии требуют новых проверок. Наличие галочки в журнале курса не является доказательством освоения.

## ticket-01: сортировка

Ожидаемая граница изменения: нормализация URL, модель запроса, API и контрол списка. Применяйте сортировку к результату filter **до** slice. `filter` уже создаёт новый массив, поэтому допустим и `matching.sort`, если компаратор не изменяет объекты. Запрос с неизвестным sort безопасно принимает newest. Смена sort обнуляет страницу и сохраняет q/status/неизвестные параметры.

Независимая маленькая фикстура: 8 записей `A`…`H`, даты `01, 08, 02, 07, 03, 06, 04, 05`, размер страницы 6. Для newest первая страница `B,D,F,H,G,E`, вторая `C,A`. Для oldest первая `A,C,E,G,H,F`, вторая `D,B`. Две равные даты должны идти по id по возрастанию в обоих режимах. Не вычисляйте expected тем же сортировщиком, который проверяете.

Проверка Router: `/requests?q=VPN&status=open&page=2&campaign=x` → sort=oldest → q/status/campaign сохранены, page первая. Далее, карточка, назад и reload сохраняют sort. Продолжение: неверный sort удаляется через replaceUrl без цикла и без нового шага в истории.

## ticket-02: повтор чтения

Ожидаемая граница: событие повтора входит в тот же жизненный цикл актуального query. `catchError` остаётся внутри операции чтения; внешняя цепочка маршрута не должна завершаться. Новый query отменяет запросы старого. Удобно хранить одно состояние loading/error/page вместо нескольких несогласованных флагов.

Проверки: 503 → повтор → успех; 503 → повтор → 503 → повтор → успех; успех с нулём записей; повтор A → новый запрос B → ответ A не влияет на B. Управляемые Subject в компонентном тесте позволяют проверить порядок ответов без ожидания реального времени. Проверьте состояние **до** ответа B: `finalize` отменённого A не должен выключать его загрузку. URL после ручного повтора не меняется.

Продолжение: старые данные разрешены только для того же нормализованного query. Текст «Обновляем» и запрет действий должны сопровождать устаревший результат. Отказ обновления не превращает устаревшие данные в якобы актуальные.

## ticket-03: форма назначения

Ожидаемая граница: форма, узкий RequestPatch, сообщения ошибок и тесты. API уже умеет проверять status/assignee. Не удаляйте серверную проверку и не принимайте редактирование customer/priority/id/updatedAt. Клиентский валидатор использует trim для темы, но не обязан переписывать значение на каждом вводе.

Проверки: загрузить `SD-101` (open, без исполнителя); выбрать in-progress — пустой assignee невалиден; назначить Анну — PATCH содержит редактируемые поля; успех обновляет блок «Обработка». Сменить обратно на open и очистить исполнителя — допустимо. Тема из пробелов не проходит. Серверный 422 с известным полем показывается рядом с ним; неизвестное поле не исчезает, а попадает в общее сообщение. Изменение одного поля не уничтожает чужие ошибки или клиентские validators.

503 сохраняет весь черновик и dirty; повтор возможен. Два submit во время одного ожидания дают одну запись. Продолжение: зафиксировать payload при отправке; если поля доступны для редактирования, поздние ошибки применять только к тому же отправленному значению. Реально disabled fieldset тоже допустимое доказуемое решение.

## ticket-04: фокус и объявления

Ожидаемая граница: жизненный цикл маршрута и шаблон. Программный фокус на h1 с tabindex=-1 после готовности нового экрана. При смене только query params фокус остаётся в поиске. Для результата нужен стабильный короткий live region, не весь список. Ошибка уже объявляется через alert.

Проверки: Tab до ссылки → Enter → activeElement равен h1; возврат → заголовок списка; поиск → фокус на прежнем контроле; успешный нулевой ответ → сообщение о 0, без старого количества; 404 → понятный заголовок и фокус. Просмотрите ширину 390 px. Автотест DOM не равен проверке скринридера: запишите реально проверенный браузер и скринридер или явно укажите, что последнее не проверено.

Продолжение: хранить последний открытый id как навигационный контекст, после загрузки списка искать существующую ссылку и фокусировать её. Если её нет (например, статус изменён и запись ушла из фильтра), использовать h1. Не оставлять фокус на удалённом узле.

## ticket-05: массовое закрытие

Ожидаемая граница: Set id текущей страницы, действия выбора, результаты отдельных PATCH, обновление списка. Нативные checkbox с label достаточны; не добавляйте ручной Space поверх браузерного поведения. Выбор страницы должен учитывать disabled/closed записи и indeterminate.

Проверки: выбрать два id → закрыть → оба сохранены; одна операция 503, другая успех → два честных результата. Каждый внутренний запрос должен превратить успех/ошибку в значение, чтобы общий сбор результатов не потерял частичный успех. `forkJoin` без обработки отдельных ошибок не даёт транзакционность. После операции перечитайте список и проверьте исчезновение закрытых записей из open, а также уменьшение последней страницы. Изменение query очищает выбор; сохранённые, но невидимые id не отправляются.

Продолжение: повторить только сохранённый набор ошибок последней операции. Новый выбор и текущие фильтры не расширяют этот набор. Тест: два id, один успех → изменить фильтр → повтор → только ошибочный id отправлен; успешный не отправляется повторно.

## ticket-06: несохранённые данные

Ожидаемая граница: CanDeactivate на маршруте карточки и ответ компонента о состоянии формы. Начальный reset и reset после успешного PATCH дают pristine; ошибка оставляет dirty. Проверка saving должна иметь ясное сообщение и блокировать переход до завершения.

Проверки через Router: начальная загрузка → уход без вопроса; изменение → confirm=false → URL и черновик сохраняются; confirm=true → переход разрешён; 503 → предупреждение остаётся; успех → предупреждения нет; saving → переход блокируется. Проверьте и ссылку, и верхнюю навигацию, и историю браузера. Только обработчик click одной кнопки не выполняет требование. Закрытие вкладки вне Router не входит в этот тикет.

Продолжение: dirty — история взаимодействия, а не доказательство отличия данных. Сравнивайте нормализованный редактируемый снимок с последним подтверждённым снимком. Сценарий «изменить → вернуть значение» не должен предупреждать. Определите одинаковые правила trim на сравнении, валидации и сохранении.

## Ключ к ревью

| ID | Решение | Проверяемый механизм |
| --- | --- | --- |
| review-01 | changes | query params заменяются, фильтры теряются |
| review-02 | changes | внешний catchError завершает наблюдение за маршрутом |
| review-03 | accept | filter уже создал отдельный массив; порядок хранилища не мутирует |
| review-04 | changes | finalize(A) исполняется после внешнего tap(B) |
| review-05 | accept | проверка нормализованной длины совпадает с сервером |
| review-06 | changes | navigate выполняется до next/error и уничтожает компонент |
| review-07 | changes | отдельные PATCH не транзакция; UI и итог ложно обещают общий результат |
| review-08 | accept | нативный checkbox уже имеет семантику и клавиатурное поведение |

Для changes хороший ответ содержит пользовательский эффект, точную последовательность и тест, способный поймать дефект. Для accept — доказательство по данному контексту и проверяемые границы. Разборы в JSON содержат подробные объяснения; это учебный ключ, а не готовые patches для приложения.
