# Оптимистичное состояние, подтверждение и rollback

180 минут: 40 на модель состояний, 35 на последовательности, 80 на реализацию и 25 на проверку. Нужны [ошибки и повтор](/lessons/w11-01). Результат — поздний ответ не перетирает новую операцию, а отказ возвращает последнюю подтверждённую запись.

## Два значения вместо одной переменной

Оптимистичный интерфейс показывает ожидаемый результат до ответа сервера. Это уменьшает задержку восприятия, но создаёт обязательство объяснить отказ и восстановить согласованное состояние. Храните отдельно confirmed — последний подтверждённый сервером DTO, и value — то, что сейчас отображается. Третья сущность — token активной операции. Pending отвечает, ожидается ли завершение именно этой операции, а не существует ли вообще какой-либо старый HTTP в сети.

После begin новое title берётся из намерения пользователя, остальные поля — из confirmed. Нельзя считать optimistic version подтверждённой. При успехе сервер может вернуть каноническое title и новую version; именно его DTO становится confirmed. При отказе возвращается последняя confirmed, а не initial со времени открытия страницы. Иначе после успешного изменения A неудачное изменение B неожиданно откатит пользователя в состояние до A.

Angular signal хранит наблюдаемое значение; сам по себе он не знает ни requestId, ни семантику подтверждения. Замена объекта через set позволяет явно показать новое состояние. Readonly signal не делает вложенный объект неизменяемым, поэтому используйте независимые снимки на входе/ответе и не делитесь mutable DTO с внешним кодом. В этом упражнении DTO плоский, shallow copy достаточен; для вложенного плана политика копирования должна охватывать строки. [Angular Signals](https://angular.dev/guide/signals).

## Request ID не равен серверной версии

Request ID упорядочивает операции внутри конкретного store. Server version обозначает состояние записи, которое видел клиент, и участвует в серверной проверке записи. В middle-10 последнее begin заменяет активную операцию. Ответ старого requestId игнорируется даже при большой version: это правило применения результата, не доказательство отсутствия серверного commit. Реальная интеграция после таких ситуаций требует отдельного reconciliation через GET/конфликт.

Для серверной защиты Java может использовать JPA `@Version` или атомарный compare-and-set. Проверка «прочитать version, затем записать» без атомарности допускает гонку между двумя клиентами. Для HTTP возможно использовать If-Match/ETag либо ожидаемую version в DTO; важно, чтобы сервер отвергал stale значение. Клиентская фильтрация ответов не выполняет эту роль. [Jakarta Version](https://jakarta.ee/specifications/persistence/3.2/apidocs/jakarta.persistence/jakarta/persistence/Version.html), [HTTP conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html).

## Разобранная последовательность

Этот пример использует интерфейс упражнения. После собственной реализации выполните его в локальном scratch или перенесите в тест; пока предскажите каждый вывод:

```ts
const store = createOptimistic({ id: 'P-8', title: 'Исходное', version: 2 });
const first = store.begin('Первое');
const second = store.begin('Второе');
store.resolve(first, { id: 'P-8', title: 'Первое', version: 3 });
console.log(store.value().title, store.pending()); // Второе, true
store.resolve(second, { id: 'P-8', title: 'Второе!', version: 4 });
console.log(store.value().title, store.pending()); // Второе!, false
const third = store.begin('Третье');
console.log(third.expectedVersion);              // 4
store.reject(third);
console.log(store.value()); // { id:'P-8', title:'Второе!', version:4 }
```

Поздний reject(first) после этого ничего не меняет. Повторный resolve(second) тоже не должен снова применить старое состояние: завершённый token уже не активен. Ответ с id='P-9', version=4, дробной version или NaN считается неприемлемым и не меняет ни value, ни pending. Это консервативный контракт лаборатории; в продукте adapter должен превратить некорректный ответ в явный protocol error и завершить ожидание по выбранной политике, а не оставить пользователя навсегда в saving.

Предположим, first действительно записался на сервере, second конфликтовал. После reject(second) локальный confirmed всё ещё version 2, потому что старый ответ был сознательно проигнорирован. Это известное ограничение модели latest-wins. Оно показывает, почему для важной записи часто проще сериализовать команды или блокировать повторный submit, а не пытаться вывести все серверные события из одного signal.

## Аналогия с Java и выбор UX

Rollback здесь — восстановление клиентского снимка, а не откат уже завершённой транзакции базы. Нельзя отменить серверный commit вызовом `value.set(confirmed)`. Если действие финансовое, необратимое или имеет сложные последствия, подтверждённый UX с явным ожиданием может быть правильнее optimistic. Для лёгкого изменения title схема подходит, пока пользователь видит состояние отправки и имеет путь восстановления.

Для draft формы иногда не подходит даже rollback UI: пользователь мог ввести новый текст, который не обязан исчезать при отказе. Тогда store отображения и draft редактора разделяют. В этой лаборатории value является optimistic представлением записи, а не единственным хранилищем текста формы. Практикум недели 11 проверяет обе части вместе.

## Практика в IDE — middle-10

В `practice/middle/middle-10/solution.mjs` реализуйте `createOptimistic(initial)`. Верните настоящие Angular Signals `value`, `pending` и методы `begin(title)`, `resolve(token, server)`, `reject(token)`. Начальная version корректна и является неотрицательным safe integer. Begin выдаёт уникальный возрастающий requestId, expectedVersion из confirmed и title. Resolve принимает только активный requestId, тот же entity id и safe integer version строго больше confirmed. Reject действует только на активный token. Снимки initial/server не должны делить mutable объект со store.

Запустите `npm.cmd run learn -- check middle-10`. Сначала проверьте свой прогноз четырёх последовательностей, затем исправляйте код. Не переписывайте starter и авторские ответы: они нужны для воспроизводимой оценки. Grader не запускает Java и не подтверждает серверное optimistic locking.

## Новые данные и критерии

Начните с version 9, подтвердите 11, начните следующую команду, затем получите stale success 10 и чужой id с version 99. Ожидается сохранение текущей optimistic операции. После корректного reject вернётся confirmed 11. Измените внешний объект server после успешного resolve — store не меняется. Объясните, почему глобально большая server version не разрешает применить чужой ID.

## Критерии самопроверки
