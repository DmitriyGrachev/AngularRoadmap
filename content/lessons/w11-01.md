# API-контракт, Problem Details и обоснованный повтор

180 минут: 40 на механизм, 30 на пример, 80 на реализацию и 30 на новые случаи. Нужен [динамический редактор](/lessons/w10-workshop). Результат — безопасное сообщение UI и явная политика, когда допустимо предложить повтор запроса.

## Ошибка имеет несколько слоёв

Сетевой сбой, HTTP-статус и доменная ошибка — разные сведения. HTTP 409 сообщает о конфликте, а конкретный type/code объясняет, какой конфликт ожидает продукт. Body может отсутствовать, оказаться HTML от proxy или содержать поля другой версии. Поэтому граница API сначала получает unknown, проверяет форму данных и только затем строит прикладной результат. Generic `http.get<T>()` не выполняет runtime-проверку T. [Angular HTTP](https://angular.dev/guide/http/making-requests).

Problem Details задаёт стандартные поля type, title, status, detail, instance и допускает расширения. Spring может отдавать такой ответ через ProblemDetail. Но наличие стандартного envelope не делает detail безопасным текстом для пользователя: там может быть техническая информация, непредусмотренный язык или присланный контент. Для UI держите собственное отображение известных статусов/кодов; техническую диагностику связывайте через безопасный requestId. Не вставляйте ответ через innerHTML. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html), [Spring error responses](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html).

В реальном transport адаптере основной HTTP-статус берётся из ответа, а не слепо из поля body.status. Их несогласованность — нарушение контракта, а не повод проигнорировать HTTP 403. Чистая функция упражнения получает уже выбранный status в объекте problem и не умеет сама проверить HTTP. Это важная граница её доказательства.

## Повтор может выполнить запись ещё раз

Retry заново подписывается на источник. Для cold HttpClient Observable это новая попытка HTTP, а при мутации — потенциально новая серверная работа. Timeout не доказывает, что сервер ничего не сохранил: он мог завершить commit и потерять ответ. Поэтому правило «любая ошибка → retry(3)» опасно для записи. Даже метод PUT с идемпотентной семантикой не разрешает бесконечные автоматические повторы без анализа конкретного API, версии и побочных эффектов. [RxJS retry](https://rxjs.dev/api/operators/retry), [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html).

Упражнение выбирает более консервативную прикладную политику: повтор разрешён только GET, HEAD, OPTIONS и только при статусах 0, 429, 502, 503, 504. Это не исчерпывающая классификация HTTP-методов. Записи можно повторять по отдельному доказанному контракту, например с ключом идемпотентности и серверным хранением результата, но этот механизм здесь не реализован. Сам canRetry также не запускает таймер и не ограничивает число попыток.

В приложении дополнительно учитывайте Retry-After, верхнюю границу попыток, задержку и отмену при уходе со страницы. Для 401 нужен путь восстановления входа, для 403 — объяснение прав, для 409 — согласование версий, для 400 — исправление данных. Нажатие общей кнопки «Повторить» без изменения условий обычно не решает эти ошибки.

## Разбор безопасного результата

Ниже пример потребления будущего mapper; он не содержит таблицу его реализации:

```ts
const readFailure = presentProblem(
  { status: 503, detail: '<b>internal host=db-7</b>' }, 'GET');
console.log(readFailure);
// { message: 'Сервис временно недоступен', canRetry: true }

const writeFailure = presentProblem({ status: 503 }, 'POST');
console.log(writeFailure.canRetry); // false

const malformed = presentProblem({ status: '503' }, 'GET');
console.log(malformed);
// { message: 'Не удалось выполнить запрос', canRetry: false }
```

Ожидаемое различие основано на типе status и методе, а не на detail. Строка `'503'` не приводится к числу: отсутствие строгого контракта нужно заметить. Status 0 — специальный клиентский сигнал отсутствия полученного HTTP-ответа, а не настоящий HTTP status code. Пропущенный status нельзя превращать в 0 через `Number(null)`, иначе ошибочный payload будет назван сетевым сбоем и предложит повтор.

Для Java-разработчика mapper похож на перевод исключений в public API response. Но frontend делает ещё один перевод — из transport результата в состояние интерфейса. Это разные границы; серверный ExceptionHandler не знает, сохранён ли draft и есть ли у пользователя действие «войти заново». Поэтому не переносите UI-навигацию в общий interceptor только ради удобства reuse.

## Практика в IDE — middle-09

Редактируйте `practice/middle/middle-09/solution.mjs`, экспорт `presentProblem(problem, method)`. Результат ровно `{message, canRetry}`. Признаются только целые числовые status. Для 0 используйте «Нет соединения», 400 — «Проверьте данные», 401 — «Войдите в систему», 403 — «Недостаточно прав», 404 — «Объект не найден», 409 — «Данные изменились; обновите экран», 429 — «Слишком много запросов», 500–599 — «Сервис временно недоступен», остальные/неизвестные — «Не удалось выполнить запрос».

Method сравнивается строго: только uppercase GET/HEAD/OPTIONS попадают в разрешённую группу. Никакие title/detail/HTML не отражаются в message. Точное правило retry приведено выше и в README. Запустите `npm.cmd run learn -- check middle-09`. Эта проверка не делает сеть, не тестирует Spring ExceptionHandler и не доказывает идемпотентность API.

## Критерии самопроверки

middle-09 проходит; неизвестный вход имеет безопасный fallback; сообщения не раскрывают payload; повтор зависит от метода и выбранного статуса. Без подсказки объясните неопределённый исход записи после timeout и назовите дополнительный серверный контракт, который сделал бы повтор допустимым.
