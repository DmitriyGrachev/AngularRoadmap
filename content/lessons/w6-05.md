# Завершить изменение и подготовить его к просмотру

120 минут. Результат: фильтр приоритета завершён, проверен по требованиям и объяснён коротким описанием. Нужен [первый сеанс самостоятельной задачи](/lessons/w6-04).

## Ситуация и прогноз

Фильтр работает после одного нажатия. Достаточно ли этого для коллеги, который откроет прямую ссылку в новой вкладке? Предскажите поведение с пустым параметром, неизвестным приоритетом, Back, последней страницей и недоступным API. Самопроверка должна выйти за пределы последовательности, которую вы использовали при разработке.

## Вернитесь к требованию

Откройте собственные критерии из прошлого занятия. Для каждого назовите конкретное наблюдение и способ проверки. Выбор HIGH должен появиться в URL и запросе; новая вкладка должна восстановить select; смена priority с page=3 должна запросить page=0; сочетание с q/status должно сохранить все параметры. Если критерия нет в списке, добавьте его до объявления готовности.

Очистка фильтра означает отсутствие ограничения по priority, а не строку `ALL`, переданную API как будто это допустимый enum. Удалите query-параметр согласованным способом и восстановите UI «Все». Пустое значение и неизвестная строка требуют определённого поведения. При нормализации URL избегайте бесконечного navigate → queryParamMap → navigate: сравнивайте, действительно ли нужна канонизация.

Browser Back и Forward проверяют, кто владеет состоянием. Если select обновляется только обработчиком click, история изменит URL, но не поле. Если HTTP слушает signal, а URL меняется отдельно, возможен ещё один разрыв. Один путь URL → нормализованное состояние → запрос упрощает доказательство согласованности, хотя не освобождает от проверки.

## Нейтральная демонстрация полезной матрицы

Полный файл: `practice/angular-labs/scripts/w6-05.ts`. Команда из корня `node practice/angular-labs/scripts/w6-05.ts` завершается без вывода, если три assertion верны; нарушенное условие выведет `Assertion failed`. Браузер и Java API не нужны. Для каталога книг матрица показывает независимые входы, а не полное решение трекера.

```ts
const cases = [
  { availability: null, expected: 'ALL' },
  { availability: 'AVAILABLE', expected: 'AVAILABLE' },
  { availability: 'unknown', expected: 'ALL' },
];
function normalizeAvailability(value: string | null) {
  return value === 'AVAILABLE' || value === 'BORROWED' ? value : 'ALL';
}
for (const item of cases) {
  const actual = normalizeAvailability(item.availability);
  console.assert(actual === item.expected, 'Неверная нормализация', item);
}
```

Отсутствие сообщения означает только прохождение этих трёх условий. Оно не доказывает HTTP и доступность select. Вариация: добавьте BORROWED и пустую строку. Затем отдельно проверьте переход состояния page. Разделение проверок позволяет понять, какой именно контракт нарушен, вместо одного гигантского сценария «всё работает».

## Доступность входит в готовность

У select должна быть связанная label, видимый фокус и возможность выбора клавиатурой. Изменившийся результат должен иметь понятную подпись; пустой набор объясняет, что можно изменить фильтры. Не прячьте сообщение об ошибке только в Console. На узком экране панель фильтров не должна перекрывать кнопку перехода и текст состояния.

Проверьте отсутствие скрытой зависимости от цвета: HIGH может иметь цветной badge, но рядом нужна текстовая подпись. Счётчик должен объяснять, относится он к фильтрованному набору или всем данным. Серверный total уже учитывает фильтры, поэтому подпись «всего в системе» для него неверна.

## Прочитайте собственный diff

Посмотрите только изменённые строки и связанный код. Нет ли дублированного поля состояния, неиспользуемых imports, старого TODO уже завершённой части, временных логов и `as any`? Не удаляйте последующие учебные TODO и не форматируйте весь проект без нужды: лишние изменения затрудняют просмотр конкретной задачи. Но связанный неправильный caller обязательно исправьте.

Короткое описание изменения должно говорить о поведении: «Фильтр приоритета передаётся в API, хранится в URL и сбрасывает страницу при изменении. Проверены прямой URL, сочетание с поиском и ошибка API». Не пишите «добавлены файлы», если это не объясняет результат. Отдельно назовите реальное ограничение, если оно осталось; не выдавайте непроверенный случай за пройденный.

## Мост от Java

Как и перед code review Java-задачи, важны контракт и регрессии. Но у браузерного изменения есть ещё история навигации, фокус и размеры экрана. Unit-тест parser не проверяет, можно ли попасть на select клавишей Tab. Ручной сценарий не проверяет все плохие входы функции. Эти проверки дополняют друг друга и имеют честные границы.

## Проверка понимания

1. Что действительно доказывает зелёный parser-тест?
2. Почему Back выявляет двойное владение состоянием?
3. Как обозначить total после фильтрации?
4. Какие изменения diff мешают оценить маленькую задачу?

Новая вариация: пользователь открывает сохранённый URL с priority после изменения серверного набора. Объясните, почему page/total нужно читать заново, а не считать постоянными.
