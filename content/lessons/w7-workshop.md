# Практикум: устойчивый клиентский модуль

360 минут: 40 на контракт, 160 на реализацию, 90 на проверку, 40 на новое требование и 30 на защиту. Предыдущий шаг — [браузер и доступность](/lessons/w7-03). Вы соедините ограничение параллелизма, проверку данных и доступный экран в одну пользовательскую функцию.

## Требование продукта

В учебном трекере пользователь выбирает от одной до восьми заявок и открывает сравнительную сводку. Для каждого ID загружаются детали; одновременно выполняются не более трёх чтений. Строки отображаются в порядке выбора. Один отказ не уничтожает успешно загруженные строки. Для ошибочной строки доступен повтор, не перезагружающий остальные. Во время работы видны число завершённых чтений и результат по каждой заявке. Повторное нажатие запуска не создаёт второй пакет поверх первого.

Это новая функция вашего `practice/issue-tracker`, доработанного в неделях 3–6. Исходная заготовка сама по себе ещё не содержит HTTP: перед практикумом проверьте, что ваш сервис обращается к Java API и умеет читать одну заявку по ID. Запуски из корня: `npm.cmd run practice:api` и `npm.cmd run practice:angular`; адрес интерфейса `http://127.0.0.1:4302`. Если базовый трекер ещё не закончен, завершите его либо сначала выполните функцию на отдельном интерфейсе над вашим сервисом. Авторский пример не копируйте поверх своей работы.

## Зафиксируйте решения до реализации

Определите, откуда берётся порядок ID, как удаляются повторы, где проверяется допустимость ответа и что считается завершением строки. У состояния пакета должны различаться ожидание слота, загрузка, успех и ошибка. Единственный boolean loading не объясняет, почему две строки готовы, одна ошибочна, а остальные ещё ожидают. При этом отдельная машина состояний для каждой иконки не нужна: выберите минимальную модель, выражающую требование.

Политика частичного успеха задаёт границу ошибки. Если одна деталь недоступна, пакет продолжает чтение остальных. Однако ошибку программирования в собственном отображении не следует маскировать как «сервер временно недоступен». На входе разбирайте неизвестный ответ, а ошибки транспорта и формы ответа превращайте в разные диагностические категории. Пользователю достаточно понятной подписи и действия; в техническом отчёте нужны ID запроса и причина без приватных данных.

Не начинайте все Promise заранее. Ограничитель управляет запуском функций чтения, а не количеством await над уже начатыми операциями. Передавать ему массив готовых Promise поздно. Если используется RxJS, явно задайте ограничение concurrency и отдельно восстановите исходный порядок результатов. Порядок прихода ответа и порядок представления — два независимых решения. Повтор строки должен заменить её состояние, не дописать дубликат в конец.

Сравнение с Java помогает только частично. Ограничитель похож на пул исполнителей, но JavaScript callback не получает отдельный вычислительный поток. Набор UI-переходов похож на агрегат, но браузер не обеспечивает транзакционный rollback для уже выполненного серверного действия. В этом практикуме выполняются чтения. Добавление массовой записи потребовало бы отдельной политики идемпотентности, конфликтов и неизвестного результата операции.

## Разобранный пример протокола

Следующий самостоятельный Node-пример показывает, почему пустой ответ и ошибка — разные строки результата. Сохраните его в собственной временной папке как `packet-demo.mjs` и выполните `node packet-demo.mjs`. Он не является реализацией ограничителя и не обращается к API.

```js
const received = [
  { id: 'B', kind: 'error', message: 'Недоступно' },
  { id: 'C', kind: 'ready', title: '' },
  { id: 'A', kind: 'ready', title: 'VPN' },
];
const byId = new Map(received.map(row => [row.id, row]));
for (const id of ['A', 'B', 'C']) {
  const row = byId.get(id);
  console.log(id, row.kind === 'error' ? 'Повторить' : row.title || 'Без названия');
}
```

Ожидаются `A VPN`, `B Повторить`, `C Без названия`. Не допускайте превращения ошибки B в пустую успешную строку. В настоящем модуле пустое название может нарушать DTO-контракт и тогда станет отдельной ошибкой данных; пример намеренно принимает уже проверенную модель представления. Объясните, на каком слое вы приняли политику и почему UI не должен повторно гадать о форме JSON.

## Практика в IDE — w7-workshop-ex1

Откройте `practice/middle/w7-workshop-ex1/README.md` и заполните прогноз в `notes.md`. Разрешённые точки изменения — компоненты, модели, сервис и проверки вашего трекера. Для теста контролируйте завершение чтений вручную: запрос C отвечает раньше A, запрос B получает ошибку, четвёртый запрос не стартует до освобождения слота. Таймеры в тесте допустимы только когда сами таймеры являются предметом проверки; управляемые ответы дают более надёжное доказательство ограничения.

Разработайте интерфейс выбора самостоятельно: чекбоксы, отдельный список выбранного или компактная форма ID. Важно сохранить понятные подписи, запрет запуска пустого пакета и объяснение лимита восемь. Нативные кнопки и заголовки здесь достаточны; установка новой UI-библиотеки не требуется. При появлении ошибки не переводите фокус неожиданно. Повтор активируется клавиатурой, а изменение общего прогресса получает спокойное текстовое сообщение. Частые объявления каждой миллисекунды не нужны.

Продемонстрируйте границу отмены. При закрытии сводки старые ответы не должны переписать новую открытую сводку. Допустимо отменить реальные чтения через их поддерживаемый механизм либо игнорировать результат устаревшего поколения с документированным ограничением. Простое присваивание `loading = false` не отменяет работу. В отчёте различайте «перестал показывать» и «прервал подписку/запрос», подтверждая последнее наблюдаемым teardown либо отменой в Network.

<details><summary>Подсказка 1 — контракт</summary>Нарисуйте четыре состояния одной строки и возможные переходы. Затем добавьте номер пакета: он отвечает на вопрос, относится ли ответ к открытому экрану.</details>
<details><summary>Подсказка 2 — проверка лимита</summary>Пусть fake API хранит количество активных чтений. Завершите второй запрос раньше первого и проверьте запуск ровно одного нового.</details>
<details><summary>Подсказка 3 — повтор</summary>Повтор использует тот же ID и место строки. Успех обновляет существующую запись; ошибка сохраняет возможность ещё одной попытки.</details>

**Новые данные.** Первый пакет содержит три существующих ID, один неизвестный и повтор существующего ID. Сначала примените свою записанную политику повторов. Затем откройте другой пакет до окончания первого. Старые строки не должны попасть в новый результат. Наконец повторите неизвестную строку после исправления ID через предусмотренное действие; проверьте, что успешные строки не загружались заново. Не меняйте серверный seed, чтобы незаметно подогнать сценарий.

## Критерии защиты

Обязательны ограничение трёх активных чтений, сохранение порядка, частичная ошибка, повтор одной строки и защита нового пакета от старых ответов. Доказательство включает один тест конкуренции и одну ручную проверку клавиатуры на узком экране. По каждому пункту отметьте самостоятельное выполнение, помощь или повторную попытку. Для сильного результата без подсказки объясните, где именно запускается работа, почему `Promise.all` сам не ограничивает её и какой инвариант защищает номер пакета.

Практикум не проверяет авторизацию, устойчивое серверное хранение или конкурентную запись. Он даёт одно свидетельство самостоятельной frontend-работы. Сохраните краткое описание дефекта, исправление, проверку и оставшийся предел решения; оно понадобится для итоговой защиты, где правильный результат на знакомых данных ещё потребуется перенести на новое требование.
