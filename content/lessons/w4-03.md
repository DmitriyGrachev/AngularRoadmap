# Состояния загрузки и композиция pipe

120 минут. Результат: ожидание, пустой ответ, ошибка и данные различимы, повтор работает. Нужны [HttpClient и Observable](/lessons/w4-02), [signals](/lessons/w3-03).

## Ситуация и прогноз

После сбоя API индикатор крутится бесконечно. В коде `loading = false` расположен только в успешном callback. Что произойдёт при error? Поток завершится по другому пути. А что произойдёт при уходе со страницы до ответа? Обработка результата вообще не должна изменять уничтоженный интерфейс. Сначала перечислите все способы окончания операции.

## Состояния должны иметь смысл

Минимум для чтения списка — loading, success, empty, error. Пустой набор является успешным ответом, но требует другого текста, чем ошибка. Пользователь должен понимать, стоит ли менять фильтр или повторять соединение. Не показывайте «заявок нет», пока запрос ещё не завершился: это промежуточная ложь, даже если через секунду всё исправится.

Несколько независимых boolean позволяют невозможные комбинации: `loading=true` и `error=true`, либо старые items и сообщение «ничего нет». Union состояния ограничивает варианты типами. Альтернативно можно оставить отдельные signals, если переходы строго согласованы; выбор оправдывается читаемостью. Главное — заранее решить, показываете ли старые данные во время обновления и как обозначаете их актуальность.

`pipe` собирает последовательность операторов над Observable. `map` преобразует каждое значение: например, envelope в список названий. Он не подписывается и не отправляет запрос сам. `catchError` перехватывает ошибку и должен вернуть другой Observable: `of(fallback)` продолжит как значение, `throwError` передаст ошибку дальше. Простое `return []` имеет особый смысл Iterable и может завершиться без ожидаемого next; для одного массива используйте `of([])`.

`finalize` выполняется при завершении, ошибке и отписке. Он подходит для освобождения локального ресурса или снятия флага одной операции. Он не доказывает успех. Навигация «сохранено» внутри finalize была бы ошибкой: она выполнится и после HTTP 500. При нескольких перекрывающихся запросах общий boolean в finalize старой операции способен выключить индикатор новой. Нужно либо исключить перекрытие, либо связывать состояние с актуальной операцией.

## Разобранная демонстрация

Полный файл: `practice/angular-labs/src/demos/w4-03.ts`. Запуск из корня: `npm.cmd run practice:labs`; страница `http://127.0.0.1:4304/w4-03`. Компонент уже подключён, Java API не нужен. Нейтральный пример использует имитацию каталога. Нажатие первой кнопки показывает loading, затем empty; второй — loading, затем error через 400 мс.

```ts
import { Component, DestroyRef, inject, signal } from '@angular/core';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { catchError, map, of, switchMap, throwError, timer } from 'rxjs';

type View = { kind: 'loading' } | { kind: 'empty' }
  | { kind: 'success'; titles: string[] } | { kind: 'error'; message: string };

@Component({
  selector: 'catalog-state-demo', standalone: true,
  template: `
    <button type="button" (click)="load(false)">Пустой каталог</button>
    <button type="button" (click)="load(true)">Сбой</button>
    <p>{{ state().kind }}</p>
  `,
})
export class CatalogStateDemo {
  state = signal<View>({ kind: 'empty' });
  private destroyRef = inject(DestroyRef);
  load(fail: boolean) {
    this.state.set({ kind: 'loading' });
    timer(400).pipe(
      switchMap(() => fail ? throwError(() => new Error('Каталог недоступен')) : of<string[]>([])),
      map(titles => titles.length
        ? ({ kind: 'success', titles } as const)
        : ({ kind: 'empty' } as const)),
      catchError(() => of({ kind: 'error', message: 'Повторите загрузку' } as const)),
      takeUntilDestroyed(this.destroyRef),
    ).subscribe(state => this.state.set(state));
  }
}
```

Этот пример намеренно ограничен одиночным нажатием: две кнопки не моделируют отмену предыдущего запроса. Следующий урок устранит гонки. Здесь важны тип состояния и превращение ошибки в явное состояние, которое действительно получит подписчик. Вариация: замените `of<string[]>([])` на `of(['Сети'])` и дополните шаблон показом titles только в success-ветке.

`DestroyRef` передан явно, потому что `load` вызывается позднее из события и не находится в injection context. Вызов `takeUntilDestroyed()` без аргумента в таком месте неверен. Получение ссылки на уничтожение при создании компонента позволяет использовать её позже безопасно.

Для реального HTTP можно оставить ошибку в error callback и снять `loading` через finalize. Или, как в демонстрации, выразить каждый исход union-значением. Не смешивайте два подхода так, что один путь обновляет state, а другой только скрытый boolean. Выберите одну понятную схему переходов и проверьте её на каждом исходе.

## Мост от Java

`catchError` напоминает catch, но возвращает поток продолжения, а не произвольное значение метода. `finalize` напоминает finally, но относится к жизненному циклу подписки, включая unsubscribe. Поэтому «выполнилось finalize» не означает «пришёл HTTP-ответ». В UI отменённое чтение часто вообще не нуждается в сообщении об ошибке пользователю.

## Проверка понимания

1. Почему empty не равен error?
2. Что обязан вернуть catchError?
3. Когда выполняется finalize без ответа сервера?
4. Почему DestroyRef иногда передают явно?

## Критерии ручной проверки

Наблюдаются все четыре исхода; повтор после ошибки успешен; ожидание завершается; отсутствующая деталь не выглядит сетевым сбоем; подписка связана с жизнью компонента; временные диагностические изменения удалены.
