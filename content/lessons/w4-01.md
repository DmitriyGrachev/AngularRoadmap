# HTTP-контракт и вкладка Network

120 минут. Результат: вы читаете конкретный запрос и отличаете неверный адрес, ответ сервера и ограничение браузера. Нужны [Promise](/lessons/w2-02), [типизация внешних данных](/lessons/w2-04) и [маршруты](/lessons/w3-05).

## Ситуация и прогноз

Java API запущен на порту 8080, Angular — на 4302. В адресной строке API отдаёт JSON, а приложение сообщает об ошибке. Доказывает ли это дефект JSON? Нет: прямой переход и чтение ответа скриптом имеют разные условия безопасности. До запуска выпишите, что хотите проверить: адрес запроса, метод, status, тело и заголовки. Так гипотеза получает наблюдаемый признак.

## Из чего состоит обмен

HTTP-запрос содержит метод, URL, заголовки и иногда тело. GET читает представление ресурса, POST создаёт или выполняет команду, PATCH передаёт частичное изменение. Метод является частью контракта: одинаковый URL с другим методом может дать другой результат или 405. Тело JSON — строковое представление данных; заголовок `Content-Type: application/json` объясняет серверу формат тела.

Ответ содержит числовой status, заголовки и тело. Успешный 200 не означает, что UI правильно понял структуру. Сервер может вернуть `{ items: [...] }`, а компонент ошибочно ожидать массив. Тогда HTTP успешно завершён, но обработка данных неверна. Разделяйте транспорт, контракт и отображение — иначе будете исправлять CSS для ошибки имени поля.

В подготовленном API список доступен как `GET /api/issues`. Query-параметры: `q`, `status`, `priority`, `page`, `size`. Номер страницы начинается с нуля. Ответ — `{ items, total, page, size }`; `total` означает число записей после фильтрации до разбиения на страницы. Деталь — `GET /api/issues/:id`. Значения status: `OPEN`, `IN_PROGRESS`, `DONE`; priority: `LOW`, `MEDIUM`, `HIGH`. ID — строка, createdAt — ISO-дата с часовым поясом.

Контракт записи отличается от контракта чтения. POST принимает `title`, `description`, `priority`, а сервер создаёт ID, дату и начальный статус. PATCH принимает изменяемые `title`, `status`, `priority`; отсутствие поля не равно пустой строке. При 400 тело имеет `message` и `fieldErrors`. Точные ограничения полей читайте в локальной инструкции API; не придумывайте число символов на основе вида поля.

## Origin, CORS и proxy

Origin определяется схемой, хостом и портом. `http://127.0.0.1:4302` и `http://127.0.0.1:8080` — разные origin. CORS — разрешение сервера браузеру предоставить ответ скрипту другого origin. Это не аутентификация и не средство защиты API от прямого вызова. Ошибка CORS часто видна в Console, а в Network можно увидеть preflight OPTIONS или сам запрос без доступного коду ответа.

Dev proxy позволяет браузеру обращаться к относительному `/api`, а сервер разработки пересылает запрос к Java. Для браузера адрес остаётся на 4302. Такая настройка удобна локально; при размещении нужна соответствующая конфигурация сервера либо осознанный CORS. Не добавляйте `Access-Control-Allow-Origin` к заголовкам запроса и не отключайте безопасность браузера: разрешение находится в ответе сервера.

## Разобранная демонстрация

Полный диагностический скрипт: `practice/angular-labs/scripts/w4-01.ts`. Сначала запустите `npm.cmd run practice:api`, затем в другом терминале `node practice/angular-labs/scripts/w4-01.ts`. Ожидаются `200 application/json; charset=utf-8` и `true 0 2` с текущим total. Скрипт использует абсолютный адрес `http://127.0.0.1:8080/api/issues`, потому что Node не имеет базового URL страницы. Для браузерной проверки Network выполните следующий вариант с относительным `/api` в Console трекера: он проходит через dev proxy. Node-скрипт сам по себе не проверяет браузерный CORS.

Запустите два процесса из корня в разных терминалах: `npm.cmd run practice:api` и `npm.cmd run practice:angular`. В Console страницы `http://127.0.0.1:4302` выполните небольшой диагностический пример. Это чтение API для наблюдения, не готовый сервис приложения.

```js
const params = new URLSearchParams({ q: 'сервер', page: '0', size: '2' });
const response = await fetch('/api/issues?' + params);
console.log(response.status, response.headers.get('content-type'));
if (!response.ok) {
  console.log('HTTP-ошибка', await response.text());
} else {
  const page = await response.json();
  console.log(Array.isArray(page.items), page.page, page.size, page.total);
}
```

Ожидается status 200, JSON content type, `true` для массива items и числовые сведения о странице. Конкретный total зависит от набора API. Пустой `items` при редком q — допустимый успешный ответ. `fetch` не отклоняет Promise лишь из-за 404, поэтому проверка `ok` необходима. Это отличается от обработки неуспешного status в Angular HttpClient, где он попадёт в канал ошибки.

Откройте Network, очистите список и повторите вызов. Найдите Request URL с закодированным русским текстом, метод GET, status, Query String Parameters и Preview. Затем запросите `/api/issues/definitely-missing`. Сравните 404 и тело ответа с успешным пустым поиском. Вариация: остановите Java и повторите запрос. Если proxy вернёт свою ошибку, браузер видит HTTP-ответ proxy; если запрос не получил доступного ответа, возможен транспортный сбой. Не называйте оба случая «404» по привычке.

## Мост от Java

DTO с сервера не становится экземпляром Java-класса в браузере. После JSON parsing вы получаете обычный JavaScript-объект, а дата остаётся строкой. TypeScript interface помогает компилятору, но не валидирует ответ автоматически. Также localhost внутри браузера означает компьютер пользователя; адрес backend в контейнере или на сервере может иметь другой смысл.
