# Доставка изменения, наблюдаемость и разбор инцидента

180 минут: 35 на модель доставки, 35 на пример расследования, 80 на практику и 30 на новые условия. Нужен [разбор производительности](/lessons/w12-02). Результат — изменение с воспроизводимыми проверками, понятным откатом и свидетельством исправленного отказа.

## Что доказывает зелёная сборка

Сборка проверяет, что исходники превращаются в bundle, но не что приложение правильно разговаривает с сервером. Unit-тест подтверждает выбранный контракт при заданных условиях. Интеграционный тест проверяет взаимодействие компонентов. Браузерный сценарий показывает пользовательский маршрут и способен заметить неверную кнопку, фокус или URL. Ни один слой не обязан повторять все сценарии другого. Выберите для каждого риска самое дешёвое достаточное наблюдение и одну сквозную проверку главного пути.

Для frontend + Java изменения отдельно важна совместимость доставки. Новый UI может загрузиться при ещё старом API; старая вкладка может продолжить работать после обновления Java. Если добавить обязательное поле в запрос без переходного периода, зелёные проверки только новой пары версий не обнаружат отказ. Сначала расширяйте принимаемый контракт, затем переводите потребителя, затем удаляйте старый путь, когда политика совместимости это допускает. Условная возможность прочитать старый ответ должна быть оговорена явно: нельзя выдумывать version=0 и отправлять незащищённую запись.

CI повторяет команды в чистом окружении с зафиксированными зависимостями. Укажите runtime из проекта и lockfile; не используйте глобально установленный случайный Angular CLI. Для данного курса обязательны `npm.cmd run verify:content`, `npm.cmd run test`, `npm.cmd run build`, а для изменённого учебного приложения — его тест и сборка. На Linux CI используется `npm`, без `.cmd`. Pipeline может быть описан и воспроизведён локально: подключать внешний аккаунт ради этого урока не нужно. [GitHub Actions syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

## Наблюдаемость без лишних данных

Полезное событие связывает действие, исход и время. Минимум для запроса: безопасное имя операции, status, duration, requestId, версия клиента и признак отмены. Не логируйте session cookie, CSRF token, полный текст формы, пароль или тело каждого ответа. Чтобы сопоставить браузер и Java, сервер возвращает requestId, а его журнал содержит тот же идентификатор. Это не означает доверять произвольной строке клиента как управляющей команде или печатать её без ограничений.

Логи отвечают «что произошло с этой операцией», метрики — «как часто и насколько долго», trace — «где прошло время между участками». Для локальной практики достаточно структурированных записей и Network; устанавливать OpenTelemetry collector не требуется. Названия и единицы измерений важнее красивого dashboard. Например, `durationMs: 850` понятнее `time: 850`, а число 409 нужно отделять от 500: ожидаемый конфликт не равен падению сервиса. [OpenTelemetry observability](https://opentelemetry.io/docs/concepts/observability-primer/).

## Разобранный инцидент

Пользователь сообщает: «Нажал сохранить один раз, после ошибки название изменилось дважды». Есть такая последовательность:

```text
10:00:00.010 UI   save clicked, draftRevision=7
10:00:00.018 HTTP PUT /api/plans/PLAN-17, expectedVersion=4, requestId=A
10:00:00.160 JAVA A committed version=5
10:00:00.180 NET  response lost
10:00:01.190 HTTP PUT /api/plans/PLAN-17, expectedVersion=4, requestId=B
10:00:01.230 JAVA B conflict 409
10:00:01.240 UI   reset draft to initial value
```

Из этих данных нельзя заключить, что Java записала дважды: второй запрос конфликтовал. Доказаны потерянный ответ, повторная отправка и неправильный reset формы. Проверьте, откуда пришёл B: generic retry interceptor, вторая подписка на cold HTTP Observable или повторный click? Гипотеза должна иметь различающий эксперимент. Например, временно замените транспорт управляемым fake, выдайте network error и посчитайте подписки; затем отдельно проверьте число click events.

Правка — убрать необоснованный повтор записи из общего пути и сохранить draft при неопределённом исходе. После ошибки предложите явно проверить серверное состояние; не обещайте «ничего не сохранилось». Ожидаемый тест: одна пользовательская команда создаёт одну попытку записи, failure оставляет форму редактируемой, последующий GET показывает version 5, а пользователь решает, как сопоставить её со своим draft. В Java это напоминает расследование повторной транзакции, но добавляется жизненный цикл подписок и состояние браузера.

## Практика в IDE — w12-03-ex1

Используйте интеграцию недели 11, если она готова. Если нет, воспроизведите frontend-часть в `practice/workplace` управляемым fake и честно пометьте отсутствие реального transport/commit. Сделайте точку восстановления и временную учебную ветку/копию. Внесите один контролируемый дефект: повтор записи после network error либо сброс draft на failure. Не оставляйте его в итоговом решении.

В `practice/middle/w12-03-ex1/notes.md` сначала запишите симптом и две конкурирующие гипотезы. Получите наблюдение, различающее их, добавьте тест, который краснеет на дефекте, исправьте причину и повторите тот же сценарий. Добавьте безопасный requestId в пользовательское сообщение/диагностический отчёт, если сервер его предоставляет. Не генерируйте на клиенте «серверный» ID, которого нет в серверном журнале.

Составьте короткий план выпуска: какие команды запускаются, какие версии клиента/сервера совместимы, каким действием откатить frontend и какое поведение сохранится у API. Для изменения схемы базы данных объясните, почему откат bundle сам по себе не откатывает данные. Не выполняйте публикацию: проверяемым результатом здесь служит локальный артефакт и инструкция восстановления.

## Новые условия

Теперь сервер сохранил изменение, но вкладка закрылась до получения ответа. После нового открытия GET показывает version 6. Объясните, какие факты сохранились, что невозможно восстановить из памяти компонента и какие дополнительные продуктовые требования нужны для сохранения draft между сессиями. Не добавляйте localStorage автоматически: в форме могут быть чувствительные данные.

<a id="criteria"></a>
## Критерии ручной проверки

Есть воспроизводимый симптом, проверенная гипотеза, красная/зелёная проверка и безопасная диагностика; новая ошибка не маскируется reset/reload. План доставки учитывает старую вкладку, реальный API и откат. Самостоятельность означает объяснить новую последовательность событий и ограничения свидетельств без угадывания причины по одному статусу.
