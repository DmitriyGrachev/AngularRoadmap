# Отмена, ошибки и события: не дать старой работе управлять экраном

180 минут: 35 на временную модель, 25 на пример, 90 на изменение и 30 на проверку. Нужны [кэш](/lessons/w9-01) и [очередь записи](/lessons/w9-02). Результат: вы различаете состояние и событие, изолируете ошибку одного чтения и привязываете индикатор к актуальному запросу.

## Повтор — событие, фильтр — состояние

Фильтр описывает, какие данные нужны сейчас. Нажатие «Повторить» требует ещё раз выполнить работу с тем же фильтром. Если поток строится только из query params, повторная навигация к тому же URL может ничего не изменить. Это не ошибка Router: состояние действительно осталось прежним. Добавлять случайный timestamp в URL ради повторного запроса означает смешать внутреннее событие с адресом, который пользователь копирует и хранит.

Сохраняйте нормализованное состояние фильтров отдельно от события повторного чтения. Например, поток route-state вместе с reload-trigger может создавать запрос при изменении любого из них. Начальное событие повторного потока обеспечит первое чтение. Конкретная композиция зависит от существующего кода; важно, чтобы повтор использовал текущий фильтр и не создавал новую запись браузерной истории. Не превращайте каждое событие кнопки в ещё один долгоживущий boolean signal, который потом приходится сбрасывать.

Ошибка одного HTTP-чтения должна дать состояние ошибки этого запроса и оставить возможность обработать следующий фильтр. Поэтому catchError располагают внутри переключаемого запроса, если нужна такая политика. Если ошибка завершила внешний поток навигации, изменение URL больше не обновит экран. В UI отсутствие результатов, неизвестный ID и отказ транспорта — разные состояния; одинаковый пустой массив скрывает отличие и лишает пользователя осмысленного действия.

## Отписка не является успешным завершением

SwitchMap отписывает предыдущий внутренний поток перед подпиской на новый. Если это HttpClient, отписка прерывает ожидание HTTP на клиенте; старое значение не должно попасть в текущую цепочку. Если источник реализован вручную и не освобождает ресурс в teardown, работа может продолжить расходовать ресурсы. В Observable-контракте закрытому observer нельзя доставить новое значение, но внешний side effect внутри плохо написанного callback всё ещё может повредить глобальное состояние.

Finalize вызывается при complete, error и unsubscribe. Следовательно, он подходит для освобождения ресурсов, но не для сообщения «успешно сохранено». Общий boolean loading, который каждый запрос сбрасывает в своём finalize, часто создаёт гонку: начало B устанавливает true, отмена A устанавливает false, хотя B ещё работает. Правильнее выдавать loading как часть состояния конкретного внутреннего запроса либо проверять поколение перед изменением общего состояния.

Компонент также должен прекращать принадлежащие ему подписки при уничтожении. AsyncPipe управляет подпиской шаблона; ручной subscribe требует явного владельца времени жизни, например takeUntilDestroyed в подходящем injection context. Не передавайте владение root-сервису случайно ради удобства доступа. Если запись должна продолжаться после ухода со страницы, это отдельное продуктовое решение: требуется место для результата и восстановления состояния, а не просто отсутствие unsubscribe.

Java-аналогия — отмена Future или HTTP-клиента с кооперативной обработкой прерывания. Вы не считаете interrupt доказательством rollback транзакции. Аналогично здесь отмена клиентской подписки не доказывает отмену записи сервером. Для поиска правило latest-wins обычно оправдано: старый результат уже не нужен. Для сохранения оно требует отдельного анализа и часто оказывается неверным.

## Разобранный пример

Сохраните `cancel-demo.mjs` в корне рабочей копии и запустите `node cancel-demo.mjs`. Зависимости RxJS уже установлены:

```js
import { Subject, Observable, switchMap } from 'rxjs';
const requests = new Subject();
const respond = new Map();
const sub = requests.pipe(switchMap(id => new Observable(observer => {
  console.log('start', id);
  respond.set(id, () => observer.next(id));
  return () => console.log('stop', id);
}))).subscribe(id => console.log('result', id));
requests.next('A');
requests.next('B');
respond.get('A')();
respond.get('B')();
sub.unsubscribe();
```

Ожидаются `start A`, `stop A`, `start B`, `result B`, `stop B`. Result A отсутствует, хотя callback ответа вызван вручную. Этот пример не выполняет сеть и не сохраняет данные: он доказывает доставку уведомлений и teardown. Если в respond поместить запись в сторонний массив до observer.next, эта запись произойдёт даже для A. Именно поэтому side effect должен находиться на корректной границе и не обновлять экран обходным путём.

Посмотрите существующий `practice/workplace/src/app/list-page.ts`. Внутренний startWith создаёт loading для каждого запроса, catchError возвращает ошибку того же запроса. Такой объект модели представления проще проверять, чем три независимые подписки, каждая меняющая свой флаг. При расширении сохраните это свойство. Типовая union-модель loading/ready/error ещё точнее запрещает невозможные комбинации, но полный рефакторинг всех файлов ради этого урока не обязателен.

## Практика в IDE — w9-03-ex1

Условия и отчёт находятся в `practice/middle/w9-03-ex1`. В своей версии workplace добавьте доступную кнопку «Повторить» для ошибки списка. Она запускает чтение текущего запроса без изменения адреса. Повтор во время уже активного чтения должен следовать явно выбранной политике: в этом задании кнопка недоступна до окончания попытки, поэтому повтор не создаёт параллельные дубликаты. Изменение фильтра во время загрузки остаётся разрешённым и заменяет актуальное чтение.

Запуск: `npm.cmd run practice:workplace`. Внизу страницы используйте «Следующее чтение списка: 503», затем измените фильтр, чтобы отказ был потреблён. Ожидайте ошибку, нажмите повтор и получите данные с тем же URL. Network здесь не покажет GET: DeskApi использует RxJS-таймеры в памяти. Для доказательства числа чтений примените spy или fake API в компонентном тесте; команды проверки — `npm.cmd run test:workplace` и `npm.cmd run build:workplace`.

## Критерии ручной проверки

Повтор использует текущий запрос, не меняет историю и остаётся возможным после отказа. Старый ответ не заменяет новый, отмена A не скрывает loading B, уничтожение компонента освобождает подписку. Самостоятельная защита объясняет различие события и состояния, место catchError и ограничение отмены. Если проверка опирается только на визуальное ожидание 350 миллисекунд, добавьте управляемый сценарий: редкая гонка может не воспроизводиться вручную каждый раз.
