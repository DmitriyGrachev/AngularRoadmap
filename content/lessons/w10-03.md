# Собственный контрол, CVA и доступный диалог

180 минут: 35 на механизм, 40 на разобранный пример, 75 на практику и 30 на новые сценарии. Нужен [разбор серверных ошибок](/lessons/w10-02). Результат — компонент ввода, который ведёт себя как обычное поле формы, и проверяемая политика фокуса.

## От красивой кнопки к контракту компонента

В приложении могут соседствовать Material/CDK, Bootstrap-обёртки и собственные компоненты. Их внешний вид не определяет, кто владеет значением, disabled, touched и ошибкой. Если обёртка копирует вход в локальное поле, но не принимает последующие изменения родителя, после reset на экране останется старое значение. Если каждый программный write порождает change, появятся повторные события и ложный dirty. Начинайте с этих потоков данных, а не с темы оформления.

ControlValueAccessor связывает Forms API с вашим UI. `writeValue` принимает значение от модели, `registerOnChange` сохраняет callback пользовательского изменения, `registerOnTouched` — callback завершённого взаимодействия, `setDisabledState` отражает доступность. Это разные направления. Обычный native input уже имеет accessor; своя реализация нужна, когда внешний компонент представляет одно логическое значение и прячет внутреннее управление. Для простого подписанного input зачастую достаточно компонента с явными inputs/outputs. [Контракт CVA](https://angular.dev/api/forms/ControlValueAccessor).

Типизированный FormControl родителя не делает интерфейс CVA автоматически типобезопасным. На границе обработайте null и недопустимое значение согласно политике компонента. Не превращайте неизвестный приоритет в HIGH: для критичного выбора это незаметная смена намерения пользователя. Обязательность и серверные ограничения оставьте форме/домену. UI-компонент не должен самостоятельно отправлять PATCH.

## Разбор: выбор уровня важности

Ниже ядро accessor, которое можно поместить в standalone-компонент. Для Angular-подключения добавьте provider `NG_VALUE_ACCESSOR` с `multi: true` и `useExisting: forwardRef(() => PriorityControl)`. Шаблон использует native select с label; CSS может быть собственным. Это пример механизма, не готовый файл упражнения.

```ts
type Priority = 'LOW' | 'MEDIUM' | 'HIGH';

export class PriorityControl {
  value: Priority | null = null;
  disabled = false;
  private change: (value: Priority | null) => void = () => {};
  private touch: () => void = () => {};

  writeValue(value: unknown) {
    this.value = value === 'LOW' || value === 'MEDIUM' || value === 'HIGH'
      ? value : null;
  }
  registerOnChange(fn: (value: Priority | null) => void) { this.change = fn; }
  registerOnTouched(fn: () => void) { this.touch = fn; }
  setDisabledState(disabled: boolean) { this.disabled = disabled; }
  choose(value: Priority) {
    if (this.disabled) return;
    this.value = value;
    this.change(value);
  }
  blur() { this.touch(); }
}
```

При `control.setValue('HIGH')` ожидаются HIGH в UI и ноль callback пользовательского change. Один выбор LOW вызывает change ровно один раз. Blur сообщает touched; показ серверной ошибки сам по себе touched не меняет. После `control.disable()` пользователь не меняет значение ни мышью, ни клавиатурой. Если выберете OnPush и обычные поля, предусмотрите `markForCheck()` после программных записей; альтернативно используйте signals, читаемые шаблоном. Это важнее добавления ещё одного output поверх CVA.

В Java аналогией будет адаптер между интерфейсами, но здесь есть обратные callback и жизненный цикл DOM. Не считайте `writeValue` setter с доменным событием: это путь синхронизации представления. Аналогия с DTO тоже ограничена: контрол дополнительно хранит состояние взаимодействия, которого у DTO нет.

## Фокус и библиотеки

Для модального редактора недостаточно нарисовать overlay и поставить `role="dialog"`. При открытии фокус должен перейти внутрь; Tab и Shift+Tab остаются в модальном контексте; Escape закрывает по выбранной политике; после закрытия фокус возвращается на вызывающую кнопку либо на разумный соседний элемент, если строка удалена. У диалога есть доступное имя. Не задавайте положительные tabindex для перестановки порядка. [WAI-ARIA: dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

Material dialog/CDK предоставляют механизмы overlay и работы с фокусом; Bootstrap-классы сами не доказывают доступность. Обёртка должна сохранять label, disabled, aria-describedby и поведение клавиатуры. Не запускайте два менеджера фокуса над одним диалогом. В этом репозитории Material/CDK/Bootstrap не установлены, поэтому обязательную практику выполните native select и `<dialog>.showModal()`, без новых зависимостей. В рабочем Angular 21-проекте с установленной библиотекой сопоставьте эти обязанности с существующей обёрткой. [CDK accessibility](https://material.angular.dev/cdk/a11y/overview), [Bootstrap accessibility](https://getbootstrap.com/docs/5.3/getting-started/accessibility/), [native dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog).

## Новые данные и объяснение

Проверьте reset в null, два последовательных программных значения, disabled до первого открытия, закрытие Escape, удаление вызывающей строки и ширину 360px. На каждом шаге назовите наблюдаемый результат до запуска. Отдельно объясните, что сломается, если вызвать change внутри writeValue, и почему внешний required не должен исчезать при удалении серверной ошибки.

## Критерии ручной проверки

Два направления синхронизации не создают лишних событий; disabled действует на реальный control; blur выставляет touched; label и ошибка связаны с полем; диалог проходит клавиатурный маршрут и возвращает фокус. В отчёте есть сценарий нового ввода и ограничение выбранного baseline. Самостоятельность подтверждает изменение второго поля без пошаговой подсказки, а не только сходство с демонстрацией.
