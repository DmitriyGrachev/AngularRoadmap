# Поиск: задержка, повтор и отмена старого чтения

120 минут. Результат: быстрый ввод не позволяет старому результату заменить новый. Нужны [состояния загрузки](/lessons/w4-03) и [callback](/lessons/w2-01).

## Ситуация и прогноз

Пользователь набрал «с», затем «сеть». Первый запрос занял 800 мс, второй — 100 мс. Если оба callback просто присваивают список, что будет через 800 мс? Старый результат затрёт актуальный. Ошибка зависит от порядка ответов, поэтому обычный медленный ручной ввод её может не показать.

## События образуют последовательность

Поиск — не один HTTP-запрос, а поток условий поиска. Сначала нормализуем ввод, например убираем пробелы по краям. Затем ждём короткую паузу через `debounceTime(300)`. Если за это время пришёл новый текст, предыдущий ожидающий текст не проходит дальше. Это уменьшает лишние запросы, но само по себе не отменяет уже отправленный HTTP.

`distinctUntilChanged()` пропускает значение, если оно отличается от предыдущего прошедшего. Для строк сравнение предсказуемо. Для объектов `{ q, page }` стандартное сравнение ссылок не сравнивает поля: два новых одинаковых объекта считаются разными. Либо используйте понятный comparator, либо стройте поток простых значений на нужной стадии. Порядок операторов меняет поведение: нормализация до distinct позволяет считать `"сеть"` и `" сеть "` одинаковыми запросами.

`switchMap` на каждое внешнее значение подписывается на внутренний Observable и отписывается от предыдущего. Для HttpClient это отменяет устаревшее чтение на стороне клиента. Даже если сервер продолжил работу, его старый ответ уже не должен попасть в этот подписчик. Поэтому поиск отображает результат актуального запроса, а не самого медленного запроса.

Операторы описывают разную политику конкуренции. `mergeMap` допускает параллельные результаты, `concatMap` ставит операции в очередь, `exhaustMap` игнорирует новые, пока текущая не завершится. Не нужно запоминать весь RxJS; нужно уметь сформулировать требование. «Покажи результат последнего текста» естественно соответствует switchMap. «Сохрани каждую оплату» — совершенно другой контракт.

## Разобранная демонстрация

Полный файл: `practice/angular-labs/scripts/w4-04.ts`. Из корня выполните `node practice/angular-labs/scripts/w4-04.ts`. Ожидается только строка `Результат для «сеть»`; процесс сам завершится примерно за 500 мс. Установленный RxJS используется напрямую, Angular dev server и Java API не требуются.

```ts
import { Subject, map, switchMap, timer } from 'rxjs';

const query$ = new Subject<string>();
const subscription = query$.pipe(
  switchMap(query => timer(query === 'с' ? 300 : 30).pipe(
    map(() => `Результат для «${query}»`),
  )),
).subscribe(value => console.log(value));

query$.next('с');
setTimeout(() => query$.next('сеть'), 10);
setTimeout(() => subscription.unsubscribe(), 500);
```

Ожидается только «Результат для «сеть»». Отсчёт первого timer отменён новой подпиской. Вариация: замените switchMap на mergeMap и добавьте его в import. Тогда сначала появится «сеть», потом устаревшее «с». Эта контролируемая перестановка сильнее, чем случайное наблюдение на быстром локальном API.

Для реального пользовательского ввода перед switchMap добавьте `map(q => q.trim())`, `debounceTime(300)`, `distinctUntilChanged()`. В демонстрации их нет намеренно: пауза ввода скрыла бы соревнование двух запросов и не позволила увидеть разницу операторов. Сначала изолируем причину, затем собираем полный поток.

Ошибку внутреннего чтения обрабатывайте внутри switchMap, возвращая состояние ошибки. Если catchError стоит снаружи и заменяет весь поток на `of(errorState)`, после ошибки внешний поток может завершиться: следующий ввод больше не запустит поиск. Правильное место обработки определяется областью восстановления. Хотим восстановить один запрос и продолжить слушать текст, а не завершить всю последовательность ввода.

## Загрузка и отмена

Общий `loading` требует аккуратности: finalize отменённого запроса выполняется при смене текста. Если новый флаг включили до отмены старого, старый finalize может выключить его. Надёжный вариант — внутренний Observable сам выдаёт loading через `startWith`, затем success/empty/error. switchMap пропускает состояния только актуального внутреннего источника. Другой вариант — выставлять флаг в `defer` внутреннего запроса после отмены предыдущего.

Очистка текста — тоже запрос состояния. Пустая строка обычно означает показать весь набор с первой страницы; простое игнорирование пустой строки оставит старый поиск на экране. При смене q сбрасывайте страницу, иначе редкий запрос может открыться на несуществующей четвёртой странице и выглядеть пустым.

## Signals и RxJS в сервисах PL

В переданном разборе PL2.2/PL2.1 `StoreService` хранит текущее состояние через Signals, а `EventsService` использует RxJS. Это полезные ориентиры для чтения, а не обещание конкретного API: перед вызовом события найдите его тип, отправителя и подписчиков. Выбранная вкладка должна иметь текущее значение; команда «обновить данные» может повториться без смены вкладки. У обычного `Subject` нет автоматического сохранения последнего события для позднего подписчика. Не превращайте все команды в значения signal и не переносите всё состояние в поток событий.

На границе потока и экрана выберите один способ потребления. `async` pipe удобен для Observable в шаблоне и освобождает подписку при уничтожении представления; standalone-компоненту нужен `AsyncPipe` в `imports`. Если результат нужен и вычислениям класса, `toSignal` создаёт signal из Observable. Создавайте его один раз, обычно в инициализаторе поля, и повторно читайте возвращённый signal. Вызов `toSignal` при каждом клике или чтении getter создаёт новые подписки; для холодного HTTP это может дать повторные запросы. По умолчанию ему нужен injection context, а очистка привязана к создавшей его области.

Ниже — учебный фрагмент полей Angular-компонента. Предполагается уже полученный через DI `api`, чей `search(q)` возвращает `Observable<readonly Book[]>`; это условный контракт, не API PL и не готовый файл для запуска. Импортируйте `signal` из `@angular/core`, `toObservable` и `toSignal` из `@angular/core/rxjs-interop`, остальные операторы и `of` — из `rxjs`. Поля создаются в injection context, по одному разу на экземпляр компонента:

```ts
readonly query = signal('');
private readonly query$ = toObservable(this.query);
readonly result = toSignal(this.query$.pipe(
  map(query => query.trim()),
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(query => this.api.search(query).pipe(
    map(items => ({ kind: 'success' as const, items })),
    catchError(() => of({ kind: 'error' as const })),
    startWith({ kind: 'loading' as const }),
  )),
), { initialValue: { kind: 'loading' as const } });
```

Обработчик ввода вызывает `query.set(text)`, шаблон читает `result()`. Здесь `toSignal` создаёт единственную подписку на цепочку HTTP; не добавляйте второй `subscribe` или `async` к той же холодной цепочке ради отображения. Начальная пустая строка запускает поиск всех записей после паузы; до первого ответа показан `loading`. Каждый актуальный запрос выдаёт `loading`, затем `success` или `error`. Пустой `items` — пустой результат внутри `success`. Внутренний `catchError` позволяет следующему вводу снова запустить запрос. Без обработки ошибка Observable будет выброшена при чтении signal: `toSignal` не делает запрос безошибочным.

`toObservable` наблюдает текущее значение signal через эффект; несколько синхронных `set` могут дать только итоговое значение после стабилизации. Для текста поиска это подходит, для учёта каждого клика — нет. Повторный «Обновить» при том же тексте должен быть отдельной командой с собственной обработкой, а не надеждой на `query.set(query())`. Смена строки здесь также подавляется `distinctUntilChanged`, если после нормализации она прежняя.

Когда нужна явная подписка ради действия, используйте существующий механизм проекта либо `takeUntilDestroyed`. Например, заранее получите `private readonly destroyRef = inject(DestroyRef)`, а в `ngOnInit` завершите цепочку как `events$.pipe(takeUntilDestroyed(this.destroyRef)).subscribe(...)`. Здесь `events$` обозначает уже найденный поток; пример не задаёт API рабочего `EventsService`. Если в классе уже действует ручная отписка через базовый класс, сначала прочитайте её контракт. Две разные схемы cleanup и повторная подписка на один поток сами по себе не улучшают надёжность.

## Мост от Java и предел отмены

Отмена похожа на прекращение ожидания Future, но не гарантирует остановку серверной транзакции. Если POST уже создал заявку, unsubscribe не удалит её. Поэтому switchMap хорошо подходит для заменяемых чтений, а при записи нужно отдельное решение о повторных нажатиях и идемпотентности. Название оператора не является бизнес-гарантией.

## Критерии ручной проверки

Побеждает актуальный запрос; повтор строки не отправляет лишний GET; очистка восстанавливает набор; после ошибки ввод продолжает работать; нет вложенных подписок и ложного прекращения loading. У потребителя есть явный владелец и cleanup; отображение не создаёт повторную подписку, а событие обновления отличается от текущего состояния.
