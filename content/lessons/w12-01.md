# Поведенческие тесты: доказать, что нарушение обнаруживается

180 минут: 40 на механизм, 35 на пример, 75 на собственные тесты и 30 на новые условия. Нужна [интеграция Angular + Java](/lessons/w11-workshop). Результат — набор проверок, который принимает правильный контракт и отвергает несколько правдоподобных ошибок.

## Зелёный тест не равен полезному тесту

Тест должен различать допустимое и недопустимое поведение. Проверка «функция вызывается» не замечает, что она всегда возвращает true. Проверка одного happy path пропускает забытую ветку отказа. Название теста формулируйте через наблюдаемый результат и условие: «неактивный администратор не получает редактирование», а не «проверяет canEdit».

Выбирайте данные так, чтобы ошибочная реализация дала другой результат. Если проверяете фильтрацию, во входе нужны и включаемые, и исключаемые элементы. Если проверяете правило ролей, разделите роль, владение, активность и состояние записи. Важнее различающие случаи, чем десятки копий одного примера с другими именами. Expected outcome записывайте независимо от алгоритма реализации: копирование того же логического выражения в тест может воспроизвести ту же ошибку.

Небольшая таблица решений помогает увидеть независимые условия. Но не обязательно перебрать все возможные значения текста и все комбинации состояния, если это не меняет правило. Сначала охватите каждый ограничитель и разрешающее исключение, затем границы типов/контрактов. Данные извне валидируются отдельной границей: проверка валидной доменной модели не обязана превращаться в универсальный JSON parser.

## Разбор на нейтральном правиле

Пусть каталог разрешает заказать только опубликованный товар, который есть в наличии. Пример намеренно не повторяет итоговую политику canEdit:

```js
import assert from 'node:assert/strict';

function verifyOrderable(orderable) {
  assert.equal(orderable({ published: true, stock: 2 }), true);
  assert.equal(orderable({ published: false, stock: 2 }), false);
  assert.equal(orderable({ published: true, stock: 0 }), false);
}

verifyOrderable(item => item.published && item.stock > 0); // проходит
// verifyOrderable(item => item.stock > 0);                // падает
// verifyOrderable(() => true);                           // падает
```

Каждый отрицательный случай меняет одну причину. Если удалить проверку published, второй пример ловит дефект. Если оставить только первый assert, обе неправильные реализации пройдут. Это контролируемое испытание чувствительности тестов, похожее на mutation testing. Оно не доказывает абсолютную полноту: другой дефект может остаться незамеченным. Ценность — в конкретной связи «нарушение требования → красная проверка».

Для Java-разработчика это знакомая проверка сервисной политики через JUnit. Во frontend дополнительно выбирайте наблюдение, которое не зависит от private-state компонента. Если требование — «кнопка недоступна и не отправляет команду», вызов private-метода не доказывает DOM-binding. Нужны отдельные проверки публичной политики и пользовательского действия; один слой не обязан знать внутреннее имя signal.

## Граница Angular-тестов

TestBed создаёт окружение standalone-компонента и его dependencies. Для сервисного HTTP-контракта HttpTestingController проверяет URL, method, headers и body, затем управляемо завершает ответ. Для компонента можно подменить сервис, чтобы проверить pending, отказ и сохранённый draft. Не подменяйте сам проверяемый участок: fake, который сразу возвращает ожидаемый текст, ничего не говорит о mapper реального сервиса. [Angular component scenarios](https://angular.dev/guide/testing/components-scenarios), [HTTP testing](https://angular.dev/guide/http/testing).

Асинхронный тест должен дождаться ожидаемого результата. Произвольный sleep создаёт задержку и нестабильность; управляемый fake или завершение HTTP делает порядок явным. Для race-сценария нужен контроль двух ответов: завершите B, затем A и проверьте, что старый результат не заменил новый. Отдельно подтвердите, что ошибка снимает pending и следующая попытка возможна. Проверка только первоначального текста не затрагивает этот переход.

Браузерный сценарий оставьте для важного пути: фокус диалога, переход по URL, реальная отправка и отрисовка. Виртуальный DOM тестового окружения не является доказательством раскладки и производительности. Серверная авторизация требует API-теста на Java/HTTP: зелёное canEdit никогда не разрешает объявить backend защищённым.

## Практика в IDE — middle-11

Здесь вы пишете тесты, а не реализацию правила. В `practice/middle/middle-11/solution.mjs` экспортируйте `verifyCanEdit(canEdit)`. Переданный canEdit принимает actor=null либо `{id,roles,active}` и issue=`{ownerId,status}`. Результат должен быть boolean. Разрешение есть только при active actor, status не DONE и одном из условий: ADMIN либо EDITOR с совпадающим ownerId.

ADMIN не обходит inactive или DONE. Владелец без EDITOR/ADMIN не получает право. Неизвестная роль и null запрещают редактирование. Функция verify должна вызвать переданную реализацию и бросить assertion/Error при нарушении; просто вернуть false недостаточно. Можно использовать `node:assert/strict`, sync либо async интерфейс по README. Не проверяйте исходный текст функции, её имя или специально выбранные константы grader.

Запустите `npm.cmd run learn -- check middle-11`. Grader пропускает через ваши тесты корректное поведение и несколько дефектных реализаций. Успех требует принять первое и отвергнуть остальные. Он оценивает чувствительность ваших проверок в этом контракте, не серверную безопасность или все возможные тестовые данные.

Добавьте пользователя `u-17` с ролями VIEWER и EDITOR, свою IN_PROGRESS запись и чужую OPEN. Затем проверьте пустые roles, null, неактивного ADMIN и владельца только с неизвестной ролью. ## Критерии самопроверки

middle-11 проходит; expected outcomes не вычисляются копией проверяемой формулы; есть разрешающий и запрещающий ADMIN-сценарии; тесты различают владение и роль; каждый существенный отказ имеет объяснение. Назовите один дефект, который ваш набор ловит, и один риск за пределами pure policy. Самостоятельность — спроектировать новые случаи до чтения авторского ответа.
