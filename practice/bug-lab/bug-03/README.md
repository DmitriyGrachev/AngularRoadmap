# bug-03: Один экран отправляет два одинаковых GET

Связанный урок: [w4-02](../../../content/lessons/w4-02.md). Около 30 минут; упражнение может заменить часть ручной практики урока.

Симптом: Network показывает два GET /api/issues, хотя createDashboard вызывает http.get один раз. Выполните node practice/bug-lab/bug-03/repro.mjs: подписчики items$ и count$ запускают источник дважды. Исправьте разделение результата, включая позднее появление счётчика. Незавершённое чтение должно отменяться после ухода всех потребителей.

## Запуск из корня проекта

```powershell
node practice/bug-lab/bug-03/repro.mjs
npm.cmd run learn -- check bug-03
```

Сценарий работает без сайта, dev server и Java API с установленными зависимостями проекта. Исходный дефект намеренно завершает repro с AssertionError и ненулевым кодом. После исправления сценарий завершается успешно. Полная проверка создаёт отчёт версии 1 для учебного сайта.

Редактируйте только `solution.mjs`. `starter.mjs` сохраняет исходную поломку для проверки качества задания и не зависит от вашего решения. Существующее приложение ученика не используется и не переписывается.

## Контракт

createDashboard(http) возвращает { items$, count$ }. http.get("/api/issues") возвращает Observable<{ items: Issue[] }>. count$ выдаёт длину того же набора.

## Критерии результата

- Одновременные подписчики items$ и count$ запускают один холодный источник.
- Поздний подписчик после успеха получает последний результат без нового GET, в том числе [].
- После ухода последнего потребителя незавершённый источник больше не наблюдается.

## Диагностика

Перед изменением запишите ожидаемое и фактическое поведение, гипотезу причины и эксперимент, различающий две возможные причины. После исправления запустите полную проверку, а не только один repro. Три последовательные подсказки и объяснение находятся в тренажёре; сначала сохраните собственную попытку.

## Новый регрессионный пример

Регрессионная задача: закройте одного потребителя, пока второй ещё ждёт; затем закройте второго до ответа. Источник должен оставаться активным только до второго ухода. Объясните, почему share без replay не решает требование позднего счётчика.
