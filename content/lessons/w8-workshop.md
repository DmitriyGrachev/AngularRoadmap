# Практикум: архитектура одной feature без лишних слоёв

360 минут: 45 на карту ответственности, 155 на реализацию, 90 на тесты, 40 на вариацию и 30 на защиту. Нужен [урок о компонентах и DI](/lessons/w8-03). Вы превратите несколько работающих частей в feature, где источник каждого состояния и путь каждого события можно объяснить.

## Требование

В `practice/workplace` добавьте «Подборку для разбора»: пользователь выбирает до трёх заявок из текущей страницы, видит выбранные строки в отдельной панели и может очистить выбор. Смена страницы и фильтра очищает подборку. В URL остаются только фильтры и пагинация; подборка — временное состояние текущего просмотра. Открытие карточки сохраняет query params, а возврат к списку восстанавливает поля и результат. После полной перезагрузки подборка пуста, потому что это явно выбранная политика.

Выбранную строку следует определять по ID и актуальному списку. Если пришла новая версия списка без выбранного ID, такого выбора больше нет. Счётчик выводится из выбранных данных и не меняется отдельной командой «прибавить один». Повторное нажатие уже выбранной заявки снимает выбор. Четвёртая новая заявка не добавляется, интерфейс объясняет лимит и не теряет первые три. Для взаимодействия предусмотрены клавиатура, видимый фокус и подпись действия.

Полностью рабочий baseline запускается `npm.cmd run practice:workplace` на `http://127.0.0.1:4305`. Он использует DeskApi в памяти, не Java HTTP. Исходные query-соглашения: status в нижнем регистре, страница начинается с единицы. Не переносите из middle-04 enum и page=0 без преобразования. Мы применяем архитектурные принципы, а не заменяем продуктовый контракт моделью упражнения.

## Карта решения

До кода нарисуйте одну цепочку: URL → разобранный ListQuery → чтение DeskApi → состояние списка → представление. Отдельной стрелкой укажите событие выбора строки → команда store → вычисленная подборка. Компонент строки должен знать данные и доступные действия, но не адрес сервера и не устройство Router. Страница собирает зависимости. Store управляет инвариантами выбора. Parser нормализует внешнее состояние. Это карта фактических обязанностей, а не обязательное количество файлов.

Проверьте, где создаётся store. Он должен обслуживать конкретный просмотр списка и его панель. Если зарегистрировать его в root, временный выбор может пережить уход и попасть в другой экран. Если зарегистрировать отдельно в списке и панели, они не увидят друг друга. Выберите ближайшего общего владельца. Поведение после ухода со страницы подтвердите тестом или наблюдением, а не названием сервиса.

В Java это похоже на application service, который координирует use case, и объект, который защищает инварианты. Но frontend feature содержит ещё маршрутизацию, время жизни отображения и доступное взаимодействие. Не превращайте каждый элемент шаблона в backend-style controller. Для одной панели может быть достаточно страницы, компонента строки и маленького store, если границы ясны и тестируемы.

## Разобранный пример инварианта

Сохраните `selection-protocol.mjs` в собственной временной папке и выполните `node selection-protocol.mjs`:

```js
const visible = [{ id: 'B', title: 'DNS' }, { id: 'A', title: 'VPN' }];
const selectedIds = new Set(['A', 'C']);
const validIds = new Set(visible.map(item => item.id));
const nextIds = new Set([...selectedIds].filter(id => validIds.has(id)));
const selected = visible.filter(item => nextIds.has(item.id));
console.log([...nextIds].join(','));
console.log(selected.map(item => item.title).join(','));
```

Ожидаются `A` и `VPN`: исчезнувший C не остаётся призрачной строкой. Пример не решает toggling, DI или лимит; это изолированное следствие обновления списка. Вариация: список содержит A с новым title. Подборка обязана использовать новый объект, а не старую сохранённую копию. Объясните, как ваши computed обеспечивают это без ручного обхода нескольких компонентов.

## Практика в IDE — w8-workshop-ex1

Откройте `practice/middle/w8-workshop-ex1/README.md` и запишите контракт в `notes.md`. Реализуйте подборку в своей версии workplace, сохранив выполненные раньше задания. Для чистоты эксперимента можно сделать локальную копию или коммит перед изменением; не заменяйте студенческие файлы авторскими. Изменения ограничьте нужными компонентами, store и проверками. Новая state-management зависимость не требуется: достаточно signal, computed и текущего RxJS-потока чтения.

Проверяйте границы отдельно. Store-тест подтверждает toggling, лимит и исчезнувший ID. Компонентный тест подтверждает, что настоящее действие вызывает ровно одну команду. Проверка страницы подтверждает смену URL и очистку подборки при изменении фильтра. Эти проверки не должны дублировать каждую строку реализации: они ловят разные пользовательские регрессии. Команды baseline: `npm.cmd run test:workplace` и `npm.cmd run build:workplace`.

Избегайте временного противоречия на экране. Если URL уже показывает новый фильтр, а результаты ещё старые, пользователь не должен принять старую подборку за результат нового запроса. Можно очистить её на переходе и показать загрузку. Можно сохранить предыдущий список с явной маркировкой, но это усложнит контракт и требует отдельного основания. Для текущего требования очистка при переходе проще и достаточна.

Подпись кнопки выбора должна отражать состояние: «Добавить …» или «Убрать …». Если используете checkbox, свяжите подпись с полем и корректно отобразите checked. Не делайте всю строку одновременно ссылкой и областью выбора без разделения действий. Пройдите сценарий только клавиатурой: выбрать три, увидеть ограничение для четвёртой, убрать одну, добавить другую, открыть карточку, вернуться. Тест логики не подтверждает, что эти действия реально доступны в DOM.

<details><summary>Подсказка 1 — факты</summary>Отметьте в карте первичные данные и производные значения разными пометками. Если счётчик или selectedRow хранится отдельно, найдите причину, по которой его нельзя вычислить.</details>
<details><summary>Подсказка 2 — владение</summary>Найдите ближайшего общего предка списка и подборки. Там обычно проще обеспечить один экземпляр store и понятное уничтожение.</details>
<details><summary>Подсказка 3 — наблюдаемая граница</summary>Один тест должен сменить реальный query param и проверить новый экран. Вызов внутреннего reset сам по себе не доказывает связь с маршрутом.</details>

**Новые данные.** Откройте прямую ссылку со второй страницей, выберите две строки, смените status, затем нажмите Back. Фильтр и список восстанавливаются по URL, подборка остаётся пустой по заданной политике. После этого смените title выбранной строки в управляемом ответе тестового API и проверьте обновление текста в панели. Наконец выполните два независимых экземпляра feature в тесте и докажите отсутствие общего временного выбора.

## Критерии защиты

Функция работает при прямой ссылке и браузерной истории; выбор соблюдает лимит и не содержит исчезнувших строк; действие имеет единственного владельца; DI-область подтверждена; доступность проверена вручную. Оценка по каждому пункту: самостоятельно / с подсказкой / повторить. Сильная защита включает удалённое лишнее состояние или объяснение, почему новый слой не нужен, и один воспроизводимый дефект, пойманный проверкой границы.

Не называйте выделение файлов архитектурным успехом без результата пользователя. Покажите цепочку одного действия за две минуты и объясните, куда добавится новое требование «выбирать до пяти» и где проверяется лимит. Успех этого практикума подтверждает владение небольшой feature; управление несколькими командами и конкурентными запросами проверяется следующей неделей.
