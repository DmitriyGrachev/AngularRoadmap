# Практикум: создание и редактирование без потери ввода

300 минут: 180 на полный путь записи, 60 на самостоятельный приоритет, 60 на отрицательные сценарии. Нужны [модель формы](/lessons/w5-01), [валидация](/lessons/w5-02), [POST](/lessons/w5-03), [серверные ошибки](/lessons/w5-04), [PATCH](/lessons/w5-05).

## Рабочая ситуация

Пользователь создаёт заявку, открывает детали, исправляет название и статус, затем возвращается в список. В новой задаче нужно добавить редактирование приоритета. Это небольшое вертикальное изменение: тип → control → payload → сервер → отображение. Успех в одном звене не означает, что поле прошло весь путь.

Предскажите: если priority появился только в select, но отсутствует в PATCH, что увидит пользователь сразу и после перезагрузки? Локальная картинка может казаться правильной, а повторный GET вернёт прежнее значение. Поэтому сохранение проверяют через новый запрос, а не только по изменившемуся тексту рядом с формой.

## Механизм полного сценария

Создание отправляет только title/description/priority и получает серверный ID. Деталь читает сохранённое представление. Редактирование загружает запись до начала ввода и отправляет разрешённый PATCH. Неправильная форма останавливается до HTTP; серверный отказ показывается после запроса без потери ввода. В ожидании нельзя случайно отправить второй параллельный POST.

Не пытайтесь сделать одну универсальную форму для всех возможных сущностей. На этом этапе полезнее явные поля и понятные различия создания/редактирования. Общее отображение можно выделить позже, когда повторение действительно мешает. Сложность абстракции не является критерием освоения Angular.

Сравнение с Java: control не является DTO, DTO не является JPA entity, а успешный браузерный callback не заменяет проверку повторного чтения. Наличие клиентского validator не даёт права удалить серверный. Даже если оба правила сейчас совпадают, пользователь может отправить запрос в обход формы.

## Независимая демонстрация границы payload

Полный файл: `practice/angular-labs/scripts/w5-workshop.ts`. Выполните из корня `node practice/angular-labs/scripts/w5-workshop.ts`. Ожидается `{"category":"ADULT"}` — остальные поля отсутствуют. Скрипт не требует Angular-сервера или Java API; выполните его до изменения трекера:

```ts
type Reader = { id: string; name: string; category: 'ADULT' | 'CHILD'; joinedAt: string };
type ReaderPatch = Partial<Pick<Reader, 'name' | 'category'>>;
const formValue = { name: 'Анна', category: 'ADULT' as const };
const request: ReaderPatch = { category: formValue.category };
console.log(JSON.stringify(request)); // {"category":"ADULT"}
```

Предскажите, присутствуют ли name, id и joinedAt в JSON. Затем добавьте name только при реальном требовании изменения. Вариация: сделайте поле undefined и наблюдайте сериализацию. Это повод строить DTO явно, а не надеяться, что сервер сам поймёт все поля формы.

## Практика в IDE — w5-workshop-ex1

Рабочие файлы: `practice/issue-tracker/src/app/{app.ts,models.ts,issue.service.ts,issue-form.ts,issue-detail.ts,issues-list.ts}` и связанные spec. Запуск двух процессов: `npm.cmd run practice:api` и `npm.cmd run practice:angular`. Проверки — `npm.cmd run practice:test -- --watch=false`.

Сначала пройдите создание → детали → редактирование → список без новой возможности. Зафиксируйте исходный ID и значения. После этого самостоятельно добавьте редактирование priority с допустимыми `LOW`, `MEDIUM`, `HIGH`. Составьте собственный список мест изменения; не ограничивайтесь select. После сохранения откройте деталь прямым URL и обновите страницу.

Проверьте пустой title, пробелы, предельную длину по контракту, ошибку поля 400, общий сбой, повторную отправку после исправления и быстрое двойное действие. При недоступном API введённый текст остаётся. При неуспехе не должно быть навигации «как после успеха». Если форму можно редактировать во время запроса, отдельно докажите актуальность field errors; если блокируете — проверьте восстановление доступности.

Сохраните короткий журнал: действие, payload/status, ожидаемый результат, наблюдение. Успешные тесты отмечайте отдельно от ручной оценки самостоятельности. Для серверного 400 используйте документированное правило API или HTTP test backend: не подменяйте его произвольным клиентским alert и не заявляйте, что проверили настоящий сервер.

## Критерии ручной проверки

Создание и редактирование проходят полным путём; priority самостоятельно проведён через все слои; ошибки не стирают данные; нет ложного успеха; повтор работает; хотя бы одна проверка формы выявляет нарушение. Для каждого пункта отметьте самостоятельность, подсказку или необходимость повторения. Красивый select без сохранения не считается завершённым изменением.
