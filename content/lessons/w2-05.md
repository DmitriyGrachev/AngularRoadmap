# Тесты поведения и команды проекта

**Результат:** вы читаете ошибку проверки, исправляете дефект фильтра и добавляете два полезных граничных случая. Нужны [операции массивов](/lessons/w1-04), [модули](/lessons/w2-01), [границы типов](/lessons/w2-04). Занятие посвящено поведению; готовый тестовый инструмент Node уже входит в среду.

## Рабочая ситуация и прогноз

После небольшой правки фильтр стал показывать все статусы, кроме выбранного. Внешне список иногда выглядит правдоподобно, особенно если проверить только пустой вход. Тест должен описать обещанное поведение и сделать нарушение заметным.

```js
function filterIssues(issues, status) {
  return issues.filter(issue => issue.status !== status);
}
```

Для входа OPEN, DONE и аргумента OPEN какую заявку вернёт функция? Пройдёт ли проверка пустого массива? Достаточна ли одна проверка пустого массива, чтобы обнаружить ошибку? Предскажите ответы до запуска подготовленного теста.

## Что проверяет тест

Тест — выполняемый пример ожидаемого поведения. В нём есть подготовка данных, вызов действия и проверка результата. Имя должно сообщать смысл: «выбирает заданный статус», а не «тест 1». Хороший тест помогает отличить дефект программы от неверного понимания требования. Он не доказывает отсутствие всех ошибок, особенно вне проверенных входов.

Для фильтра обычный случай — смешанный набор, где есть подходящие и неподходящие заявки. Пустой вход проверяет границу. Отсутствие совпадений отличается от пустого входа: элементы есть, но ни один не подходит. Неизменность входа проверяет другое свойство контракта. Если тесты многократно проверяют одно и то же случайными названиями, их количество растёт без новой уверенности.

`node:test` — встроенный тестовый модуль Node. Импорт `test` регистрирует именованную проверку с функцией-телом. `node:assert/strict` предоставляет утверждения, которые выбрасывают ошибку при несовпадении. Это реальные ошибки теста, а не просто console.log с оптимистичной подписью. Вывод «успех» без сравнения факта и ожидания ничего не подтверждает.

`assert.deepEqual(actual, expected)` сравнивает содержимое массивов и объектов по строгим правилам модуля, поэтому подходит для результата фильтра. Обычное `actual === expected` сравнило бы идентичность разных массивов и дало false даже при одинаковых элементах. Утверждение не должно вычислять ожидаемое значение той же логикой, которую проверяет. Если expected снова строится тем же ошибочным filter, обе ошибки совпадут и тест станет бесполезным.

## Как читать неуспех

Имя упавшего теста говорит, какое обещание нарушено. Поля expected и actual показывают ожидание и факт; строка стека помогает найти утверждение. Сначала проверьте вход и договор. Затем сформулируйте причину. В нашем дефекте оператор `!==` выбирает неподходящие элементы, хотя нужен точный статус. Изменять expected на DONE ради зелёного вывода означало бы переопределить требование без основания.

Красный тест может также означать ошибку самого теста, неверный путь импорта или сбой инструмента. Ошибка импорта не говорит, что фильтр вернул неверный массив: функция вообще не была вызвана. Поэтому читайте сообщение, а не только цвет. Для учебного дефекта ожидается именно несовпадение результата, затем успешный повтор после изменения логики.

Проверка мутации требует наблюдать исходник после вызова. Сохраните исходные поля или используйте замороженные входы: `Object.freeze` запрещает изменения свойств объекта в строгом модульном коде. Заморозка поверхностна: замороженный массив не делает автоматически замороженными его элементы. Для плоских заявок можно заморозить и каждый объект, и массив. Такой тест обнаружит попытку присваивания, но сам по себе не доказывает правильность выбора — нужен обычный случай отдельно.

## Мост от Java

По структуре test и assert похожи на JUnit: подготовка, действие, проверка и читаемое сообщение неуспеха. Но здесь импортируется модуль и функция, не обязательно создаётся тестовый класс. Проверка типов TypeScript и тесты решают разные задачи: tsc может запретить неверный статус в коде, но не докажет, что ваш предикат выбирает правильные значения на реальном входе. Runtime-проверка JSON также не заменяет тест логики.

## Разобранный пример

Выполните `node --test practice/foundations/async-types/examples/filter.test.mjs`. Два демонстрационных случая должны пройти: выбор OPEN и пустой массив. Они импортируют корректную функцию из examples/filter.mjs, отдельно от самостоятельного задания. Прочитайте один тест целиком и укажите, где fixture — подготовленные данные, где действие и где ожидание.

Теперь мысленно замените в примере `===` на `!==`: обычный случай падает, пустой остаётся успешным. Так видно, зачем нужны разные входы. Не изменяйте демонстрацию навсегда; исправляемый дефект уже находится в отдельной заготовке.

## package.json, scripts и lockfile

`package.json` описывает проект, зависимости и именованные команды scripts. `npm.cmd run learn` находит запись learn и запускает подготовленный runner. `--` передаёт последующие аргументы этой команде. Это не произвольная магия сайта: команду можно прочитать в корневом файле.

Lockfile фиксирует конкретное дерево зависимостей. Для установки подготовленного проекта используется команда из README, обычно `npm.cmd ci`, когда package.json и lockfile согласованы. Не удаляйте lockfile ради случайной ошибки установки и не обновляйте все зависимости ради задачи фильтра. Смена среды — отдельная работа. Наши проверки функции используют встроенные модули Node и не требуют добавления новой библиотеки.

## Практика в IDE

Упражнение `w2-05-ex1`: редактируйте `practice/foundations/async-types/w2-05-ex1/filter.mjs` и `filter.test.mjs`. Выполните `node --test practice/foundations/async-types/w2-05-ex1/filter.test.mjs`. Сначала сохраните смысл ошибки: ожидается OPEN, фактически приходит DONE. Исправьте предикат без изменения уже заданного ожидания. Добавьте два теста: пустой вход и неизменность массива/объектов. Повторите запуск.

Это ручное упражнение по написанию тестов; успешный вывод Node не импортируется как отчёт курса. Критерием служат проверяемое поведение и объяснение проверки. Приложение с нерешённым starter не должно считаться поломанной учебной платформой.

## Критерии

- Первоначальное нарушение воспроизведено и объяснено; исправление сохраняет исходный контракт.
- Три содержательных случая проходят: точный выбор, пустой вход, отсутствие мутации.
- Если временно вернуть неверный предикат, обычный тест снова падает; после опыта исправление восстановлено.
- Вы находите scripts в package.json и объясняете роль lockfile без его удаления.

## Проверка понимания

1. Почему === не подходит для сравнения содержимого двух массивов?
2. Почему зелёный тест пустого входа не обнаруживает инвертированный фильтр?
3. Чем сбой импорта отличается от неверного результата?
4. Почему tsc не заменяет тест поведения?

Новая вариация: добавьте вход без совпадений, но с несколькими DONE. Объясните, какое новое обещание он проверяет относительно пустого исходника.
