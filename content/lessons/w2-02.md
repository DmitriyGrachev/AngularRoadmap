# Ожидание данных: Promise и async/await

**Результат:** вы предсказываете простой порядок выполнения и обрабатываете успех и сбой, всегда завершая состояние ожидания. Нужны [callback и функции](/lessons/w2-01). Не требуется знать потоки RxJS или устройство браузерного движка изнутри.

## Рабочая ситуация и прогноз

Список загружается с задержкой. Пользователь должен видеть «Загрузка», затем данные или сообщение ошибки. Если убрать индикатор только в успешной ветке, при сбое он останется навсегда.

```js
console.log('A');
Promise.resolve().then(() => console.log('C'));
console.log('B');
```

В каком порядке появятся буквы? Вызовет ли уже выполненный Promise обработчик then прямо в середине текущего стека? Добавьте в прогноз таймер `setTimeout(() => console.log('D'), 0)` после первой строки. Ожидаемый порядок для этого ограниченного примера: A, B, C, D.

## Стек, задачи и microtasks

Текущий JavaScript выполняет синхронный код в стеке вызовов. Вызов функции добавляется в стек, возврат убирает его. Пока выполняется длинный синхронный цикл в основном потоке страницы, пользовательский интерфейс не может обработать очередное действие. Ожидание сети поэтому не реализуют таким циклом.

Среда выполняет внешнюю работу и ставит продолжение в очередь. Таймер создаёт задачу, которую можно обработать позже. Обработчики завершения Promise попадают в очередь microtasks — микрозадач. Когда текущая синхронная работа завершена, среда выполняет доступные микрозадачи перед следующей обычной задачей. Поэтому B появляется раньше C, а C — раньше таймера D. Это достаточная модель для наших примеров; она не утверждает, что у всей среды существует единственная очередь и что таймер гарантирует точное время.

`setTimeout(callback, 100)` просит вызвать callback не раньше приблизительно указанной задержки, когда среда сможет обработать задачу. Он не останавливает выполнение следующих строк. Нулевая задержка тоже не означает немедленный вызов. Расчёт интерфейса на точные миллисекунды таймера ошибочен; в заданиях задержка служит только наблюдаемой имитацией ожидания.

## Promise описывает один исход

Promise — объект будущего результата. Он находится в состоянии pending, затем один раз становится fulfilled со значением или rejected с причиной ошибки. Повторное завершение не меняет первый исход. `new Promise((resolve, reject) => ...)` создаёт Promise; переданная функция запускается сразу и получает функции успешного и неуспешного завершения. В примере авторский загрузчик вызывает их позже из таймера.

`then` регистрирует продолжение успеха и возвращает новый Promise. `catch` позволяет обработать отклонение. Это не то же самое, что try/catch вокруг самого запуска таймера: ошибка произойдёт позднее, когда внешний вызов уже закончился. Поэтому асинхронную ошибку нужно передавать через Promise и обрабатывать в его цепочке или через await.

`async function` всегда возвращает Promise. Внутри неё `await expression` приостанавливает именно эту функцию до завершения ожидаемого Promise. Браузер и вызывающий код могут продолжать работу; весь процесс не блокируется. После успеха await даёт значение, после отклонения ведёт себя как выброшенная ошибка в точке ожидания. Последующие строки этой функции ещё не выполнены, пока она ожидает.

`try` окружает операцию, которая может завершиться ошибкой. `catch` получает ошибку и выбирает пользовательское сообщение. `finally` выполняется после успеха или обработанного сбоя и подходит для снятия loading. Оно не означает автоматическое восстановление данных или повтор запроса. Не возвращайте из finally случайный результат: это способно перекрыть прежний return или ошибку и запутать контракт.

## Мост от Java

Promise отдалённо напоминает CompletableFuture как значение будущего результата. `await` здесь не является блокирующим `get()` на UI-потоке: продолжение функции планируется позже. Один Promise представляет один итог; это не непрерывный поток изменений. И, как в Java, ошибка может быть обычным результатом внешнего взаимодействия, поэтому нужны явные состояния и понятное сообщение, а не только stack trace для пользователя.

## Разобранный пример

Выполните `node practice/foundations/async-types/examples/async.mjs`. Ожидается:

```text
A
B
loading true
C
rows 1
loading false
loading true
error Нет связи
loading false
```

Первый show запускается синхронно до await и успевает напечатать loading. Затем текущая работа отдаёт управление, поэтому C появляется до данных таймера. После первой завершившейся show запускается вторая. В её ветке catch выводится сообщение ошибки, а finally снова снимает ожидание. Уберите finally мысленно: какой исход оставит loading истинным? Затем проверьте в отдельной временной копии.

## Первое знакомство с fetch

Fetch отправляет HTTP-запрос и возвращает Promise ответа. При работающем `npm.cmd run practice:web` откройте любую страницу на порту 4301 и выполните в её Console:

```js
const response = await fetch('/foundations/async-types/examples/issues.json');
if (!response.ok) throw new Error(`HTTP ${response.status}`);
const data = await response.json();
console.log(data.length); // 1
```

Это отдельный демонстрационный запрос. `response.ok` проверяет успешный HTTP-статус; ответ 404 сам по себе обычно не отклоняет Promise fetch. Сбой сети может отклонить. `response.json()` тоже асинхронен и может дать ошибку некорректного JSON. Пока тип и структура data не проверены: успешный разбор JSON ещё не означает корректную заявку. Этот вопрос разбирается далее.

## Критерии

- Оба исхода завершаются, ожидание снимается в каждом; ошибка не останавливает демонстрацию неконтролируемым отклонением.
- Данные читаются после await, а не из самого объекта Promise.
- Вы предсказываете A/B/C и объясняете момент приостановки функции.
- Проверка ручная по выводу и объяснению; эта команда не создаёт отчёт runner.
