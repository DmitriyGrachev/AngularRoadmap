# Браузер, CSS и доступность: исправлять причину, а не пиксель

180 минут: 35 на механизм, 25 на разбор, 90 на изменение и 30 на проверку. Результат: вы исправляете переполнение и управление клавиатурой, объясняя DOM, каскад и фокус. Предыдущий шаг — [проверка внешних данных](/lessons/w7-02).

## Сначала наблюдение, затем правило

В рабочей таблице длинная тема вытесняет кнопку действия за экран. Разработчик увеличивает ширину страницы, затем уменьшает шрифт, затем добавляет `!important`. На одном ноутбуке дефект исчезает, на телефоне остаётся. Причина могла быть в минимальном размере flex-элемента, запрете переноса или фиксированной ширине родителя. Эти причины требуют разных исправлений. Перед изменением запишите ширину окна, проблемную строку, вычисленную ширину элемента и ближайшего контейнера. Скриншот фиксирует симптом; вкладка Computed помогает проверить объяснение.

Браузер разбирает HTML в DOM, сопоставляет CSS-правила, вычисляет стили, строит геометрию и рисует результат. Изменение текста может изменить размер; изменение цвета обычно не требует пересчитать геометрию. Это полезное различие при поиске медленной страницы, но не обещание конкретного внутреннего алгоритма браузера. В Angular условия и циклы добавляют и удаляют DOM-узлы. Если `@if` убирает элемент с фокусом, пользователь теряет точку взаимодействия независимо от красоты следующего состояния.

Каскад не сводится к «последний стиль побеждает». Учитываются происхождение, важность, слои, специфичность и порядок. В DevTools посмотрите, какое правило реально выиграло, и откройте его исходник. Не повышайте специфичность, пока не понятно, откуда пришёл конфликт. Emulated encapsulation Angular ограничивает применение компонентных стилей через атрибуты, но не превращает CSS в полностью изолированный документ. Глобальные правила, наследование и библиотечная разметка всё ещё влияют на результат.

## Геометрия и семантика — разные контракты

Для строки с текстом и кнопкой полезна сетка с `minmax(0, 1fr) auto`: текстовая колонка может сжиматься, кнопка сохраняет место. Для flex-контейнера аналогичную проблему нередко решает `min-width: 0` у текстового ребёнка. Затем выбирается продуктовая политика: переносить тему, сокращать визуально или давать отдельный доступ к полному тексту. Многоточие без возможности прочесть содержание не является законченным решением. `overflow-wrap: anywhere` помогает длинному токену переноситься, но не заменяет адаптацию всей таблицы.

Кнопка запускает действие, ссылка меняет адрес. `div` с обработчиком клика не получает автоматически клавиатурную активацию, роль, доступное имя и состояние disabled. Нативный элемент снимает часть этой работы. Атрибут `aria-label` даёт имя там, где видимой подписи недостаточно; он не добавляет поведение. Не назначайте `role="button"` настоящей кнопке и не скрывайте всю строку через `aria-hidden`, пытаясь убрать лишнее объявление иконки.

Порядок Tab должен следовать смыслу документа. Положительный `tabindex` создаёт отдельный порядок, который ломается при добавлении новых элементов. Обычно достаточно нативных контролов и `tabindex="-1"` для программного переноса фокуса на заголовок или сводку ошибок. Видимый `:focus-visible` обязателен для понятной навигации. Outline, который перекрыт соседним контейнером, формально существует в CSS, но не помогает человеку.

Для Java-разработчика удобна аналогия с публичным API: семантический HTML описывает контракт взаимодействия, CSS — его представление. Как успешный HTTP 200 не доказывает правильность тела ответа, так корректный внешний вид не доказывает доступность. При этом браузер не Spring MVC view: DOM живёт между действиями, фокус и прокрутка являются пользовательским состоянием, которое легко потерять при перерисовке.

## Разобранный пример

Запустите `npm.cmd run practice:workplace`, откройте `http://127.0.0.1:4305/requests`. В DevTools временно замените текст одной темы длинным словом. Изменение в Elements пропадает после перезагрузки и не меняет исходники. Сравните ширину списка до и после; найдите узел, который создаёт переполнение. Затем сохраните следующий независимый пример как локальный HTML-файл и откройте браузером:

```html
<!doctype html><html lang="ru"><meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>Проверка строки</title>
<style>
  * { box-sizing: border-box; }
  .row { display: grid; grid-template-columns: minmax(0, 1fr) auto;
    gap: 12px; max-width: 400px; border: 1px solid; padding: 12px; }
  .title { overflow-wrap: anywhere; }
  button:focus-visible { outline: 3px solid #1254c2; outline-offset: 3px; }
</style>
<div class="row">
  <span class="title">ОченьДлиннаяТемаОбращенияБезПробеловДляПроверкиГраниц</span>
  <button type="button" onclick="document.querySelector('#status').textContent='Выбрано'">
    Выбрать
  </button>
</div>
<p id="status" role="status"></p></html>
```

При ширине 320 CSS-пикселей текст переносится, кнопка остаётся доступной. Tab выделяет кнопку, Space меняет подпись статуса на «Выбрано». Живая область сообщает изменение поддерживающим её средствам доступа; конкретное объявление проверяйте со скринридером. Пример не является моделью полноценной таблицы и не решает навигацию по сложной сетке. Удалите `minmax(0, 1fr)`, поставьте `1fr` и сравните поведение с длинным неделимым токеном без `overflow-wrap` — проверяйте взаимодействие двух правил, а не запоминайте магическую строку.

## Практика в IDE — w7-03-ex1

Условия и место отчёта: `practice/middle/w7-03-ex1/README.md`, `notes.md`. Работайте в своей версии `practice/workplace`. Приведите панель фильтров и строки списка к работе при 320, 768 и 1280 CSS-пикселях. У полей должны быть связанные подписи, у ссылок и действий — понятные имена, у ошибки — текст и доступный повтор. Если полноценная таблица требует горизонтальной прокрутки, ограничьте её контейнером, обеспечьте обнаружимость и клавиатурный доступ; вся страница не должна бесконтрольно расширяться.

Сначала воспроизведите один дефект на длинном тексте и один на клавиатуре. Исправьте оба минимально и добавьте проверку поведения, если меняете обработчик или управление фокусом. Проверьте начало загрузки и возврат результата: кнопка, на которой стоит фокус, не должна неожиданно исчезать без понятной следующей точки. Сохранение формы здесь не требуется. `DeskApi` работает в памяти; HTTP-запросов списка в Network нет.

<details><summary>Подсказка 1 — локализация</summary>Сравните scrollWidth и clientWidth документа и контейнеров. Переполнение начинается у конкретного узла, а не у абстрактного «Bootstrap».</details>
<details><summary>Подсказка 2 — контракт элемента</summary>В дереве Accessibility проверьте роль, имя и состояние. После этого пройдите тот же элемент Tab, Enter и Space без мыши.</details>
<details><summary>Подсказка 3 — состояние после действия</summary>Перед повтором ошибки запишите document.activeElement. После появления результата проверьте, остался ли элемент в DOM и видна ли рамка фокуса.</details>

**Новые данные.** Возьмите тему из 180 букв без пробелов, затем обычное предложение из 30 слов. Увеличьте масштаб до 200%, отправьте пустой поиск и вызовите одно чтение с ошибкой через панель среды. Это четыре разных проверки; успех короткой строки не заменяет остальные. Запишите ожидаемую политику переноса и результат каждой.

## Критерии ручной проверки

По отдельности оцените диагностику CSS, семантику, клавиатуру, изменение состояний и адаптацию: самостоятельно / с подсказкой / повторить. Для зачёта нужны воспроизведение причины, корректный Tab-порядок, видимый фокус и доступные действия на узком экране. Объясните, почему выбран grid или flex, где граница прокрутки и что делает live region. Автоматический тест не подтверждает удобство чтения скринридером; этот пункт фиксируется отдельным наблюдением либо честной отметкой о непроведённой проверке.
