# Практикум: Angular с локальными данными

300 минут: 180 минут на связный сценарий, 60 на новый счётчик, 60 на проверку и объяснение. Нужны [все компоненты недели](/lessons/w3-01), [signals](/lessons/w3-03), [сервис](/lessons/w3-04) и [маршруты](/lessons/w3-05).

## Ситуация

Коллега должен открыть трекер по ссылке, найти заявку, изменить её локальный статус и вернуться в список. Набор данных пока хранится в браузерной памяти. Перезагрузка возвращает fixtures; это ограничение данной стадии, которое нужно объяснить, а не скрывать обещанием сохранения.

Перед работой предскажите: если список и детали получают root-сервис, что произойдёт после изменения статуса в деталях? Что изменится после полного обновления вкладки? Правильное объяснение различает общий экземпляр внутри запущенного приложения и долговечное хранение.

## Механизм целого

Маршрут выбирает страницу, страница получает ID или фильтр из URL, сервис предоставляет данные, вычисления подготавливают видимый набор, карточка отображает вход и отправляет намерение. Выделение компонентов полезно, когда эти границы прослеживаются в коде. Пять компонентов, каждый из которых правит один массив напрямую, не дают полезного разделения.

Счётчик открытых заявок является производной исходного набора. Не увеличивайте и не уменьшайте его вручную рядом с каждым изменением статуса: появится второй источник истины. В локальном варианте вычислите его из всех записей сервиса. Подпись должна объяснять область подсчёта. «Открыто всего» и «Открыто в текущем фильтре» могут одновременно иметь разные правильные значения.

Сравнение с Java помогает видеть слои: DTO описывает данные, сервис — операции, страница — представление. Но здесь нет отдельного потока запроса на каждый click и нет базы данных. Компоненты продолжают жить между событиями, поэтому копия входных данных, сохранённая однажды, может устареть. Проверяйте изменение при уже открытой странице, а не только после перезапуска.

## Маленькая демонстрация перед работой

Полный независимый файл: `practice/angular-labs/scripts/w3-workshop.ts`. Из корня выполните `node practice/angular-labs/scripts/w3-workshop.ts`. Ожидаемый вывод: `1 0`, затем `false`. Он показывает, почему считать нужно из актуального набора; Angular-сервер и Java API для этого скрипта не нужны.

```ts
type Book = { id: string; returned: boolean };
const countWaiting = (books: Book[]) => books.filter(b => !b.returned).length;
const initial = [{ id: 'a', returned: false }, { id: 'b', returned: true }];
const next = initial.map(b => b.id === 'a' ? { ...b, returned: true } : b);
console.log(countWaiting(initial), countWaiting(next)); // 1, 0
console.log(initial[0].returned); // false
```

Сначала предскажите оба вывода, затем запустите. Вариация: выполните изменение для неизвестного ID. Набор и счётчик должны остаться прежними; никакая случайная строка не должна измениться.

## Практика в IDE — w3-workshop-ex1

Рабочие файлы: `practice/issue-tracker/src/app/app.ts`, `app.html`, `models.ts`, `issue.service.ts`, `issues-list.ts`, `issue-detail.ts`. Запуск: `npm.cmd run practice:angular`, адрес `http://127.0.0.1:4302`. Java API на этой неделе не нужен.

Сначала запишите самостоятельный план из нескольких действий. Затем соберите маршрут списка, детали и возврат. Карточки должны иметь явные входы и события. Статус меняет владелец данных; фильтрация строит новое представление. URL списка хранит статус, прямой URL детали содержит ID. После этой части добавьте счётчик открытых заявок без пошаговой инструкции.

Проверяйте сценарии осмысленно: открыть список; включить фильтр; перейти к детали; изменить статус; вернуться; открыть неизвестный ID; очистить фильтр; обновить вкладку. Отдельно проверьте клавиатуру и отсутствие записей. Записывайте наблюдаемое значение до и после действия. Скриншот красивого списка не доказывает корректность обработки отсутствующей записи.

Оставьте десять минут на чтение изменённых файлов: нет ли двух массивов с независимым состоянием, ручного копирования счётчика, mutation входов и неиспользуемых imports? Не добавляйте HTTP, авторизацию и библиотеку компонентов для завершения этой контрольной точки.

<details><summary>Подсказка 1 — от симптома к владельцу</summary>Если детали и список расходятся, проверьте область providers и ручные new сервиса.</details>
<details><summary>Подсказка 2 — производное значение</summary>Счётчик должен читать исходный signal внутри computed. Проверьте, что обновление создаёт новую ссылку.</details>
<details><summary>Подсказка 3 — маршрут</summary>Не храните выбранную заявку только в поле списка: восстановите её через ID из paramMap.</details>

## Контрольная точка

1. Покажите путь от URL до названия в карточке.
2. Где находится единственный владелец локального набора?
3. Почему изменение статуса меняет computed?
4. Какие данные переживают переход между страницами, но исчезают при перезагрузке?

Новая вариация: добавьте текст «Нет открытых заявок» только когда общий счётчик равен нулю, независимо от текущего фильтра. Объясните отличие от пустого видимого списка.

## Критерии ручной проверки

Оцените пять пунктов: навигация и прямой URL; единый владелец данных; корректные фильтр и счётчик; отсутствие записи и пустое состояние; самостоятельное объяснение изменения. Для каждого отметьте «самостоятельно», «с подсказкой» или «нужна повторная попытка». Непройденный пункт превращается в конкретное короткое повторение, а не закрывается отметкой чтения.
