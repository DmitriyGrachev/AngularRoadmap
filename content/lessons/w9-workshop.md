# Практикум: экран с конкурирующими запросами

360 минут: 45 на временной контракт, 155 на реализацию, 90 на проверки, 40 на новую последовательность событий и 30 на защиту. Нужен [урок об отмене и событиях](/lessons/w9-03). Результат: список, карточка и очередь сохранений работают согласованно при быстрых действиях и отказах.

## Сценарий продукта

В вашей версии `practice/workplace` список уже умеет читать URL и повторять ошибочное чтение. Добавьте кэш чтения карточек по ID и очередь явно подтверждённых сохранений. Пока сохраняется команда A, пользователь может подготовить и поставить в очередь команду B. Каждая команда содержит снимок полей на момент подтверждения, собственный ID для корреляции и ID заявки. Порядок выполнения — порядок подтверждения. Отказ A отображается отдельно и не уничтожает B.

После успешного сохранения карточки её кэш инвалидируется. Следующее открытие этой карточки получает актуальные данные. Если изменились поля, влияющие на список, возвращение к списку также должно прочитать актуальные данные, сохранив URL. Не показывайте «сохранено» по факту finalize. Во время записи текст, который пользователь ещё не подтвердил, не должен перезаписываться ответом предыдущей команды. Это основная проверка сохранности пользовательского ввода.

Граница учебной среды принципиальна: DeskApi — in-memory сервис, операции запускаются RxJS-подпиской и используют таймер. Перезагрузка страницы возвращает seed. Здесь нет HTTP, авторизации, базы и конкурентного доступа двух клиентов. Поэтому практикум доказывает клиентский порядок, обновление кэша и состояние экрана. Серверные версии, идемпотентность и конфликт двух пользователей требуют отдельного интеграционного задания, а не двух вкладок этой лаборатории.

## Уточните политику перед кодом

Определите, как пользователь видит очередь: например, число ожидающих команд и короткий журнал с результатом по ID. Установите разумный учебный предел в три ожидающие команды; когда он достигнут, новое подтверждение не принимается, а черновик сохраняется. Это делает ограничение нагрузки наблюдаемым. Очередь не должна незаметно расти бесконечно. Повтор неуспешной команды создаёт новую команду с тем же снимком либо с текущим черновиком — выберите и подпишите одну политику.

Разделите поля сервера, текущий draft и снимок команды. Если положить в очередь ссылку на изменяемый объект формы, команда B может изменить то, что позже отправит A. Снимок должен содержать нужные примитивные поля и быть независимым от дальнейшего ввода. После ответа обновляйте подтверждённую серверную модель. Применять ответ к draft допустимо только если пользователь не изменил его после отправки; иначе сохраните более новый ввод и явно покажите результат старой команды.

Выберите владельца очереди. Для этого задания она принадлежит открытой карточке: при уходе активная подписка освобождается, ожидающие команды больше не стартуют, а интерфейс заранее сообщает о несохранённых или ожидающих изменениях. В локальном DeskApi отмена таймера предотвращает операцию. Для настоящего HTTP та же клиентская отписка не гарантирует отмену серверной записи; в отчёте это ограничение обязательно. Не делайте вывод о базе из поведения таймера.

## Разобранный пример снимка

Сохраните `snapshot-demo.mjs` в своей временной папке и выполните `node snapshot-demo.mjs`:

```js
let draft = { title: 'VPN недоступен', description: 'Первый текст' };
const command = { id: 'cmd-1', entityId: 'SD-101', patch: { ...draft } };
draft = { ...draft, title: 'DNS недоступен' };
const confirmed = { ...command.patch, updatedAt: '2026-10-28T10:00:00Z' };
console.log(command.patch.title);
console.log(confirmed.title);
console.log(draft.title);
```

Ожидаются «VPN недоступен», «VPN недоступен», «DNS недоступен». Подтверждённая старая команда и новый draft намеренно отличаются. Ошибочным было бы после её ответа безусловно вызвать reset формы старым confirmed. Для вложенных структур поверхностного spread недостаточно: в текущем RequestPatch поля примитивные, а более сложный редактор потребует отдельного снимка вложенных строк.

Сравнение с Java — immutable command DTO, переданный исполнителю. Но frontend ещё решает, какой из нескольких снимков пользователь сейчас редактирует. Ответ сервера не является приказом уничтожить более новый ввод. Поэтому тест должен проверять текст поля после ответа, а не только содержимое журнала успешных команд.

## Практика в IDE — w9-workshop-ex1

Откройте `practice/middle/w9-workshop-ex1/README.md` и `notes.md`. Работайте в своей версии `practice/workplace`, используя идеи middle-05 и middle-06, но адаптируя их к RequestItem и RequestPatch. Не вставляйте общий кэш в каждый компонент отдельно: назовите владельца и срок его жизни. Не меняйте DeskApi так, чтобы он всегда успешно отвечал или терял существующий сценарий 422. Запуск — `npm.cmd run practice:workplace`; проверки — `npm.cmd run test:workplace` и `npm.cmd run build:workplace`.

Создайте управляемый fake API для временных проверок: тест должен сам решать, когда A выдаёт ответ и complete, когда B падает, а когда C начинается. Не используйте случайные задержки. Отдельно посчитайте вызовы загрузчика кэша: два одновременных чтения одного ID дают один запуск; после успешной записи новое чтение даёт новый запуск. Незавершённое старое чтение после инвалидации не должно заново стать актуальным источником.

Пользовательская проверка включает список → карточка → быстрые изменения draft → два подтверждения → один отказ → успешная следующая команда → возврат к списку. Ошибка отображается с привязкой к команде, а не как необъяснимый красный баннер для всего экрана. Проверьте клавиатурную доступность подтверждения и повтора; число ожидающих команд сообщайте без частого навязчивого объявления каждой внутренней смены счётчика.

**Новые данные.** Подготовьте A с title «Проверка VPN», B с title «Проверка DNS», затем продолжите ввод «Проверка почты» без подтверждения. A завершите успехом, B — ошибкой. В поле остаётся «Проверка почты», журнал различает оба результата, новое подтверждение возможно. Затем поставьте три ожидающие команды и проверьте отказ принять четвёртую без потери текста. Уйдите со страницы при активной команде и подтвердите выбранный cleanup-контракт.

## Критерии защиты

Обязательны снимки команд, последовательный запуск, продолжение после отказа, сохранность нового draft, ограничение очереди, правильная инвалидация и отсутствие устаревшего отображения. По каждому пункту нужны действие, ожидаемый результат и наблюдаемое доказательство. Самостоятельный уровень означает перенос на новую последовательность без подсказки; решение с помощью оценивается отдельно. Потеря пользовательского ввода или ложное сообщение об успешной записи требует повторной попытки независимо от числа зелёных тестов.

За пять минут объясните различие latest-wins чтения, последовательной записи и invalidation кэша. Покажите один тест, который падает при намеренном переносе catchError наружу, и другой, который ловит безусловный reset формы старым ответом. Сохраните эти доказательства для итогового этапа; они демонстрируют поведение, которое редко проверяется чтением кода по счастливому сценарию.
