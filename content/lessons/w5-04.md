# Серверные ошибки полей и актуальность ответа формы

120 минут. Результат: ответ 400 объясняет конкретное поле, а старая ошибка не прикрепляется к уже изменённому значению. Нужны [POST](/lessons/w5-03), [валидация](/lessons/w5-02), [unknown](/lessons/w2-04).

## Ситуация и прогноз

Отправлено название «Повтор». Пока запрос шёл, пользователь ввёл «Новое». Сервер ответил ошибкой старого названия. Правильно ли показывать «Новое уже существует»? Нет: ошибка относится к снимку отправленных данных. Сначала выберите политику: запретить редактирование на время отправки либо проверять актуальность перед показом field error. Оба варианта требуют явного кода.

## Серверная проверка имеет другую информацию

Клиент знает длину строки и обязательность поля. Сервер знает существующие записи, ограничения предметной области и права. Поэтому valid-форма может получить 400. Это нормальная ветвь процесса, а не повод отключать кнопку навсегда. Общую message показывают рядом с формой, fieldErrors связывают с соответствующими полями. 500 и сетевой сбой не нужно маскировать сообщением «название неверно».

Подготовленный контракт ошибки — `{ message, fieldErrors }`, причём значение каждого поля — массив строк, например `{ title: ['Название слишком короткое'] }`. Перед использованием читайте тело как недоверенные данные: HttpErrorResponse описывает транспортную оболочку, но `.error` не гарантированно имеет нужную структуру. Там может быть строка HTML от proxy или пустое тело. Не делайте `error.error.fieldErrors.title` без проверки: тогда обработчик ошибки сам бросит новую ошибку, скрыв исходную.

Отдельный signal серверных сообщений часто проще, чем смешивание их с validator errors. Он не меняет valid/invalid автоматически, зато позволяет явно очистить сообщение при изменении поля и перед новой отправкой. `control.setErrors({ server: message })` тоже возможен, но нужно сохранить существующие ошибки и понимать, что следующий цикл validation может их пересчитать. Не затирайте required, устанавливая новый объект только с server.

Ошибка конкретного поля должна исчезнуть после относящегося к нему исправления либо после новой попытки. Но общая ошибка соединения не должна исчезать от изменения любого символа, если пользователь по-прежнему не смог сохранить. Выберите понятную политику и покажите различие состояния «изменено» и «подтверждено сервером».

## Разобранная демонстрация

Полный файл: `practice/angular-labs/scripts/w5-04.ts`. Выполните из корня `node practice/angular-labs/scripts/w5-04.ts`. Ожидаются объект с message и nickname «Псевдоним занят», затем общая message «Не удалось сохранить». Java API не нужен. Нейтральная функция читает ответ регистрации читателя; она не является готовым обработчиком всех ошибок API трекера.

```ts
type ReaderError = { message: string; nickname?: string };

function readReaderError(value: unknown): ReaderError {
  if (typeof value !== 'object' || value === null) {
    return { message: 'Не удалось сохранить' };
  }
  const object = value as Record<string, unknown>;
  const message = typeof object['message'] === 'string'
    ? object['message'] : 'Не удалось сохранить';
  const fields = object['fieldErrors'];
  if (typeof fields !== 'object' || fields === null) return { message };
  const nickname = (fields as Record<string, unknown>)['nickname'];
  return Array.isArray(nickname) && typeof nickname[0] === 'string'
    ? { message, nickname: nickname[0] } : { message };
}

console.log(readReaderError({
  message: 'Проверьте поля', fieldErrors: { nickname: ['Псевдоним занят'] },
}));
console.log(readReaderError('<html>Proxy error</html>'));
```

Первый вывод содержит конкретное сообщение nickname, второй — безопасную общую ошибку. Функция проверяет только нужные поля: полный универсальный schema framework для такого примера не требуется. Вариация: передайте `fieldErrors: null` и затем число вместо строки ошибки. Обработчик должен вернуться к общему сообщению без исключения.

Теперь модель актуальности: сохраните `const sentNickname = control.value` перед запросом. При ответе сравните текущее `control.value` с sentNickname. Если значения различаются, не прикрепляйте серверное сообщение к новому тексту. Укажите, что отправленный вариант отклонён и текущие изменения ещё не сохранялись. При нескольких разрешённых запросах одного сравнения значений мало: понадобился бы ID попытки. В курсе параллельные submit запрещены, что упрощает модель.

## Два устойчивых пути

Если форма блокируется, снимок не меняется во время запроса. При disabled controls учитывайте getRawValue и порядок получения DTO: сначала получить данные, затем блокировать. При ошибке восстановите доступность во всех ветвях, включая завершение и уничтожение. Недостаток — пользователь не может исправлять текст, пока ждёт ответ.

Если редактирование разрешено, не сбрасывайте всю форму при успехе старой попытки: вы уничтожите новые изменения. Можно явно отделить подтверждённый снимок от текущего черновика. Это более сложный UX, поэтому для первого учебного варианта блокировка полей на время короткой отправки допустима. Главное — объяснить выбранную границу и проверить её, а не оставить случайное поведение.

## Мост от Java

Ошибки Bean Validation обычно превращаются backend в response DTO. В браузере это уже обычный JSON, названия полей должны совпадать с договорённостью. `title` и `name` не станут одним полем автоматически. Ошибка от предыдущей попытки похожа на ответ по устаревшему запросу, но в форме нельзя просто отменить запись и считать её несуществующей — помните семантику POST.

## Критерии ручной проверки

400 отображается у нужного поля; 500 не приписывается title; повреждённое тело не ломает обработчик; ошибка не стирает ввод; повтор возможен; поздний ответ не обвиняет новое значение; политика ожидания объяснена.
