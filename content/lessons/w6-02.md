# Диагностика: воспроизведение, гипотеза, проверка

120 минут. Результат: вы находите причину дефекта, подтверждаете исправление тем же сценарием и не меняете случайные участки. Нужны [чтение цепочки](/lessons/w6-01), [Network](/lessons/w4-01), [состояния](/lessons/w4-03).

## Ситуация и прогноз

«Иногда список пустой» не является воспроизводимым описанием. Запишите URL, шаги, исходные данные, ожидание и фактический результат. Может оказаться, что пустота возникает только на третьей странице после смены фильтра. Предскажите: если API честно возвращает items=[] для page=2 узкого набора, ошибка находится в UI-состоянии страницы, а не обязательно в фильтрации Java.

## Двигайтесь от наблюдаемой границы

Начните с воспроизводимого сценария на одной вкладке. Уберите лишние действия, но не условия возникновения. Если ошибка требует быстрой смены текста, медленный одиночный ввод не является повторной проверкой. Если она требует прямого URL, запуск только через меню не подтверждает исправление. Минимальный сценарий сохраняет причину, а не просто делает демонстрацию удобной.

Разделите цепочку на границы: DOM-событие, состояние компонента/URL, HTTP-запрос, HTTP-ответ, преобразование, отображение. На каждой спросите: соответствует ли наблюдение ожиданию? Если payload уже неправильный, нет смысла дебажить серверный parser. Если ответ правильный, идите к чтению полей и актуальности состояния. Это двоичный поиск по ответственности, а не угадывание по названию файла.

Гипотеза должна быть опровержимой. «Angular не обновляется» слишком широко. «Метод мутирует прежний массив, поэтому computed не получает уведомление» даёт конкретную проверку: сравнить ссылки до/после и посмотреть вызов update. «Старый ответ перезаписывает новый» проверяется управляемой перестановкой задержек. Запишите ожидаемый признак до правки, чтобы не подгонять объяснение под случайный результат.

Debugger позволяет остановиться в обработчике и проверить фактические значения. Смотрите Call Stack, Scope и порядок входа в callbacks. Breakpoint на исключениях полезен, если ошибка перехватывается выше и превращается в общий текст. Не оставляйте бессистемные console.log во всех слоях: они создают шум и могут вывести чувствительные значения. Для учебного API достаточно ID, page и типа состояния.

## Разобранная демонстрация

Полный файл: `practice/angular-labs/scripts/w6-02.ts`. Из корня выполните `node practice/angular-labs/scripts/w6-02.ts`. Ожидается `{ q: 'редкая книга', page: 3 }`: это намеренно ошибочное сохранение старой страницы для диагностического опыта. Браузер и Java API не нужны. Сначала предскажите результат, затем найдите причину:

```ts
type Search = { q: string; page: number };
function changeQuery(current: Search, q: string): Search {
  return { ...current, q }; // намеренный дефект: номер старой страницы сохранён
}
const before = { q: '', page: 3 };
const after = changeQuery(before, 'редкая книга');
console.log(after); // { q: 'редкая книга', page: 3 }
```

Предметное требование: новая строка поиска начинается с первой страницы. Гипотеза — переход состояния не сбрасывает page. Наблюдение подтверждается до HTTP, значит backend может работать правильно. Исправление функции должно вернуть page=0 при смене q; выполните его сами в demo. Затем проверьте прежний сценарий и соседний: переход на следующую страницу при том же q должен сохранять поиск.

Это исправление относится к примеру, а не указывает строку дефекта в вашем трекере. В рабочем проекте переход может находиться в обработчике, построении URL или преобразовании queryParamMap. Нужно найти фактического владельца. Вариация: измените status вместо q и сформулируйте, должен ли номер страницы тоже сбрасываться.

## Типичные ложные исправления

Полная перезагрузка страницы иногда скрывает неправильную синхронизацию, потому что сбрасывает память. Это не исправление навигации назад/вперёд. `setTimeout` может поменять порядок событий, но не гарантирует его при другой скорости сети. `as any` скрывает ошибку типа, не меняя данных во время выполнения. Удаление failing assertion делает тест зелёным без изменения поведения.

Минимальная правка должна устранить причину в одном владельце. После неё пройдите исходный сценарий, ближайший пограничный случай и подходящую проверку. Если изменён только parser page, полезны плохая строка и отрицательное число. Если исправлена отмена запроса, нужен изменённый порядок ответов. Не запускайте огромную случайную матрицу вместо доказательства ключевой гипотезы.

## Мост от Java

Логи сервера и browser debugger показывают разные процессы. Java breakpoint не остановит TypeScript-код после получения JSON; browser breakpoint не покажет состояние транзакции backend. Correlation ID помогает в реальных системах, но здесь достаточно сопоставить запрос по URL/времени. Важнее правильно назвать слой ошибки, чем использовать знакомый инструмент в неподходящем месте.

## Проверка понимания

1. Что делает гипотезу проверяемой?
2. Почему перезагрузка может скрыть дефект?
3. Как отличить неправильный запрос от неправильного отображения ответа?
4. Почему повтор должен сохранять условия гонки?

Новая вариация: тот же симптом возникает только после browser Back. Обновите сценарий и место наблюдения, не добавляя случайный таймер.

## Критерии ручной проверки

Есть короткий воспроизводимый сценарий; гипотеза подтверждена значениями; правка устраняет причину; исходный и соседний случай проверены; временные логи/дефекты убраны; вы объясняете, почему проверка могла бы поймать повтор ошибки.
